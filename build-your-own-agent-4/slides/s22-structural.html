CH 5 · 与 pi / oh-my-pi 的区别

水分挤完，剩下四条 —— 配置到不了的地方

每一条都必须满足：要么换语言，要么换分发形态，要么重写内核。改配置、写 SKILL.md、装扩展，都到不了。
S1

分发形态：1 个依赖的静态单二进制

  • CGO_ENABLED=0 交叉编译四平台，go:embed 把 397 KB 的 skill（加 prompts 共约 403 KB）打进二进制，目标机零运行时
  • 对照：pi 是 npm + 27 个依赖；omp 是 npm + 原生 addon + 664 个 npm 包 + 912 个 crate
  • 为什么配不出来：这是换语言才能得到的东西。而它只在一个场景里真的重要 —— scp 到一台离线的、受限的、不归你管的分析机
S2

把别的 agent 当模型用

  • cli-tmux provider 1,443 行：tmux 生命周期 + 三种私有 JSONL 事件格式 + 原生 session 续接 + Claude 任务表状态机
  • 注释原话：「在 detached tmux 里跑一个本地 coding CLI，tail 它的 JSONL stdout，让操作员实时看到推理、工具活动和 token 计数」
  • 为什么是结构性的：pi/omp 的 provider 契约不覆盖这种形态。它把 re-agent 从「一个 agent」变成「别人 agent 的编排者」，顺带改了计费模型 —— 吃订阅，不吃 API token
S3

为「模型拒答」设计的两阶段隔离

  • 四个开关同时打在 RunOptions 上：Isolated + FreshSession + 独立 system prompt + 收窄到 14 个只读工具 —— 内核级支持，不是外挂
  • 这是四条里唯一一条能直接从领域推出来的架构。omp 的 11 种 dialect 是同一架构家族，但它解的是能力问题，不是拒答问题
  • 而且红线写死在代码和单测里：不许翻译、不许暗语、不许 prompt laundering
S4

扩展性方向：把几十个钩子压成 1 个 interface

  • 全仓只有一个 interface（types.Provider，三个方法）+ 8 个回调。对照 pi 的 33 个钩子、omp 的 25+39 钩子 + 5 类扩展点 + 14×17 能力矩阵
  • pi 和 omp 把权限、plan mode、todo、MCP、上下文发现全推到扩展层；re-agent 全焊进内核，扩展只剩数据（JSON / md / MCP）
  • 这是两个互相配置不到的极点。没有谁对谁错 —— 一个赌「别人会来扩展」，一个赌「只有我自己会改」
整章一句话 → re-agent 不是「更小的 pi」，也不是「配了 RE prompt 的 pi」。它在四件事上做了配置到达不了的选择：换语言换分发形态、把别的 agent 当 provider、为拒答设计两阶段隔离、把扩展面压成一个 interface。
除此之外 —— skill、prompt、工具清单、审批闸、MCP —— 全是 pi/omp 用现成机制就能复刻的配置层；而重试、会话树、并发调度、quirk 表、中断模型这五项，它是明确落后的。这就是「一个人写一个 harness」到今天能到的真实位置。
判据：只改配置 / SKILL.md / 现成扩展能否复刻 · 逐条证据见研究笔记 R04 §2 🔴 S1–S4
