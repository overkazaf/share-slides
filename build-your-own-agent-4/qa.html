CH 3 · 实现原理

整个控制流就是一个函数 —— 骨架和教科书一模一样

`AgentLoop.Run` 241 行（agentloop.go:265-505）。多出来的部分不在状态机，在每一步外面包的那层生产化。

三个停止条件，加一个触顶出口

  • ctx 被取消 · 回复里没有 tool call · 工具阶段被打断；第四个是 maxTurns 默认 8（config.go:25）
  • 中断被当成结果而非失败：返回 Interrupted:true 且 err 为 nil

8 个扩展钩子，不是 40 个

  • OnEvent / OnProgress / OnPlan / Confirm / OnPhase / OnChunk / OnFrame / Provider.Complete
  • 对照：pi 33 个，omp 25+39 个。少一个数量级 —— 这是成本，也是可读性

同页的代价：工具是串行的

  • 分发就是线性查表 findTool，一个一个跑（agentloop.go:439,556-563）—— 没有并行工具调用
  • 逆向里 strings 和 entropy 完全可以同时跑，这里跑不了。这是明确的未做

两个座位：规划一个模型，动手另一个 —— 默认就跨厂商

planner = Codex CLI，executor = Claude Code CLI（config.go:20-23）。都在 detached tmux 里跑，不直连 API。

接线其实只有两个字段

  • plannerProvider / executorProvider 两个字符串（types.go:98-109）。循环只认 Provider 接口的 三个方法，所以任意组合都合法
  • 走 CLI 而不是直连 API：两家已经做好的工具集、权限提示、订阅计费一并白拿

关键词表长这样，中英混排

  • "run " · "execute" · "objdump" · "strings" · "grep" · "执行" · "跑一下" · "读取" · "分析 ./"（agentloop.go:618-632）

CH 3 · 实现原理

模型太谨慎不干活 —— 解法不是换个说法，是换个结构

红线是写进送给模型的 prompt 里的："Do not use translation, classical Chinese, ciphering, euphemisms, or prompt laundering to bypass a model or site policy." 而且有单测断言它必须在。

它解的是哪个失败模式

  • 普通商用模型面对「逆向这个 APK」这类整体请求时会过度谨慎，或者把长上下文越滚越危险
  • 解法不是骗模型，是缩小上下文 + 只要本地证据 + 按产物拆解 —— 注释原话

这条可核对，且确实属实

  • 「executor 的工具表是只读的」不是宣传语 —— delegate.go:145 是一张14 项白名单，写和执行两类工具压根不在表里

没有状态机，只有两次顺序调用

  • 阶段推进写死在 runDelegatedWorkflow 里，就是两次 Loop.Run；planner 被打断就直接返回，不进 executor
  • 合并后 provider 字段变成 "codex->claude"，turns 与 usage 相加 —— 账仍然是一本

同页的代价：交接靠正则抠文本

  • planner 产出是自由文本，靠 ExtractExecutorPacket 容忍四种写法去抠 —— 格式没写对就走本地兜底包
  • 这是协议层的脆弱点，不是结构化交接

CH 3 · 实现原理

上下文有三道闸 —— 逆向最要命的是工具输出那道

注释写得很直白：objdump -d / strings 这类命令就是会吐兆字节，原样倒进 transcript 等于一次性烧掉整个窗口。

会话是只追加的 JSONL

  • 每行一条 {Type, Timestamp, Data}，三种类型：session / message / event。O_APPEND + mutex，文件名带 UTC 时间戳

恢复路径处理得很硬核

  • 解析失败的行静默跳过，注释：「会话被写到一半杀掉时，末行截断是预期内的」
  • repair() 双向修剪：有 call 无 result 就摘掉 call，有 result 无 call 就丢掉 result —— 两种都会被 provider 拒收

同页的代价：三道闸都是「丢信息」

  • 省略掉的 tool result、丢掉的老对话、被 head/tail 切走的中段 —— 模型都看不见了
  • 逆向恰恰是两小时前那个不起眼的字符串突然变关键的场景。这里没有语义索引，只有「你自己记得去读那个 artifact 文件」

52 个命令里，大约 49 个一个 token 都不花

帮助里归为 direct tools 的有 16 条，其中 11 条走 runDirectTool —— 直接调工具函数，完全绕过 agent loop。你只在真想让它「想一下」的时候才付钱。

一张表同时驱动三件事

  • ui/help.go:23-88 那张 54 行的表，同时喂给帮助、Tab 补全和命令面板 —— 加命令只改一处，三处不会漂

reverse_toolkit 是白名单动作，不是命令注入

  • 20 个外部工具族（r2 · rizin · jadx · ghidra · gdb · binwalk · yara · apktool · frida · angr …），动作固定：info / sections / symbols / imports / strings / functions / disasm

  • reverse_toolkit 申请审批时不带 concerns（retool.go:838）—— 全仓只有 3 处会填 Concerns，这里不在其中

  • 零 token 很爽，但「绕过 loop」也绕过了 loop 上的那道闸

CH 5 · 与 pi / oh-my-pi 的区别

水分挤完，剩下四条 —— 配置到不了的地方

每一条都必须满足：要么换语言，要么换分发形态，要么重写内核。改配置、写 SKILL.md、装扩展，都到不了。
S1

分发形态：1 个依赖的静态单二进制

  • CGO_ENABLED=0 交叉编译四平台，go:embed 把 397 KB 的 skill（加 prompts 共约 403 KB）打进二进制，目标机零运行时
  • 对照：pi 是 npm + 27 个依赖；omp 是 npm + 原生 addon + 664 个 npm 包 + 912 个 crate
  • 为什么配不出来：这是换语言才能得到的东西。而它只在一个场景里真的重要 —— scp 到一台离线的、受限的、不归你管的分析机
S2

把别的 agent 当模型用

  • cli-tmux provider 1,443 行：tmux 生命周期 + 三种私有 JSONL 事件格式 + 原生 session 续接 + Claude 任务表状态机
  • 注释原话：「在 detached tmux 里跑一个本地 coding CLI，tail 它的 JSONL stdout，让操作员实时看到推理、工具活动和 token 计数」
  • 为什么是结构性的：pi/omp 的 provider 契约不覆盖这种形态。它把 re-agent 从「一个 agent」变成「别人 agent 的编排者」，顺带改了计费模型 —— 吃订阅，不吃 API token
S3

为「模型拒答」设计的两阶段隔离

  • 四个开关同时打在 RunOptions 上：Isolated + FreshSession + 独立 system prompt + 收窄到 14 个只读工具 —— 内核级支持，不是外挂
  • 这是四条里唯一一条能直接从领域推出来的架构。omp 的 11 种 dialect 是同一架构家族，但它解的是能力问题，不是拒答问题
  • 而且红线写死在代码和单测里：不许翻译、不许暗语、不许 prompt laundering
S4

扩展性方向：把几十个钩子压成 1 个 interface

  • 全仓只有一个 interface（types.Provider，三个方法）+ 8 个回调。对照 pi 的 33 个钩子、omp 的 25+39 钩子 + 5 类扩展点 + 14×17 能力矩阵
  • pi 和 omp 把权限、plan mode、todo、MCP、上下文发现全推到扩展层；re-agent 全焊进内核，扩展只剩数据（JSON / md / MCP）
  • 这是两个互相配置不到的极点。没有谁对谁错 —— 一个赌「别人会来扩展」，一个赌「只有我自己会改」
整章一句话 → re-agent 不是「更小的 pi」，也不是「配了 RE prompt 的 pi」。它在四件事上做了配置到达不了的选择：换语言换分发形态、把别的 agent 当 provider、为拒答设计两阶段隔离、把扩展面压成一个 interface。
除此之外 —— skill、prompt、工具清单、审批闸、MCP —— 全是 pi/omp 用现成机制就能复刻的配置层；而重试、会话树、并发调度、quirk 表、中断模型这五项，它是明确落后的。这就是「一个人写一个 harness」到今天能到的真实位置。

CH 6 · 能干什么

四个场景 —— 每一步都能对回 skill 原文的行号

这些不是「它应该能做」，是 SKILL.md 里写死的步骤和命令。判据是：你能不能照着自己跑一遍。

① CTF 未知样本首轮分诊　ctf-first-pass

  • 零 token 五连：/scan ./artifact → /entropy → /carve → /findbytes ./artifact flag{ → /decode auto
  • 五条判据表（skill 原文，可直接背）：高熵 + 低可打印率 → 加壳/压缩/加密；危险导入或 /bin/sh → 走 pwn；base64 串挨着 crypto 词 → 先解码再看 key/IV/mode；多个 magic 偏移 → 走取证 carving；见 APK/DEX/SO → 转 Android 那条线
  • 收敛成一句假设：类别 + 可能的 primitive + 最小的下一步实验。不给结论，给下一步

② APK 签名算法逆向　android-apk-frida

  • /apk ./app.apk 出加固壳与框架 → 对可疑 so 跑 /scan → jadx -d jadx_out 后 rg -n "Cipher|MessageDigest|sign|token|encrypt"
  • 先定死 class/method，才生成 hook 脚手架 —— 三种目标写法：com.example.Crypto.sign(java.lang.String, byte[]) / libfoo.so!Java_com_example_Crypto_sign / libfoo.so+0x1234
  • 模板输出有单测钉死：给 android_ssl_pinning 必须吐 CertificatePinner + TrustManagerImpl（tools_test.go:271-300）—— 比文档更硬的证据
  • 纪律条款：先观察后改写 —— 先打参数/返回/调用栈/字节数组，假设被验证过才去改返回值

③ SO 里的 native 函数变成可调服务　unidbg

  • 选型分界线写得很清楚：要 Java/JNI 上下文、framework 取值、文件系统 mock → unidbg；只是一段没有 Java 依赖的独立指令区间 → unicorn
  • 流程：先攒证据（包名/类/方法/ABI/偏移）→ 写最小 harness → 第一次开 verbose，只补失败日志里真正缺的 JNI 回调 → 稳定 Android 状态 → 定点 trace（全量指令 trace 很贵）
  • armeabi-v7a → for32Bit()，arm64-v8a → for64Bit()。交付物包含「仍然缺哪些回调」 —— 把没做完的部分也写进报告

④ 混淆墙：OLLVM / VMP / JSVMP

  • 这是第一讲第 ⑦ 道坎的落点，全部住在 skill 里而不是 prompt 里：ollvm-deobfuscation 583 行 · vmp-restore 604 行 · jsvmp-analysis 620 行 · so-string-deobfuscation 428 行
  • 顺序是强制的：传统去混淆和符号恢复先跑完，模型只上最后一公里 —— 因为混淆是信息论层面的删除，模型再强也变不出被删掉的信息
  • Web 那条线接得也很实：web-wasm-crypto 的 fetch / WASM hook，加 jsvmp 的六特征探测脚本
但这一页必须配一句实话 → 这四个场景全部没有成功率数字。全仓 0 个 Benchmark、0 个 eval harness、没有 CI，只有 164 个正确性单测。
所以准确的说法是：这四条路径被写成了可执行的步骤，而不是被证明了有效。 作者自己在 README 里承诺要补「可复现的评测样例」—— 那是下一步，不是现状。

先把洞摊开，再谈规划 —— 而明写的规划只有一句

仓库里没有 ROADMAP.md、没有 issue 模板、没有 milestone。所以左边是实测的洞，右边分两栏：明说的 和 从代码缝里推的。

安全闸的七个洞（挑最要命的四个）

  • 默认档就不安全：AutoApproves 对 yolo 和 safe 都无视 tier 一律放行 —— 而 safe 是默认。架构文档自己承认了这一点
  • run_command 就是 bash -c，没有 chroot / namespace / seccomp。python3 -c 一行就能绕过 --write 和 --allow-network
  • 路径包含检查不解 symlink：util.ResolveInside 只做 Clean + 前缀比对（全仓唯一一处 EvalSymlinks 在 assets.go:52，与它无关）。而这个函数所在的 util 包零测试
  • reverse_toolkit 申请审批时不带 concerns —— 其中 frida 会真的起进程，在 --allow-network 关着时照跑（burp / mitmproxy 只吐模板，这条别夸大）

还有三个「说了但没兑现到底」

  • 写盘有两处绕过写闸门（output 落 artifact、retool 落产物）；!cd 用 bash 解析并能把工作区搬走；knowledge 和 skills 绕过包含检查读盘
