一句话主旨

值得花一整讲，是因为它和 pi 同源，所以每一处差异都是一个可归因的工程决定；但它不是推荐给你用的产品。

怎么讲

（停一拍）先回答一个合理的质疑：一个人写的 fork，凭什么占你们一个小时。（指左边这张青色卡）三个理由。第一，第一讲那张 harness 七层地图，我找了一圈，omp 是我能找到的唯一一个七层全点满的公开样本——上下文管理、工具层、权限、多模型适配、记忆、TUI，它每一层都有自己的、明显不是抄来的做法。第二个理由才是关键，这也是我为什么把它排在 pi 后面讲：它和 pi 是同一份基座。这意味着什么？意味着两边的每一处差异都是一个可归因的工程决定，不是风格差异，不是「这个人喜欢这么写」。上游有的它删了，那是它判断不值；上游没有它加了，那是它判断值。你等于拿到了一份带对照组的实验记录，这在开源项目里是很稀有的。第三个理由——（重）它把失败也留在仓库里。这个我要特别强调，因为大部分项目只留成功：仓库里有回滚记录、有引用具体 issue 编号的注释、CH5 里你会看到一条 benchmark，作者自己测出来 Rust 版本在小 payload 上比原来还慢，他没删这个结果，而是在代码里写了一句规矩——「若更慢，不要切换调用点」。（停一拍）能看到人家怎么面对自己的失败，这比看功能列表有用得多。

（指中间绿卡）那你今天能带走什么。这四条我是按可迁移性排的，不是按精彩程度排的——也就是说，越靠上的越可能明天就用得上，跟你用什么语言、什么框架关系越小。第一条规则三桶路由，同一份 markdown 规则文件，按 frontmatter 分流到三种不同的执行时机，这个想法脱离 omp 也成立。第二条逐工具并发调度，核心逻辑十三行，你抄完就能用。第三条是个方法而不是代码——把口味问题变成可测问题：编辑工具怎么写更好，这本来是个吵不完的事，他自建了一套 edit benchmark 把它变成有数的事。第四条是那份别抄清单，六项我认为的过度工程，每项我尽量附了代价数字。

（指右边玫红卡，慢下来）但是——这张卡我讲得最慢，因为它划的是边界。第一，这一讲不做产品推荐。我不劝你换工具。我把话说明白：omp 的口味很重，多数人不该用它。它有大量为作者一个人的工作流做的取舍，你照搬会很难受。今天讲它，是把它当研究样本，不是当推荐位。第二，这一讲不跑分。所有性能数字都只引用仓库里自带的 benchmark 和代码注释——原因很实在，我本机没装 bun，跑不起来。所以凡是我没实跑过的，页面上一律有标注，你看到那个标注就知道那是转述不是实测。这条我宁可讲得难听一点，也不想让你把二手数字当成我验过的。第三，先认错再讲课——下一页就是上一讲的三处更正。（指底下那行小字）另外，这一讲背后的八份研究笔记同步开源，仓库和 discord 都在这行，页面上放不下的细节全在里面。

P3 · 上一讲的三处更正：先认错，再讲课

提词

  • 三处：FORK.md 归属错 / 「点阵图」措辞误导 / BM25 已删
  • ① 最严重：张冠李戴。全史 16,613 commit，git log --all -- FORK.md 零命中
  • ② 不是信息可视化，是缩微胶片：点阵字体印成 PNG，vision 模型 OCR 读回

  • ③ BM25 工具发现已删除，改 xd:// 虚拟设备挂载
  • 根因：依据 v16.3.12 旧笔记，omp 2.4 天一个版本号

一句话主旨

上一讲讲 omp 的那一页错了三处，根因是同一个——我用的是旧笔记，而结论没有和取证日期绑在一起。

怎么讲

（停一拍，不要笑场，正常语速开始）上一讲我有一页讲 omp，那一页，错了三处。今天开讲之前先把它改掉。（停一拍）三处我一条一条说，说错在哪、为什么会错。

（指第一张卡）第一处，也是最严重的一处。上一讲我说，omp 最值得抄的东西是它的 FORK.md，里面有一套 tier 成本模型——把 fork 相对上游的改动按维护成本分层。我甚至在页脚标了出处，写的是 oh-my-pi/FORK.md。（停一拍）这个文件从来没有存在过。 我这次把仓库 unshallow 拉了全史，一万六千六百一十三个 commit，git log --all -- FORK.md，零命中。它不在 HEAD 里，也不在任何一个历史版本里。那份 tier 模型是真实存在的，但它出自某个私有下游 fork 自己写的维护手册——我当时手上同时开着两个仓库的笔记，把它安到了 omp 头上。这是张冠李戴，属于最不该犯的一类错，因为它不是判断错误，是取证错误。（指卡底那行小字）那套 tier 模型本身我今天仍然认为成立，但今天开始它归属于「某个下游 fork 的做法」，不再挂在 omp 名下。

（指第二张卡）第二处，措辞误导。上一讲我说 snapcompact 把旧的对话记录「画成点阵图」，还说它零 LLM 调用。（停一拍）方向是对的，但「画成点阵图」这个说法会让人往错的地方想——听着像是信息可视化，像是把内容抽象成图表。不是。 它做的事更接近缩微胶片：把文本用点阵字体直接印成一张 PNG，需要的时候，让 vision 模型 OCR 读回来。信息一个字都没有被抽象掉，只是换了个存储介质。另外「零 LLM 调用」我也得加个限定——是零额外调用，压缩这个动作本身确实不需要再叫一次模型；但那张帧此后每一轮都要重新附在上下文里，是按 vision token 计费的。（指卡底）这个区别不是抠字眼——它直接决定了压缩率该怎么算，CH3 那一章我会拿真实数字回来讲，你会看到压缩率其实并不是这个设计的卖点。

（指第三张卡）第三处，过时。上一讲我说 omp 默认只给模型 6 个必备工具，其他工具让模型自己用 BM25 检索出来。这个机制已经被删除了，CHANGELOG 里有明确的删除记录，现在改成了 xd:// 虚拟设备挂载这套做法。（停一拍）那我为什么会讲一个已经不存在的机制——因为我写上一讲的时候，依据的是我在 v16.3.12 时期做的旧笔记。而这个项目，（重）平均 2.4 天出一个版本号。（停一拍，慢）所以这三处错误，前两处是我自己不细致，第三处不完全是——但它们其实是同一个根因：我的结论没有和取证日期绑在一起。一条关于快速演进项目的结论，脱离了「我是在哪个 commit 上看到的」，它的保质期可能只有几天。这是我这次最大的收获，也是我今天想让大家带走的第一件事：讲快速演进的项目，取证日期必须和结论绑在一起。（指页脚）所以你会看到，今天每一页页脚都标了取证基准 HEAD，就是为了防这件事。这不是仪式感，是我交过学费的。

（停一拍，收）好，认完了，我们开始讲课。

一句话主旨

omp 在用 omp 开发 omp——全史 16,613 个 commit 里 2,564 个署名给它自己驱动的机器人，而贡献指南已经开始给这个机器人让路了。

怎么讲

上一页结尾我说算术对不上——72 万行 TS、18.5 万行 Rust、8.3 万行 Python、日均 155 个 commit，一个人。这一页给缺的那块。（停一拍）标题就是结论：omp 的代码，有一部分是 omp 自己写的。

左边这张图是完整的回路，五步，全部来自 python/robomp/README.md 的前 22 行，我照着走一遍。①有人在 GitHub 开一个 issue，robomp 先把它分类打标签——bug、documentation、question、enhancement、proposal、invalid、duplicate，七类。②它起一个 omp 子进程，注意这行小字：omp --mode rpc，也就是把 omp 当成一个可被程序驱动的服务跑起来，每个 issue 开一个独立的 git worktree。这里有个设计我很欣赏——下面那行：PAT 不给 agent，写回 GitHub 走一个单独的 sidecar 进程。也就是说 agent 有改代码的权限，但没有对外发言的凭证，这是很干净的一刀。③按标签分流：bug 和 documentation 会真的去复现、在新分支上修、跑验证；question 是发一条评论，四小时内没人反对就自动关掉；enhancement 只评论不动手。④开 PR，而且格式是钉死的——正文必须有 ## Repro、## Cause、## Fix、## Verification 四段，加一句 Fixes #N。后续如果 issue 下面又有评论，它用 --continue 恢复同一个 omp session 接着聊。⑤合并，代码进主干。

（停一拍）然后看这条橙色的虚线——从⑤绕回①，旁边写着「改好的 omp，下一轮接着用」。这就是自举回路。 这个词我想多说两句，因为它很容易被当成一句噱头。编译器的自举大家都熟：用 C 写第一版 C 编译器，然后用它编译自己。那个回路的意义在于——你对自己的每一次改进，会立刻回到你自己身上。omp 这里是同一个结构：他改进了 omp 的 bug 定位能力，下一个 issue 进来，robomp 用的就是改进后的版本，修得更准；修得更准，就有余力去改更难的地方。（停一拍）这就是上一页那个算术怎么对上的——153 万行不是一个人手敲出来的，是一条回路跑出来的。这也是我为什么把这页放在第一章的最后：前两页讲「多大」，这页讲「怎么可能这么大」。

再看右边这一栏。最上面这条堆叠柱是全史 16,613 个 commit 的署名构成，我把仓库 unshallow 之后重新数的。绿色最大那块，me@can.ac，Can Bölük 本人，8,807 个，53%。橙色这块，omp@can.ac，也就是 roboomp，2,564 个，15.4%。青色那块，Mario Zechner，1,339 个，8.1%——这就是我上一页说的，pi 时期的历史被完整带过来了。剩下灰色的是另外 403 个提交身份，全史一共 407 个。

（停一拍）中间这个玫红框是本页最有冲击力的一条，CONTRIBUTING.md 第 28 到 32 行，我念英文原文：「Do not open an issue for work you are about to submit.」——如果你打算自己实现某个改动，不要先为它开 issue。理由在下面：robomp 会把「可行动的 issue」当成工单捡起来，可能并行做同一个修复，浪费算力和维护者时间。 （停一拍）我第一次读到这句是真的愣了一下。我们写了这么多年的贡献指南，「先开 issue 讨论再动手」几乎是所有开源项目的第一条规矩，理由是避免重复劳动。这里规矩被反过来了，理由还是避免重复劳动——只不过要避开的那个「重复劳动者」，不是另一个人类贡献者，是项目自己的机器人。协作规则第一次要为 AI 贡献者腾地方，这不是修辞，是白纸黑字的一条硬规矩。

（停一拍）但这条不能只讲光鲜面，代价必须一起讲，看下面琥珀色那个框——同一份 CONTRIBUTING.md 的另一面，第 38 到 51 行：「AI agents are welcome as tools, not as unattended contributors.」 AI agent 欢迎作为工具，但不欢迎作为无人看管的贡献者。具体四条：把 agent 约束在议定范围内、逐个文件审阅它改的东西、亲自跑检查并验证行为、审完才准提 PR。还有更狠的两条——PR 正文必须至少有一句你自己写的话；以及「bun check 通过」本身不算验证。（停一拍）你把这两个框放在一起看，这个项目的立场其实非常清楚：机器可以生产代码，但责任不能转移。「你为这段代码负责，不管它是谁、是什么东西生成的。」

那问题就来了，也是我留给大家带走的问题：机器人写的这 2,564 个 commit，谁 review 的？ 从公开信息看，答案是维护者本人——也就是那个已经写了 8,807 个 commit 的人。这就是自举回路真正的代价：回路能把生产的吞吐放大，但没法把审阅的吞吐放大。 你造得越快，瓶颈就越往 review 挤，最后压在同一个人的注意力上。这个项目的所有取舍——包括后面 CH6 那页 309 次「Stop.」的事故——某种程度上都是这个瓶颈的后果。

最后一句必须说，看底下这个玫红框——这条不能过度解读。omp@can.ac 和 me@can.ac 是同一个域名、同一个人，git 元数据分不出来哪些是「bot 自主提交并被合并」，哪些是「人用 omp 辅助写完之后署名给了 bot」。所以我能讲的是：2,564 个 commit 署名给了项目自己的 bot 账号；我不能讲：「这些代码是 AI 独立写成的」。这两句话差别很大，请大家引用的时候也用前一句。

P12 · abort 不是一个布尔，是四条信号

提词
  • 四个盒子从左到右，权限递减 [重]
  • 外部 signal 杀一切；steering/IRC 只杀 interruptible
  • 其余工具只收外部 signal —— 这是核心 [慢]
  • 一句话规则：不硬杀已产生副作用的前台工具
  • 第五条不叫 abort：PauseGate，冻结不中止
  • 恢复两层：协议层 vs 策略层
  • TurnRecovery 1,787 行；pi 侧「未见」不是「删了」
  • 右栏 13 行是全场最能抄的一段 [停]
  • 右栏是「照原码语义整理」，不是逐字原文
一句话主旨

abort 被拆成四条独立信号加一道暂停闸门，规则只有一句——排队的用户插话永不硬杀一个已经产生副作用的前台工具；错误恢复则分成协议层和策略层两层。

怎么讲

这一页在我看来是 omp 内核里最精细的一块，也是最能看出"这些代码是被真实事故打磨过的"一页。（停一拍）先看最上面这四个盒子，从左到右权限递减。

第一个玫红的，外部 signal——调用方给的 abort，比如你按 Ctrl+C。这条硬杀一切，谁都拦不住。第二个青色的，steering——用户插话。第三个橙色的，IRC——别的 agent 发来的消息。这两条通过 AbortSignal.any 合成一条 interruptibleSignal。第四个绿色的，协作式软信号，通过 ctx.toolCall.steeringSignal 发给每一个工具，它不中止任何东西，只是通知："有人在等你，你要不要让个路。"比如 bash 收到这个信号可以自动把自己转到后台去跑。

那这四条怎么分派？看中间这个玫红框，规则就两行。工具如果声明了 interruptible: true——这类工具是纯等待型的，比如 hub wait、vibe，它们除了耗时间什么也不做——那它收 interruptibleSignal，可以被 steering 和 IRC 硬杀，因为杀了没有任何损失。其余所有工具，比如 bash，只收外部 signal。

这一句就是本页的心脏，我用大白话再说一遍：你在 agent 跑到一半的时候插一句话，它不会去杀那个正在跑的 bash。为什么？因为 bash 可能已经改了文件、已经发了网络请求、已经产生了副作用。杀掉它，副作用还在，但结果丢了——你的上下文里从此有一个谎：一条 "skipped"，实际上它跑了。代码注释里直接引用了 issue #4752，就是这么被打出来的。所以后面那半句也很重要：工具跑完了就保留真实结果，不因为 abort 落地而伪造成 skipped。

底下这个绿框是第五条，但它刻意不叫 abort，叫 AgentPauseGate——冻结，不中止。它只在两个动作边界上轮询：模型调用之前、每个工具启动之前。已经在飞的流、已经启动的工具，跑完再停。这个区分很重要：abort 是"别做了"，pause 是"做完这件别接下一件"。

（停一拍）下半页换话题，讲错误恢复，这里的看点是分层。左边绿框是第一层，在循环内，我叫它协议层，管的是"这一次 HTTP 流本身坏了"。四个例子：GPT-5 的 Harmony 协议泄漏，能救就截断续跑，上限两次，不能救就丢掉半截重新采样，还失败就抛；流中断时有半截 toolCall，只保留 toolcall_end 已经到达的那些；瞬时流错误但工具调用其实是完整的，那就把 stopReason 从 error 改写成 toolUse，让这轮工具照跑；最后是批次尾扫，谁没产出结果就补一个 skipped，保证 tool_use 和 tool_result 严格配对——这个配对不严格，下一次请求就直接 400。对照 pi，pi 这一层只有一个函数，处理 length 截断。

右边紫框是第二层，在会话层，TurnRecovery，1,787 行，管的是"这个模型不行，换一个再来"。模型 fallback 链、空回复重试三次、非预期停止三次配四秒超时还带一个分类器、限流退避、"思考循环"重定向、重试成功之后还回头把历史里那条错误消息标成已恢复。注意底下这行灰字的措辞——本次对比基准下，pi 侧未见对应实现。跟上一页一样的谨慎，理由一样，不重复了。

分层的好处写在这行：循环内不必知道有几个模型可切，会话层不必懂 Harmony 协议是什么。这是个很干净的切法，我觉得比那 1,787 行本身更值钱。

还有一个小机关值得说：终结信号也复用了 abort。子代理调 yield 提交结果之后，会话层调 agent.abort(TERMINAL_TOOL_RESULT_ABORT_REASON)，主循环认出这个特定的 reason 就把 hasMoreToolCalls 置成 false。等于用一个 Symbol 当带内信令——既停住了循环，又不污染用户的 abort 语义。

（停一拍）好，现在看右半页，这是全场我最建议你直接抄走的一段。先说清楚一件事：这里显示的十三行，是我照原码语义整理过的，省掉了 telemetry 和错误包装，不是逐字的原文——原文在 agent-loop.ts:2660-2686，回头你自己去看。

它解决什么问题？我们先说 pi 是怎么做的：pi 有个全局配置 toolExecution，只有两个值，sequential 或者 parallel。而且更狠的是——只要这一批里有任何一个工具声明了 sequential，整批全部串行。你想想这个后果：模型一口气发了五个 read 和一个 write，read 之间完全可以并行，但因为 write 要串行，五个 read 也全被拖成串行。

omp 的做法是让每个工具自己声明，看上面这两行类型：concurrency 是 "shared" | "exclusive"，还可以是一个函数——按调用参数动态决定。比如同一个 bash 工具，跑 ls 是 shared，跑 rm 是 exclusive。interruptible 也一样能动态决定。

调度器就是这十三行，一条手写的屏障链。逻辑只有一句：exclusive 的工具要等前面所有人跑完，shared 的工具只等上一个 exclusive。我照着代码念一遍：来一个工具，先看它是不是 exclusive；是的话，start 等于 Promise.all([lastExclusive, ...sharedTasks])——等上一个 exclusive 加上它之后所有的 shared；不是的话，start 只等 lastExclusive。然后 start.then 挂上真正的执行。如果是 exclusive，就把自己记成新的 lastExclusive，并且把 sharedTasks 清空——因为后面来的 shared 只需要等我，不需要等我之前那些。

翻译成一句人话：写文件的工具声明 exclusive，只读的工具声明 shared，同一批工具调用就能既并发、又不互相打架。exclusive 在这里的角色就是批次内的写屏障。十三行，零依赖，不需要任何调度框架，你今天写的那个小 agent 就能用上。这是我这次读整个 omp 最想推荐的一段代码——不是因为它复杂，恰恰因为它简单到你没有理由不抄。

第二则，swarm-extension。左边望文生义版本：YAML 声明一张 DAG 就能编排多 agent，模型自己能触发，失败会重试，中断了还能续跑。（停一拍）右边逐条来。DAG 是真的——Kahn 算法环检测、wave 分层，dag.ts 里写得挺正经，整个包 1,795 行。但接下来四条：并发上限——没有。wave 内部是 Promise.all 全并行，无界；50 个节点就是 50 个并发子会话。而且宿主那个 task.maxConcurrency（默认 32）救不了它，因为那个信号量只在 task 工具的 spawn 路径上 acquire，swarm 是直接调 runSubprocess，绕过去了。重试——零。pipeline、executor、dag 三个文件里没有任何 retry 或 backoff。节点失败也不剪枝下游：per-agent 的 try/catch 把异常转成 exitCode: 1 的合成结果，wave 是启动前一次性算好的，之后不重算，所以依赖全挂的节点照样执行，只是磁盘上没有它要的输入。节点间零数据传递——没有变量插值、没有模板、没有结果回填。那个叫 reports_to 的字段，名字看起来像数据流，实际只是一条排序边。README 自己写得很直白："It does not pass data between them. 它不是把历史画成信息图，是用点阵字体把历史印成 PNG，让 vision 模型 OCR 读回——排版印刷，不是可视化。

怎么讲

先看左上角红框，我把常见讲法原样念一遍："把丢弃的历史画成点阵图"。这句话里"点阵"两个字是对的，"画成图"是误导的。（停一拍）我得先认个错——上一讲这一页就是我这么讲的。第 3 页那三条更正里的第二条就是它。为什么这个措辞会误导？因为你听到"画成点阵图"，脑子里浮出来的是热力图、散点、色块矩阵，是信息可视化——好像它把一段对话抽象成了某种视觉编码。不是的。看右上角紫框：实际做的事是把历史用点阵字体印成缩微胶片。PNG 上就是一行行逐格印出来的、你我肉眼也能读的文字。模型读回的时候做的是 OCR，不是读图表。所以正确的比喻是排版印刷，不是数据可视化。（停一拍）为什么我要为这三个字较真？因为它直接决定了后面两页怎么算账——如果是可视化，那"压缩率"就是个信息论问题；既然是印刷，压缩率就变成了一个很土的问题：一张图能印多少字符、这张图按多少 token 计费。这就是下一页那张表的全部内容。

往下看这四步流水线，我快速过。① 序列化加归一化：把要丢弃的消息压成 ¶user ¶think ¶ai ¶call 四种前缀的紧凑文本，然后剥掉 ANSI 颜色码、折叠空白，换行折成一个实心方块 █——注意这一步已经是有损的，工具结果每条封顶 2000 字符，而且是掐头留尾，注释说理由是"报错和测试失败通常落在尾部"。② 排版，这一步最值得看，叫中央凹布局，foveation，就是人眼视网膜中央清晰、周边模糊那个词：时间轴的两端——会话最开头和最近这一段——保留纯文本，因为这两块要能被精确检索；中段才成像；中段的中段再降质，超预算就从最老的那一端整段丢。③ 光栅化，这一步在 Rust 里，一千七百多行，用的是真实的点阵字体文件——X.org misc 的 5x8、6x12、8x13，unscii 的 8x8，还有个 TrueType 兜底字体叫 Silver。这些是字体文件，不是他们自己画的像素。④ 模型读回，前置条件写在这儿：模型的 input 必须包含 image，不支持图片的模型直接降级回 LLM 摘要。而这一步是 OCR，所以"读不读得出来"就变成了一个可以打分的指标——下下页整页都在讲它怎么塌的。底下这个紫框是名字的由来：snapcompact 约等于 microfiche，缩微胶片；注释原话是 "like an archivist at a snapcompact frame reader"，作者自己就把这套东西比作档案管理员在阅读器上翻胶片。名字已经把意图说完了，是我们上一讲没读到位。

（停一拍）现在看右边这一栏，这是本页第二个要纠的说法，而且是我更在意的一个。红框："零 LLM 调用 = 零成本"。第一句"零 LLM 调用"我上一讲也说了，它准确，但少了一个限定词，少了这个词就会把人带沟里。紫框给限定词：是零额外调用。压缩这一步确实完全本地完成——Rust 光栅化，不要 API key、不走网络、没有推理延迟、结果可复现，这几条都是真的，含金量也很高。但是——看下面这三个盒子：轮 T 压缩发生，额外 LLM 调用 0 次；轮 T+1，这 N 帧图要重新附上去，按 vision token 计费；轮 T+2，再附一次，再计一次费，一直到下次压缩重排为止。所以省的是一次推理、一次不确定性、一次幻觉机会，不是 token。token 该花还得花，而且是每轮都花。正因为如此，帧数必须被夹住，看这个琥珀框：MAX_FRAMES_DEFAULT 是 80，注释说这个数是按"装下大约 400k token"选的；但真正生效的是下面这条——FRAME_DATA_BYTES_BUDGET 3 MB，把上限实际压到了 17 帧。理由写得特别实在，我念原话的意思：一个 100 万 token 的模型纸面上放得下 70 张图，但放不下每轮 11 MB 的 JSON payload。这是一句非常工程的话——约束不在 token 数上，在 HTTP body 上。另外还有一条我觉得挺有意思：未知 provider 的图片张数预算只有 5 张，也就是它对没见过的服务商是极度保守的。最后念一下绿框，这是我给自己定的口径，也建议大家这么念：说"压缩这一步零额外 LLM 调用"是对的；说"这套方案零成本"是错的。

P16 · 压缩率不是重点，确定性才是

提词
  • 先念常见讲法：变成图就省 token，一图胜千言
  • 实情：省不省完全取决于 provider 的图片计费模型 [重]
  • 表从上往下念：Gemini 21.26（×5.3）→ Kimi 6.66 → GPT 4.83 → Claude 4.20（×1.05）→ 纯文本 4.00
  • Gemini 为什么白嫖：每图恒定 1120 token，与像素无关
  • Anthropic 走 (size/28)² × 1.05，放大就加钱
  • ⚠ 这张表是按代码公式手算的，不是实测 [重][慢]
  • 右栏对照表，重点只在第 4 行：上下文已经爆了 → 摘要不可用 / snapcompact 可用
  • 鸡生蛋：摘要请求要复用已经溢出的上下文
  • 卖点是确定性，不是压缩率 [停]
  • 代价三条：绑死 vision / MB 级 base64 伤缓存 / 降级成 OCR 可读性
一句话主旨

Claude 上 4.2 vs 纯文本 4.0 chars/token，几乎打平；真正的卖点是"上下文已经爆了、摘要式压缩恰好失效"的那一刻它还能跑。

怎么讲

上一页说了，既然是印刷，那就该算账。这一页是本章、可能也是本场最反直觉的一页，所以我讲慢一点。（停一拍）还是先念左上角的常见讲法："把文本变成图，token 立刻省下来"，理由通常是那句"一张图胜过千言万语"——图肯定比文本便宜。右边紫框，实情：省不省，完全取决于 provider 的图片怎么计费。不是取决于这个算法有多聪明，是取决于人家的价目表。

看这几根条。我从上往下念，右边这一列是 chars/token，就是"一个 token 能装多少个字符"，越大越省。Gemini 3.x，21.26，对比纯文本基线是 5.3 倍，这根条最长，是唯一一个吃到大红利的。往下 Kimi 和 GLM，6.66，1.67 倍，还行。GPT / Codex，4.83，1.21 倍，聊胜于无。然后是这一根——Claude Opus 4.7 以上，4.20。最底下这根虚线框是纯文本基线，4.00。（停一拍）4.20 比 4.00，×1.05。也就是说，在 Claude 上，你把整段历史印成图，省下来的 token 是 5%。基本等于没省。这个数第一次算出来的时候我以为自己算错了，回去把公式又对了一遍。

为什么会这样？看这个紫框，答案很简单，简单到有点好笑：familyBilling() 这个函数的 google 分支，frameTokenEstimate 是恒定的 1120，与像素无关。一张图 1120 token，不管你这张图是 512 还是 2048。那作者当然就把 Gemini 那条线的帧放大到 2048px——这是纯白嫖，代码注释里就是这个意思。而 Anthropic 这条线走的是 ceil((size/28)²) × 1.05，是随面积走的，你把图放大，token 就等比涨上去，怎么调都在原地。所以这不是算法差距，是计费模型差距。

（停一拍）现在讲这一页我最需要说出口的一件事，看底下这个琥珀色的框：这张 chars/token 表是我按代码公式手算的，不是实测。依据两处：几何在 geometry()，计费在 familyBilling()，两个函数的行号都在框里；基线那个 4.0 chars/token 也不是我拍的，是仓库自己注释里的换算口径——它自己的 token 计数器默认就是 bytes/4，所以我用 4.0 做基线，和它自己的会计口径是一致的。但我必须说清楚局限：本机没有 bun，仓库的测试和 research/ 下那 80 个 eval 脚本我一个都没跑，那些脚本要真实 API key，结果目录也没入库。如果真实 transcript 更密——里面全是 JSON 和代码，实际可能落在 3.5——那所有比值会上浮 5% 到 25%。方向不会变，Claude 那一行还是打平，但精确到小数点第二位你别信我。

那省不下 token，它到底换来了什么？看右边这张对照表。额外 LLM 调用，摘要 1 次，它 0 次；确定性，摘要每次都不一样，它是纯函数；幻觉风险，摘要有，它没有，因为原文逐字保留只是换了个载体。这三行都好，但都不是决定性的。真正的卖点在第 4 行，我把它标成紫色了："上下文已经爆了"——LLM 摘要在这一格是不可用，snapcompact 是可用。为什么摘要不可用？看这个紫框：摘要式压缩要先发一次请求让模型写摘要，可那次请求本身要复用已经溢出的上下文。上下文都爆了，你还怎么发这个请求？这是个鸡生蛋。docs 里写得很直白，handoff 策略不用于 overflow 场景，理由就是这个。而 snapcompact 在那一刻依然能跑，因为它根本不需要模型。（停一拍）所以这一页的标题才叫"压缩率不是重点，确定性才是"。这套方案的价值不是"更省"，是"在别的方案失效的那一刻它还在"。这是两种完全不同的价值——一个是效率，一个是兜底能力。工程上后者往往更贵。

代价我也得对称地念完，看红框：① 绑死 vision 模型，纯文本模型自动降级回摘要；② 每轮重附 MB 级 base64，前缀缓存吃亏——这条挺疼的，因为现在大家都靠 prompt caching 省钱；③ 信息不是被压缩了，是被降级成了 OCR 可读性，f1 在 .287 到 .973 之间剧烈波动，下一页整页讲这个。最后一句看页脚小字：omp 并没有二选一，context-full——也就是 LLM 摘要——完整保留为 fallback，非 vision 模型自动切回去。是互补，不是替代。

  • 第 4 行"上下文已经爆了"要专门停一下，这是全页唯一必须被记住的东西。前三行都是铺垫。
  • 代价三条要念完，不能只夸。特别是"伤前缀缓存"这条，对成本敏感的团队这条可能比 token 本身更重要。

P17 · 他们主动把压缩率降了一个量级，换可读性

提词
  • 先念常见直觉：压缩率当然越高越好，字印得越小越省
  • 实情：压得太狠，模型不是读错，是直接摆烂 [重]
  • 左卡旧线 5x8-sent@2576：165,830 字符/帧，33.0 chars/token，f1 .351
  • 右卡当前 11on16-bw@1568：13,916 字符/帧，4.23 chars/token，f1 .806
  • 两个口径别混：字符/帧 11.9×；chars/token 7.8× [慢]
  • 失败机理：低于 OCR ~16px/char 下限 → abstained，模型拒答
  • 不是缓慢劣化，是过线断崖 —— 调参找的是那条线在哪 [停]
  • ⚠ f1 来自代码注释，不是本次实测
  • 右栏才是重点：eval 写进代码注释，和参数住在一起
  • 对照我们自己：参数在代码里，结果在某人 notebook 里
  • 能搬走的一条：魔数旁写清对照组 / 指标 / 时间
一句话主旨

作者主动放弃了近一个量级的压缩率去换 OCR 可读性；而更值钱的是元层面的那件事——eval 数字被写进代码注释，和它决定的参数住在一起。

怎么讲

上一页最后我说他们试过更狠的，这一页就是那次的记录。（停一拍）先念左上角的常见直觉——注意这次我写的是"直觉"不是"讲法"，因为这条基本没人会质疑："压缩率当然是越高越好，字印得越小，一帧塞得越多，越省钱。" 听起来天经地义。右边实情：压得太狠，模型不是读错，是直接摆烂。 于是他们主动把压缩率砍掉了将近一个量级，换回可读性。

看这两张对照卡。左边红卡是已废弃的老方案，shape 叫 5x8-sent，帧尺寸 2576px。它有多猛？每帧 165,830 个字符——十六万五千字，一张图。换算成 chars/token 是 33.0，是纯文本的 8.3 倍。这是一个非常漂亮的压缩率。然后看底下这个数：在 opus-4.8 的工具输出 benchmark 上，f1 只有 .351。右边紫卡是当前默认，11on16-bw，1568px：每帧 13,916 字符，chars/token 4.23，也就是上一页那个"几乎不省"的数。f1 .806。同一个 benchmark，同一个模型。

（停一拍）这里我要特别小心地说一件事，因为很容易讲混：这里有两个口径，别混着讲。 按字符/帧看，从 165,830 掉到 13,916，是掉了 11.9 倍；按 chars/token 看，从 33.0 掉到 4.23，是掉了 7.8 倍。这两个数不一样，因为两条线的帧尺寸不同，计费也不同。页面上这个"净换算"框我写的是 压缩率 ÷ 7.8，f1 × 2.3，用的是 chars/token 这个口径，因为它才是真正的"省不省钱"。要是你想说"每帧塞的字少了多少"，那是 11.9 倍。标题写"降了一个量级"是取了个不刺激的说法，你们照哪个口径讲都行，但别在同一句话里混着用。

失败机理写在注释里，而且非常具体，看这个紫框："fell below the OCR ~16px/char floor and abstained"。翻译过来是：字号掉到了 OCR 大约每字符 16 像素这条下限以下，然后模型 abstained——弃权。（停一拍）这个词很关键。字太小的时候，模型不是读岔了、认错字了，它是判断自己读不了，然后拒绝回答。所以这条曲线不是缓慢劣化，是过了门槛就断崖。这对调参的含义完全不同：你要找的不是一个最优点，你要找的是那条线在哪儿，然后站在线的安全一侧留出余量。旁边那行小字给了同批的对照组：8on16-bw 是 .755，还不错；而 Gemini 那条线上 doc-8on16-sent-dim 只有 .287——换个模型，同一个现象再现一次，说明这不是 Claude 特有的脾气。

一句话主旨

真正的约束是"你只能改你亲眼看过的行"；4-hex 指纹只有 16 bit、必然碰撞，作者自己说它只是索引，不是身份。

怎么讲

最后一页，换一件事讲：文件编辑的安全。（停一拍）老规矩，先念左上角常见讲法："靠 4 位内容指纹防止改错文件"——读文件的时候给它一个 tag，编辑的时候带上 tag，对不上就拒改。上一讲我就是这么讲的，这是本讲第二次、也是最后一次认错。这个说法不算错，但它把重点说反了。右边实情：指纹只是索引，真防线是 seenLines。而且这句话要说得更狠一点——哪怕指纹对得上，你没看过的行照样改不了。

跟着这张流程图走一遍。最上面：一个 edit 请求进来，带着 [src/foo.ts#1A2B] 这样一个 section header，1A2B 就是那 4 位 hex。第一个分叉：全文 hash 对不对得上。先走左边这条顺路——对上了，文件没变。按常见讲法，到这儿就该放行了对吧？不放。 看这个紫框，还有一道闸门：锚点行，是不是每一行都在 seenLines 里？ seenLines 是什么？是 read 和 search 实际显示给模型看过的行号集合，1-indexed。注意这里有个细节：范围读、折叠式的结构摘要，只会填一个稀疏集合——你 read 了 100 到 120 行，那 seenLines 里就只有这 21 个数，别的行你没见过。过了这道闸门才 applyEdits；有没看过的行，直接拒绝，而且把那些行的真实内容贴回去给模型。

它防的是什么？看右下角这个框，注释原话："editing lines the model has not seen is the off-by-memory mistake that mangles files"——模型凭记忆去改它没看过的行，这是把文件搅烂的那类错误。这句话我觉得说得特别准。模型对一个文件"大概长什么样"是有先验的，它见过一万个类似的文件，所以它很敢下手。seenLines 干的事就是把这个先验掐掉：你这一次看到了什么，你才能改什么。

再走右边这条路，hash 对不上，文件漂移了。这里是个三级台阶，不是一刀切拒绝。① 先问：这次编辑是不是只在头部或尾部插入？如果是，那它没有锚点作用域，插在哪儿都不会改错地方，带个警告放行——这是个很务实的口子。② 不是的话进 Recovery，三方重映射：拿旧文本和新文本做 diff，只收录未改动的行段建映射表，锚点必须落在这些未改动的行上，锚点上下相邻的非锚点行也必须同步位移；然后是这条铁律——所有锚点必须是同一个偏移量，否则整个放弃。文件头写的原则叫 fails closed：只要目标变了或者变得有歧义，就失败，宁可不修。③ 还不行才抛 MismatchError。这里有个细节我很喜欢：报错文案分两种，别混。如果这个 tag 根本不是本会话产生的——查快照库查不到——报错是"你把 tag 编出来了，或者用了上一次会话的 tag，永远不要发明 tag"；如果 tag 认识但文件变了，报错是"文件在你读完之后被改了，去抄上一次响应里的新 header，或者重读"。这是两个完全不同的失败模式，给模型两句完全不同的话。 这个区分很值钱——大部分工具报错只有一句"hash mismatch"，模型看了不知道该干嘛。

（停一拍）现在看右边这一栏，回答那个最容易被问的问题：为什么敢只用 16 bit？ 上面这个代码框：先归一化——每行去掉尾部空白、吃掉 CR，这样 CRLF 和显示时被裁掉的尾空白不会让 tag 失效；然后 xxHash32 取低 16 位，输出 4 个大写 hex。取值空间只有 65,536。这个空间小到什么程度？一个会话里读几十上百个文件版本，撞上的概率是完全不能忽略的。所以看下面这个框：会碰撞，但无所谓。 因为 tag 只负责一件事——快速认出"这次读的是哪一版"；认出来之后，真正拿去比对的是快照里逐字保存的全文。注释原话："the tag is only a fast index, never the identity"。回到左边这个紫框验证一下：SnapshotStore 的去重条件写死成 v.hash === hash && v.text === fullText——hash 相等还不够，全文也得相等才算同一版。注释还点名了 issue #4075：如果只按 tag 合并，两段不同的内容撞了同一个 tag，就会把 B 的 seenLines 挂到 A 的文本上，patcher 从此开始误判。这是个真实踩过的坑。

最后这个红框是我最想让大家记住的一个设计细节，防绕过。刚才说拒绝的时候会把没看过的行的真实内容贴回去，让模型一次就能自纠——这很贴心。但这里藏着一个漏洞：如果贴回去的行自动就算"看过了"，那模型只要反复触发拒绝，就能一点点把整个文件"看"完，盲改照样塞进去。所以上限卡死：一次最多揭示 40 行、每行最多 512 列。而且——只有当揭示是完整覆盖的时候，这些行才并入 seenLines；一旦碰到上限被截断，就一行都不并入。一行都不。为什么？因为如果截断了还并入一部分，模型就可以把请求切成 40 行以下的小块反复重试，把盲改硬塞进去。（停一拍）我觉得这个细节能说明作者是真的在跟模型的行为对抗，而不是在写一个理想化的校验器。他假设了模型会尝试绕过——不是恶意，是模型天然会"再试一次换个写法"。

收尾看绿框这一句，这也是整章的收尾：指纹回答"是不是同一份"，seenLines 回答"你有没有资格改"。 这两个问题不是一个问题。而这，就是我在章扉页说的那句话——这一章的两个设计都不聪明，只是把"模型可能骗你"写成了代码约束。snapcompact 不信模型的摘要，hashline 不信模型的记忆。都不是什么高级算法，就是在关键位置上装了一道不讲情面的闸门。

  • "哪怕指纹对得上，没看过的行照样改不了"这句要说出口——这一句就把常见讲法和实情的差别讲完了。

P20 · 靠猜必错：543 个同名模型里，376 个价格对不上

提词

  • 543 个同名 → 376 个价格不一致（69%）、254 个窗口不一致（47%）[重]

同一个模型名在不同网关下价格、窗口、id 全都不一样，靠猜必然错，所以模型元数据得当成软件制品来造。

怎么讲

P21 · dialect 兜的不是语法，是 native 通道不会出现的失败模式

提词
  • 11 种方言，显式 PI_DIALECT opt-in，不设就走 native [重]
  • 这一页的钥匙：native 通道里根本不存在的三种失败模式
  • A 伪造工具结果：登记「结果开启 token」，撞见即 abort 上游止损
  • B GLM 把 </arg_value> 写成 </arg_key> → 吞掉后续全部参数
  • B 难在流式：三态 none / partial / heal，partial 要 hold 住
  • C 双通道抢答：Gemini via OpenRouter，tools 空了照样吐 functionCall
  • C 对策：先出真调用的通道锁死，另一条整轮丢弃 [慢]
  • 右边：opt-in 之后请求侧三件事一起做
  • 对比锚点：pi 的 packages/ai grep dialect 零命中
  • 它不是「更好的 tool calling」，是兜底通道 [停]
  • 被删的 pi 自研方言曾宣称省 46% token——没留住
一句话主旨

把工具调用从结构化字段挪进正文，你就得自己收拾三种 native 通道里根本不存在的烂摊子。

怎么讲

上一页讲数据，这一页讲协议。（停一拍）先把定位说清楚，看标题下这行小字：11 种方言，显式 PI_DIALECT opt-in，你不设它就走 native。所以它不是默认路径，是一条备用车道。什么时候走这条道？三种情况：上游根本不支持 function calling，比如你自己跑的 llama.cpp、vLLM，或者某些便宜网关；上游说支持但解析做坏了；或者你就是想把 tool 描述的裁剪、示例的渲染、token 预算全部拿回自己手里。仓库自己在 TUI 的 tips 里有一句大白话："没有 native tool calling？推理服务把解析搞砸了？PI_DIALECT=glm|kimi|anthropic 帮你在本地滚一遍。"（停一拍）现在，这一页真正的钥匙在最上面那行小字，我念一遍：这三种失败模式，native 通道里根本不存在。大多数人讲 in-band tool calling，讲的是"用 XML 还是 JSON、哪种更省 token"——那是语法问题。这一页说的是：当你把工具调用从结构化字段挪进正文，你就把一整类新的失败模式请进了门，而这三种失败模式，恰恰是 native 通道白送给你的保护。我们一个一个看。

A，模型伪造工具执行结果，英文叫 fabrication。在 native 通道里这事不可能发生，因为工具的返回值是 runtime 注入进对话的，模型压根没有机会编。但在 in-band 通道里，模型吐完调用之后手一滑，把"工具返回了什么"也一起编出来了——它编了一段 <tool_response> 里面写着"测试全部通过"，然后基于这个幻觉继续往下推理。你不管它，它能编一整篇。omp 的对策看这行：每种方言登记一组"工具结果开启 token"，下面这排就是——glm 是 <tool_response>，kimi 是 <|im_system|>，anthropic 是 <function_results>，gemini 是 `tool_outputs ，deepseek 是那个全角的 <｜tool▁outputs▁begin｜>。流式扫描器一旦在文本里撞见这些 token，立刻停。而且有两种模式：默认的 abort 模式直接掐断上游请求，注释原话是"so the provider stops spending tokens on the hallucinated continuation"——这是一条止损，不是一条正确性措施。你已经知道这轮废了，那就别再为幻觉付钱了。另一种 discard 模式是把流排干但丢弃边界之后的一切。还有一个细节值得一提：这些 token 可能被 SSE 的 chunk 边界切成两半，所以扫描器保留了一个重叠窗口，避免漏检。

B，GLM 把 </arg_value> 写成 </arg_key>。这个更具体。native 通道里参数的闭合是结构化字段保证的，压根不存在"标签写错"这回事。in-band 里，模型一个字符打错，后果是什么？看这句——后续所有参数被吞进同一个字段，一直吞到流里下一个 </arg_value> 为止。也就是说你以为你拿到了五个参数，实际上你拿到一个巨大的字符串，里面塞着另外四个。对策是流式的"愈合扫描"：识别两种修复签名，一种是闭错了（</arg_key> 后面紧跟着 <arg_key> 或者 </tool_call>），一种是压根忘了闭。（停一拍）真正难的地方在下面这行：难在流式。签名可能只写到一半，chunk 就断了——你看到一个 </arg_k，你不知道它是要闭错还是正常的 key 结束。所以这个函数返回三态：none、partial、heal。partial 的时候调用方必须 hold 住这一段，不能往下游 emit，等下一个 chunk 来了再判。这三态设计是整页最见功力的一处。另外还有防误伤的边界：标签之间最多容忍 32 个空白，key 最长 128 字符，超了就放弃愈合——因为你不能为了修 bug 把用户正常的文本改坏。他们甚至专门写了一条反向保护测试，叫 "leaves values containing tag-like prose intact"，就是说参数值里本来就写着像标签的散文时，不许动它。

C，native 和 in-band 双通道同时开火。这条最荒诞。omp 已经把请求里的 tools 字段置成 undefined 了，按理说上游不可能返回 native 的工具调用。但注释里点名了一个真实案例：Gemini 经由 OpenRouter，即使你没发 tools，它照样返回 functionCall parts。那你转发不转发？不转发，这一轮就没有任何可执行的内容，agent loop 拿到一条只有 reasoning 的消息，会无限重试下去。对策是：哪条通道先产出"真"调用，就锁死哪条，另一条整轮全部丢弃。还要处理"ghost"——一个没有 name 的空 native 块不算数，不锁通道。测试名字就叫 "drops a nameless native ghost but keeps the real native call"。（停一拍）

右边这一栏收尾。上面是 11 种方言的清单：anthropic、glm、gemini、gemma、kimi、qwen3、deepseek、minimax、harmony 对 gpt-oss、hermes 需要显式指定、最后 xml 是 FALLBACK，遇到不认识的模型就用它。中间这格讲 opt-in 之后请求侧要三件事一起做：系统提示里追加工具清单加方言语法说明、历史里的调用和结果按方言回写成文本、然后 tools 置 undefined、toolChoice 清空、描述裁剪关掉。少做一件就会前后不一致。再往下是对比锚点：pi 完全信任 native tool calling，它的 packages/ai 里 grep dialect 和 inband，零命中。这条柱子对比是 21,429 行对 99,265 行——四倍多，dialect 只是其中一块。最后这个琥珀框是这一页的落点，我照念：它不是"更好的 tool calling"，而是"上游把 native tool calling 做坏了"时的兜底通道，所以它必须处理 native 通道里不会出现的失败模式。 底下还有一行很有意思的脚注：pi 曾经有一套自研方言，宣称比 legacy 格式省 46% 的 token，最后被删掉了。省 token 没能留住它——我的理解是，模型没见过你自研的格式，你省的那点 token 换来的是更高的出错率。这条因果是我的推断，不是仓库明说的。

别漏了说
  • 开场必须先说"显式 opt-in，不设就走 native"，否则听众会以为 omp 默认不用 native tool calling，那是完全错误的印象。
  • "native 通道里根本不存在"这句话在三个失败模式里各说一遍，这是本页的结构，不能省。
  • fabrication 的 abort 是止损不是纠错——这个区分要说出来，否则听众会问"掐断了不就丢了这轮吗"。答案是这轮本来就已经废了。
  • B 的"三态 + partial 要 hold"是整页技术含量最高的一处，别赶时间跳过。
  • 46% token 那条要明确标为推断，不要说成仓库结论。
  • 如果时间紧，C 可以压到 30 秒，A 和 B 不能压。
可能被问
  • Q：那我到底该不该用 in-band？
  • A：默认不该。这一页的完整读法是"能用 native 就用 native"，dialect 是当你没得选的时候的逃生舱。omp 自己也是这么设计的——你得显式设环境变量它才走。
  • Q：伪造工具结果这事，native 通道真的完全不会发生吗？
  • A：结果注入这条路上不会。但模型在自己的文本里"假装"某个工具跑过了、编造一段输出当叙述，这在任何通道里都可能发生。这一页说的是结构化的伪造——模型吐出一个语法上合法的结果块，被你的解析器当真。这个只在 in-band 里有。
  • Q：11 种方言要维护，成本不高吗？
  • A：高。而且这个数字是会变的——旧的 pi 方言被删了，minimax 是新加的。这就是"兜底通道"的代价：上游每出一个新脾气你就得加一条。所以我才强调它是 opt-in 而不是主路。
  • Q：GLM 那个 bug 现在修了吗？
  • A：不知道。仓库的 CHANGELOG 记录说这个症状"in-band 和 native 都中招"，说明问题出在网关那一层而不只是 in-band。修没修我没验证。
  • Q：愈合扫描会不会把用户本来就想传的 </arg_key> 改掉？
  • A：这正是那条反向保护测试在防的事，加上 32 空白 / 128 字符两条边界。但严格说，任何启发式愈合都存在误伤的可能，他们的做法是把误伤面缩到最小，不是消除。

P22 · 第 05 章 · Rust 热路径

提词
  • 三十秒过
  • 章问题：纯 TS 的 agent 为什么自研 9 个 Rust crate
  • 答案预告：不是 Rust 更快，是边界换了 [重]
  • 收益和代价来自同一处边界的消失 [慢]
  • 三页：69% 不是 shell / 一行 assert / 最诚实的 benchmark
  • 84,448 行自研，vendored 的 10 万行不算
  • 只占全仓 TS 的 6.7% —— 不是重写 agent，是换掉最脏的 6% [停]
一句话主旨

P24 · 一行 assert 讲清整件事

提词

  • 它防的是：builtin 按进程全局 cwd 解析相对路径 → 目录落到宿主当前目录
  • 同一句话可以换成 fd 或信号再说两遍 [重]
  • ① fd 表：函数没法 dup2(1)，重定向拿不到 → 从 brush 取真 fd 装进 thread-local，一次调用一条线程
  • ② cwd：全 crate set_current_dir 命中数为 0；cwd 挂在 shell 实例上，路径参数逐个过 resolve
  • ③ 信号：你没法给函数发 SIGKILL → 原子标志位 + 合成 EOF + 200ms 分片 poll

一句话主旨

进程边界一消失，POSIX 白送的 fd 表、cwd、信号三样保证同时失效，446 行 pi-uutils-ctx 就是补这三个洞的全部代码。

怎么讲

这一页我只有一个论点，而且它可以被一行代码讲完。（停一拍）看左上角这个框，这是回归测试里的一行，位置是 crates/pi-shell/src/shell.rs 第 2598 行。上面一行注释我先说：mkdir 走的是进程内 builtin，不是子进程。然后跑一条命令 mkdir -p a/b/c，工作目录指定成一个临时目录。接着是这个断言——assert! 括号里是 !Path::new("a/b/c").exists()，注意那个感叹号，它断言的是"不存在"。失败信息写着："mkdir leaked into process cwd"——mkdir 泄漏到进程的当前目录去了。（停一拍）这一行在防什么？看下面这句：如果 builtin 按进程全局的 cwd 去解析相对路径，那 a/b/c 这个目录就不会落在你指定的临时目录里，而会落在宿主进程的当前目录下——也就是用户正在工作的那个仓库根目录。你让 agent 在一个隔离目录里建目录，结果它在你的项目根目录里拉了一坨。而且这不是 bug，这是子进程模型给你白送的东西，在你换成函数调用的那一刻，静悄悄地不见了。 下面这行是我最想让大家记住的：同一句话，可以换成 fd 说一遍，换成信号再说一遍——进程边界一没，三样保证一起没。

（停一拍）中间这三格就是那三样。第一样，fd 表。子进程模型里，重定向是怎么实现的？父进程 dup2 一下，子进程什么都不用管，它写 fd 1 就自动进了文件。函数调用没法 dup2，你写 println! 它就是往进程的 stdout 去了，重定向根本拿不到。omp 的做法：在任何 await 之前，从 brush 的执行上下文里把这条命令真正的 fd 取出来，装进 thread-local；而且一次调用配一条专属线程，这是刻意的——因为管道的并发各段不能互相串流。第二样，cwd。全进程只有一个当前目录，但一个 agent 可以同时开很多个 shell 会话。这里有一个数字我很喜欢：整个 crate 里 set_current_dir 的命中数是 0——它从来不改进程的 cwd。cwd 挂在每个 shell 实例上，然后每一个路径参数都逐个过一遍 ctx::resolve。注意这句话的含义：vendored 进来的那 44 个 uutils 工具是被打了补丁的，每次碰文件系统之前都要先走这个解析。第三样，信号。这条最有意思——你没法给一个函数发 SIGKILL。子进程超时了你 kill 掉就完事了，函数跑在你自己的线程里，你杀了它整个 agent 也没了。所以取消从抢占式改成了协作式：共享一个原子标志位；stdin 那边读到取消就返回一个合成的 EOF，让工具自然地退栈——这个设计很聪明，因为绝大多数命令行工具遇到 EOF 都会优雅退出；实在卡在管道上的，unix 下用 libc::poll 200 毫秒一片地循环重查标志位。（停一拍）下面这个橙色框：补这三个洞的全部代码，叫 pi-uutils-ctx，446 行。它是全仓库最小的一个 crate，但它是那 60 个进程内 builtin 能够成立的前提。八万四千行 Rust 里，最关键的四百四十六行。

（停一拍）看右边。上面是 Ctx 这个结构体，我先声明一句，这是节选——原定义里还有 stdin_fd、stdin_is_search_input、exit_code 三个字段，我为了让它和左边那三样对上，删掉了。剩下的这几行请对着左边看：stdout、stderr、stdin 三行——这就是 fd 表；cwd: PathBuf——这就是相对路径解析；cancel: Arc<AtomicBool>——这就是信号。env 是附赠的第四样，因为 shell 里 export 的变量在宿主进程的环境里根本不存在，也得快照进来。一个结构体，恰好就是进程白送你的那几样东西的清单。

（停一拍）下面这个玫红框是这一页的高潮，我讲慢一点。问题是这样的：如果某段代码跑起来了，但根本没装上下文，怎么办？直觉的做法是"那就退回默认行为，写到真正的 stdout 去"——毕竟总比丢了强。他们选的是丢弃。 看这行代码：if !ctx::is_active() { / 丢弃 / }。写入被丢弃，而不是落到宿主进程真实的 fd 1 和 2。为什么？因为宿主的 fd 1 和 2 是 TUI 的画布。omp 是个全屏终端界面，它自己在精确地控制每一个字符的位置。这时候有一个 vendored 的工具因为没装上下文，往 fd 2 打了一行"warning: something"——整屏就花了，光标位置全乱，用户看到的是一坨乱码。所以这里的 fail-safe 方向是反直觉的：宁可丢数据，不可污染画布。我觉得这是整个 crate 里最能体现"他们真的在终端里用过这东西"的一个设计——你不被这个 bug 咬过一次，你不会把默认行为设成丢弃。

最后这一格是顺手补回的第四样，panic 隔离。子进程里工具 panic 了，内核给你兜着，你只看到一个非零退出码。进程内化之后，一个 panic 直接掀桌子。而且注释里点名了一个真实事故：vendored 的 uu-tail 对 BrokenPipe 做了 unwrap——你 tail -f | head -1，head 一退出管道就断了，tail 那边 unwrap 直接 panic。现在 panic 被 catch_unwind 接住，变成 exit 1 加一行 internal error。底下这行是这一页的总结：子进程模型里内核替你做的隔离，现在每一样都要自己写。

P25 · 最诚实的一张 benchmark：小批量上 Rust 更慢

提词

  • 读法：变的不是代码，只是批量大小
  • 规矩原话：If native is slower, do not switch callsites. [慢]
  • 口径：这是 mnemopi 向量核的数，grep/shell/walker 结果未入库
  • 右边代价三条：111.2 KiB 核心包 vs 每平台 leaf 138–285 MiB

  • 防 subagent 改坏工作树，不防它读你的 ~/.ssh
一句话主旨

同一个核，count=10 时 Rust 是 0.86× 净亏，count=1000 时是 2.48×——变的不是代码，只是批量大小。

怎么讲

这一页我给它起名叫"最诚实的一张 benchmark"，理由很简单——它把自己更慢的那一行也放上去了。（停一拍）先交代口径，看右上角：Apple M1、bun 1.3.14，最关键的是 crossing-inclusive——测的时间包含 N-API 跨越的成本，不是只测 Rust 函数体内部。这个口径很重要，因为很多人贴的 native 性能对比是不含跨越的，那个数字没有意义。（停一拍）现在看表。前两行是 searchExactVectorIndex，count 10 是 1.83×，count 一万是 1.62×，都还行。然后是被玫红条框住的这一行，cosineSimilarityPairs，count = 10，TS 用了 26.42 微秒，native 用了 30.67 微秒，speedup 0.86×——Rust 更慢，净亏 14%。同一个 kernel，我们往下看：count 涨到 100，变成 2.37×；count 涨到 1000，2.48×。（停一拍）变的不是代码，一行都没改，变的只是批量大小。 这就是"读法"那一格说的：N-API 跨越成本是个常数，payload 越小它占的比例越大，小到一定程度就把 Rust 的全部优势吃光。最后这两行 mmrRerankIndices 是另一个极端，22.44× 和 30.18×——为什么差这么多？因为 MMR 重排是个 O(n²) 的算法，计算量大到跨越成本可以忽略不计。所以能不能拿到量级的差距，取决于你的核复不复杂，不取决于你用的是不是 Rust。

（停一拍）看下面这个橙框，我一个字一个字念仓库自己写的规矩："If native is slower, do not switch callsites."——如果 native 更慢，就不要切换调用点。出处是 docs/porting-to-natives.md 第 173 行。这句话看起来是废话，但它在实际工程里非常难做到，因为它意味着：你花了几周把一个函数用 Rust 重写了，测出来更慢，你得把它扔掉。 沉没成本在这句话面前是不算数的。我觉得这才是这一页真正值钱的东西——不是那些数字，是一个团队愿意提前把"我可能白干了"这条规矩写进文档。（停一拍）再往下这两行玫红字是口径，非常重要，我必须说清楚：这是 mnemopi 向量核的数字，不是 grep、不是 shell、不是 walker 的。 后者其实有一个写得相当规范的对照脚本——真的去 spawn 一个 rg 子进程做对照组，先比对匹配数确保语义等价，还带了并发维度，因为并发才是 agent 的真实场景。但是仓库里没有任何一次运行结果被提交。 所以我在这里不给数字，我也建议大家不要引用任何"omp 的 grep 快 N 倍"的说法，那个数在仓库里不存在。

（停一拍）右边这一栏是代价，三条，也全都是实测的。第一条，产物体积。 核心的 npm 包只有一个 loader，111.2 KiB，很轻。但它靠 optionalDependencies 拉一个平台专属的 leaf 包，那个包是——linux-x64 因为有 baseline 和 modern 两个变体，285.2 MiB；其余每个平台 137 到 144 MiB。这里面装的是 56 个 tree-sitter 语法、syntect 的语法和主题、两张 BPE 表、几份位图字体、webrtc 加 opus。对照一下上游 pi 的成本：首次用到的时候下载 rg 和 fd，几 MB。 这是这笔投入最直观的代价，而且它是每一个用户都要付的。第二条，构建复杂度上了一个数量级。 Bazel + rules_rust + hermetic_cc 也就是 zig 做交叉编译工具链 + crate_universe，八个构建目标；而且 cargo 和 Bazel 双轨并存——cargo 仍然是本地开发的权威，Bazel 是产物和 CI 的权威，两套依赖图都得能跑。Rust 工具链也是两份，Bazel 钉的是四月的 nightly，本地是七月的。他们甚至还要自己写一个补丁去绕开 zig 的并发缓存损坏。加白这行是最直观的：Windows 交叉编译要拉大约 3 GiB 的 SDK，darwin 冷构建大约 40 分钟。 第三条，也是最扎心的一条：最难测的那部分，零覆盖。 pi-shell 有 846 个测试，听起来很多，但绝大多数落在 minimizer——也就是纯逻辑、最好写测试的那部分。而 pi-iso 只有 3 个测试、pi-uutils-ctx 3 个、pi-voice 4 个。加白这行：overlayfs、clonefile、ProjFS 这些平台相关的代码，测试为零。 测试覆盖的分布和风险的分布正好是反的——好写的地方写满了，最容易出事的地方一个没有。这不是批评，这是所有做跨平台原生代码的人共同的处境，但把它摊开来看还是有点吓人。

（停一拍）最后这一格，也是我今天在这一章一定要说清的一件事，因为它最容易被讲错。pi-iso 是 CoW 工作区隔离，它不是安全沙箱。 我把整个 crate 翻了一遍：零 seccomp、零 landlock、零 namespace、零 cgroup、零 ptrace、零 job object、零 sandbox_init。 它做的事情是：用 APFS 的 clonefile、Linux 的 overlayfs、Windows 的 ProjFS 这些机制，给 subagent 一份写时复制的工作区副本，跑完再把改动 diff 出来。所以它防的是"subagent 把你的工作树改坏了"，它不防"subagent 读你的 ~/.ssh"，也不防它发起网络请求。这两件事经常被混为一谈，我见过不止一次有人拿"omp 有隔离"去论证"agent 执行是安全的"。不是的。 这个区分我必须讲，因为讲错的代价是有人真的把它当沙箱用。

别漏了说
  • 口径那两行是本页的诚实底线，必须念完：这是 mnemopi 向量核的数，grep/shell/walker 结果未入库。别让听众带走一个不存在的数字。
  • "crossing-inclusive"要解释一句，否则 0.86× 这个数会被质疑口径不公。
  • "If native is slower, do not switch callsites."要念英文原句，并且解释它对沉没成本的杀伤力——这是本页真正的落点，不是那些数字。
  • pi-iso 不是安全沙箱这条绝对不能省，就算时间到了也要说。零 seccomp / landlock / namespace 要具体点名，不要笼统说"没有安全机制"。
  • 285.2 MiB 那条要说明是 linux-x64 因为有双变体，别让人以为其他平台也这么大。
  • 测试覆盖那条的措辞是"覆盖分布和风险分布正好是反的"，不是"他们不写测试"。
可能被问
  • Q：0.86× 是不是测得不对？为什么不多跑几轮？
  • A：这份结果是提交在册的 JSON，我没有本机复跑（本机没有 bun）。但注意它是 crossing-inclusive，小 payload 上跨越成本占主导，这个结论在 N-API 上是通用的，不是这一次测量的偶然。仓库自己在向量核的模块注释里也写了对应的自觉——"每一次导出都处理整批候选，让跨越成本摊到整个召回操作上"。
  • Q：那 grep 到底快不快？
  • A：不知道，我不给数字。仓库有脚本没结果。要我猜的话，并发场景下因为能共享 fs_cache 应该有优势，但这是猜，不能写进 slide。
  • Q：138 MiB 的包，用户装的时候不会崩溃吗？
  • A：optionalDependencies 只会装当前平台的那一个，所以是一个 138 MiB 而不是六个。但对 CI 来说，每次冷装都是这个量级。
  • Q：既然小 payload 更慢，为什么不做个阈值自动切换？
  • A：仓库里没有看到这样的运行时切换机制，规矩是在移植决策这一层做的——测出来慢就不移植。运行时动态切换会带来两套代码路径要同时维护的问题，我猜是这个原因，但这是我的推测。
  • Q：pi-iso 既然不是沙箱，那 agent 执行安全靠什么？
  • A：靠权限审批和工具白名单那一层，也就是第一篇讲的护栏装在"环境真实执行"那一格。pi-iso 解决的是另一个问题——多个 subagent 并行改同一个工作树会互相踩。别把它们混在一起。
  • Q：为什么 Bazel 和 cargo 要双轨？
  • A：MODULE.bazel 里自己说了，cargo 仍然是本地迭代的权威，因为 rust-analyzer、cargo nextest、napi 的 typedef 生成都依赖它；Bazel 只负责产物和 CI 的内容寻址缓存。代价就是两套依赖图。

P27 · 同一份规则 markdown，按 frontmatter 分成三个桶

提词
  • 最该被抄走的一页，讲慢一点 [慢]
  • 输入只有一种：带 YAML 头的 markdown
  • 桶 1 TTSR：有 condition → 占用 0 [重]
  • 桶 2 alwaysApply → 全文，固定税
  • 桶 3 只有 description → 一行索引，rule:// 按需读
  • 判据优先级：TTSR 最高
  • 右栏五步：匹配 → abort → 删半截 → 注入 → 重跑
  • 红利：规则可测试、可生成
  • 代价：O(n²)、重跑丢 token
  • 收口那句要念全 [停]
一句话主旨

同一份规则文件按 frontmatter 自动路由到三种执行时机，prompt 占用分别是 0、全文、一行。

怎么讲

这一页我讲得最慢，因为如果今天全场你只带走一张图，我希望是这张。（停一拍）先看最上面那行小字：同一份 markdown，YAML frontmatter + 正文。请注意「同一份」三个字——这套系统的输入只有一种东西，就是一个带 YAML 头的 markdown 文件，正文是给模型看的整改说明，带 Bad / Good 对照。这些文件从哪来？第二行：按 provider 优先级，native 100、omp-plugins 90、agents 70、cursor 50、windsurf 50、cline 40，按规则名去重，first-wins。也就是说你项目里的 .cursor/rules、.clinerules、RULES.md 它全收，同名的按优先级挑一个。第三行是仓库自带的：27 条内置规则，ts-no-any、ts-import-type、rs-parking-lot、go-range-int 这些，一眼看得出是按语言分的 lint 类约束。

（停一拍）关键来了：这一份文件进来之后，走哪条路，不是人选的，是看 frontmatter 里有什么字段自动分的。 三个桶。

第一个紫框，桶 1，TTSR。判据写在这儿：有 condition 或 astCondition，优先级最高。举两条真实的：ts-no-any 的 condition 就是一段正则，": any|as any"；ts-redundant-clear-guard 用的是 astCondition，写的是 if ($X) clearTimeout($X)。这两条的区别请一定说清——底下这行灰字就是理由：同一个元变量 $X 出现两次，要求这两处必须相等，if ($X) clearTimeout($Y) 不匹配。这是纯正则做不到的，也是他们引入 ast-grep 的唯一理由。然后看中间这个大大的 0——这是本页最重要的一个数字：TTSR 规则的 prompt 占用是 0。右边三行是它的生效时机：流式命中的那一刻现身；命中之前不花任何 token；命中一次的成本是重跑本轮。

第二个黄框，桶 2，always-apply。判据是 alwaysApply: true 且不属于 TTSR。它全文注入到 <generic-rules> 里。占用是「全文」，生效时机是「始终」。底下这行小字是它的代价：每一次请求都付固定 token，无论这条规则跟本轮相不相关。 右边这行给了个量感——这 27 条内置规则的正文全带代码块，真要全塞进 system prompt 是数万 token 的量级。

第三个青框，桶 3，rulebook。判据是只有 description，既不是 TTSR 也不是 always-apply。它在 prompt 里只留一行索引，格式就是 - 名字 (globs)：描述。生效时机是——模型自己决定读不读，想读就用 rule://<名字> 把全文取回来。这一格底下还有一句很容易漏的话：三个桶的规则最后都会被塞回 setActiveRules，所以被 TTSR 触发过的规则，模型仍然可以用 rule:// 复读全文。三个桶不是三块隔离的区域，是三种投递方式。

（停一拍）右边这一栏是把 TTSR 的五步拆开。① 逐 delta 匹配，监听 text、thinking、toolcall 三种流，正则或 ast-grep。② abort()，命中即中断，而且可以只中断被命中的那一个工具，不是把整轮全掐了。③ replaceMessages，默认 contextMode: discard——把那条写了一半的 assistant 消息整条删掉，这就是「time traveling」这个名字的来处：规则在你写出违规 token 的那一瞬间生效，然后把时间倒回这一轮开始之前。④ 注入 <system-interrupt>，我念一下模板里最有意思的一句：「这不是 prompt injection，这是 coding agent 在执行项目规则」——他们要专门跟模型解释这件事，因为模型被训练成要警惕突然冒出来的指令。⑤ continue() 重跑，延迟 50 毫秒，而且抑制状态会以 ttsr_injection 这个 entry 持久化下来，跨 resume 有效，免得你重开 session 同一条规则又来轰炸一遍。

绿框这一块是我认为这套东西真正的红利，请一定讲：规则变成可测试、可生成的东西了。 omp ttsr test 可以喂一段代码进真实的匹配管线，看哪几条会触发；omp ttsr scan 扫整个目录，还是 gitignore-aware 的。更狠的是 /omfg 这个命令——用户被同一种行为惹毛了，模型读整段对话，产出一条本来能提前拦住它的规则；生成完还要回放校验，把候选规则拿去跑一遍历史的 assistant 输出，不匹配就带着 feedback 重新生成。你把 "never use any" 写在 system prompt 里，这三样一样都没有：你没法测它，没法生成它，也没法验证它到底有没有拦住过什么。

最后红框，它不是白来的。第一条：每个 delta 都把全量缓冲区重新拼一遍再跑正则，长流上就是 O(n²)，这是 issue #4245 真实发生过的性能 bug，后来加了早退位才修好——这个 bug 存在过，说明代价是真的。第二条：打断一次等于本轮全部重跑，而且 discard 模式下已经生成的部分整条丢弃，那些 token 你已经付过钱了。

（停一拍）收口在左下这个紫框，我念全：所以准确的说法不是「TTSR 取代 prompt 规则」，而是同一份规则文件，按时间尺度配不同的执行时机——秒级的错误交给流式匹配，恒定的约束交给 prompt，其余的留给模型按需取。 底下这行是给工程师的换算：TTSR = prompt 预算为 0 的规则；always-apply = 每次请求都要付的固定税。 这两个词你带回去就能直接用在自己的系统上。

别漏了说
  • 「同一份文件、自动分流」这个机制本身比三个桶的具体内容更值钱。很多人的第一反应是「我也搞个流式拦截」，那是抄功能；真正该抄的是「规则不该只有一种执行时机」。
  • 那个 0 要指着念出来，并且立刻接一句「代价在命中时才付」——否则听众会以为是免费午餐。
  • 27 条这个数字我逐文件核过：目录下 28 个条目，其中一个是 index.ts，.md 规则是 27 条。仓库研究笔记 R06 里写的是 28 条，那是把 index.ts 一起数了。以页面上的 27 为准。
  • ast-grep 那条一定要讲元变量两处相等，这是「为什么不能只用正则」唯一站得住的技术理由，少了它 ast-grep 就显得是炫技。
  • 「TTSR 命中过的规则仍可 rule:// 复读」这句别跳——它说明三个桶是同一个规则池的三种投递方式，不是三份拷贝。
可能被问
  • Q：正则会不会误杀？": any|as any" 在注释里、字符串里、markdown 里都会命中吧。
  • A：会，而且这是设计上认了的。他们的缓解手段不是把正则写得更精确，而是用 scope 收窄到流上——ts-no-any 的 scope 是 tool:edit(*.ts) 这一类，也就是只在编辑 TS 文件的那股流上匹配，不管你在正文里写了什么。这是个很值得学的取舍：降低误杀靠缩小作用域，不靠提高模式精度。
  • Q：这跟 lint / pre-commit hook 有什么区别？我 CI 上跑 eslint 不就行了？
  • A：区别在时机。lint 是在模型把整个文件写完、工具执行完、你 review 的时候才发现；TTSR 是在那几个 token 刚吐出来的时候就掐掉，然后让模型带着规则重写一遍。省的是「写完—发现—再让它改一遍」这一整个来回。但反过来说，如果你的错误容忍到 CI 才发现也不亏，那你确实不需要 TTSR，用 lint 更便宜——这也是本页要传达的判断方式。
  • Q：桶 3 的 rule:// 靠模型自觉去读，它会读吗？
  • A：不保证。这正是三个桶的差别所在：桶 1 是确定性执行、不依赖自觉；桶 2 是常驻但要付固定税；桶 3 最便宜但最不可靠。所以规则该进哪个桶，本质上就是在问「这条规则漏了会死人吗」。我没有在仓库里找到「模型实际读取 rule:// 的比例」这类数据，这个我不知道。
  • Q：interruptMode 有几档？默认是什么？
  • A：全局默认是 always，也就是命中就中断重跑，规则级可以覆盖成 never。但下一页你会看到一个很反差的事实——先卖个关子。
  • Q：这套东西对延迟的影响有多大？
  • A：仓库里有 O(n²) 的修复记录，但没有 benchmark 数据，「一次匹配是微秒还是毫秒级」我答不上来，这是我这轮取证的空白。

P28 · 作者自己也不敢默认打断

提词
  • 三条代价，全是原话和数字，不是推测 [重]
  • ① 27 条内置规则，27 条全是 never [慢]
  • 能力做出来了，默认档挑最保守的

  • "make the rules load-bearing in code instead of prose"
  • 抑制必须对模型不可见 —— 否则 Stop. 换成 Halt. [重]
  • ③ advisor 默认走强模型，省钱不靠降档
  • 五道闸：默认关 / 只喂增量 / 四层闸门 / 冷却 3 轮 / 背压 30s

一句话主旨

三条代价都是仓库里能查到的原话和数字，其中最有力的一条是 27 条内置规则全部选了「不打断」。

怎么讲

上一页我把 TTSR 讲得很漂亮，这一页专门泼冷水。副标题我先声明一下：这三条代价，全部是仓库里能查到的原话和数字，不是我的推测。 有几条我甚至是逐个文件数过的。（停一拍）

第一条，也是我个人认为整场最有说服力的一条证据。全局默认的 interruptMode 明明是 "always"——能力是做出来的，命中就 abort、就丢弃、就重跑。但是：仓库自带的 27 条内置 TTSR 规则，27 条，一条不落，全部显式写了 interruptMode: never。 这个我是逐文件 grep 过的，不是抽样。never 意味着什么？意味着不 abort，只是把提醒渲染成一个 text block，前置到工具结果的第一个 block 之前——就是这行代码：return { content: [{ type: "text", text: reminder }, ...ctx.result.content] }。模型看到工具结果的时候，先看到那句提醒。（停一拍）所以这一页的读法写在最下面这行红字：打断的能力做出来了，但默认档位挑了最保守的那一档。 一个人把这套流式打断系统从头写出来，最后自己给它配的默认值是「不要打断」。这比我说十句「谨慎使用」都有力。

第二条，advisor。advisor 是可选的第二个模型，每个主 turn 结束后看主 agent 的增量转录，通过 advise 把意见反向注入回来。听起来很合理对吧？现在看这排数字，这是 issue #3520 记录的一个 session：309 次 advise 调用，92 条唯一内容，其中 114 次是 "Stop."，52 次是「无问题，继续」，41 次是「完成」。 309 次里只有 92 条是不重复的，剩下三分之二是复读。而且——念这行——任务早就做完了，主转录还在被 <advisory severity="blocker">Stop.</advisory> 一条条灌满。（停一拍）他们的修复注释我原话念一遍："make the rules load-bearing in code instead of prose." —— 让规则在代码里承重，而不是待在散文里。这句话我认为是整个仓库里最值钱的一句话，因为它可以直接反过来用在你的项目上：你 prompt 里那些「请不要反复提醒用户」「请保持简洁」，全是 prose，全都不承重。

然后是这一页第二有意思的细节，请一定讲：抑制必须对模型不可见。 被丢弃的 advise 调用，工具照样返回 "Recorded."，就跟成功了一样。为什么？理由白纸黑字写在注释里：如果你告诉它「你这条被拦下来了」，它会把 "Stop." 换成 "Halt."，再换成 "Stop now." 绕过去。（停一拍）我第一次读到这儿是有点毛骨悚然的——这不是模型在恶意规避，它只是在尽职地完成「我要提醒主 agent 停下」这个目标，反馈信号让它学会了换个说法。你给模型的每一个失败反馈，都可能被它当成一次优化机会。 这条经验适用于任何你打算给 agent 加限流、加配额、加过滤的场景。

第三条讲钱。直觉上第二个模型应该用小模型对吧？错。ROLE_PRIORITY_ALIAS 里写着 advisor: "slow"——advisor 默认解析到 slow 强推理模型链，而且不继承主模型，所以哪怕你主 agent 用的是便宜模型，advisor 还是一个独立的强模型。省钱不靠降档。靠什么？靠另外五道：第一，默认关闭——advisor.enabled 默认 false。第二，只喂增量转录，每轮只发 delta，不发全量。第三，四层输出闸门，底下这行写全了：归一化（"Stop."、"Stop"、前后带空格的 stop 全归一到一个 stop）→ 无内容短语黑名单 → 全 session 精确去重，4096 条 FIFO → 每个 advisor 周期最多放行一条。第四，打断冷却：immuneTurns 默认 3，一次成功打断之后，接下来 3 个主 turn 里的 concern 和 blocker 全部降级成不打断。第五，背压不是锁步：主 agent 在 turn 结束后最多等 30 秒让 advisor 追上，等不到就走——这 30 秒也正是它默认关掉的原因之一。最后这行注释原话也很好："silence is the correct expression of 'no concerns'"——没问题的正确表达方式是沉默。这一句可以直接抄进你自己给 review agent 写的 prompt 里。

（停一拍）右边这一栏是平衡。绿框：它换到了 prompt-only 给不了的东西——可测试、可生成、可回放校验，这三样上一页讲过了，我这里只重复一句：system prompt 里的一句 "never use any" 没有这三样。 下面紫色这四块是顺带把记忆的天花板说清楚，因为它也是默认关的，我不打算给它单开一页，但这四条你得知道：一，向量是以 JSON 文本存的，memory_embeddings.embedding_json，而且 sqlite-vec 的路径写了但从来不建表。二，所以召回是暴力全表扫，10000 行封顶，规模上会先撞墙。三，事实去重是 SPO 精确匹配——主谓宾三个字段一模一样才算重复，所以换个说法的同一件事会被记两遍，这是记忆膨胀的现实入口。四，工作记忆 TTL 24 小时，但巩固窗口只有一半、12 小时；没赶上巩固的，24 小时后是真 DELETE，不是软删。

最后这个框是本章的收口，我念：这一章能搬走的，不是那 27 条规则，也不是那套记忆表结构；是「按错误的时间尺度，给它配一个执行边界」——秒级用流式匹配，轮级用第二意见，跨 session 用记忆。以及：把 prose 里的软约束，落成代码里的硬闸门。

别漏了说

  • 「抑制对模型不可见」这条要展开讲后果，别只念结论。它是本页唯一一条能直接迁移到听众自己系统上的反直觉设计。
  • advisor 不降档这件事要点破，因为所有人的直觉都是「监督者用小模型」。它选择了「贵但默认关」而不是「便宜但默认开」——这又是一次价值排序。

  • A：不知道。仓库里只有这一个被 issue 记录下来的 session 快照，没有分布数据。我讲它是因为它触发了一次真实的代码修复，不是因为它有代表性。

  • A：仓库没给结论，我也不替大家下。我能给的判断依据是：它补的是 prompt 和正则都覆盖不了的那一层——设计判断、方向漂移、过早宣布完成。这类问题写不成正则，也很难靠同一个模型自查，因为它已经说服自己了。如果你的场景里这类错误代价很高（比如无人值守长跑），那双倍成本可能划算；如果你全程盯着，那你本人就是 advisor。

怎么讲

七个进度点，全亮了，这是最后一章。（停一拍）先说这一章跟前面六章的关系，这句话写在标题下面：前六章讲的是它做了什么，这一章只讲一件事——它是怎么判断该不该做的。 为什么把这个放最后？因为前六章你听下来，很可能会有一种「哇好厉害但跟我没关系」的感觉——一个人写了 153 万行，8.4 万行 Rust，自建 CI 集群，你抄不动，也不该抄。但判断方式是可以抄的，而且是免费的。

往下这行小字列了本章三页的内容，我先说一件事：这三条乍看毫不相干——文档编译进二进制给 agent 自己读、每条禁令后面挂 issue 编号、edit 格式好不好靠基准量出来。但它们是同一件事的三个面，那句共同点写在这行的最后：规范和执法者成对出现，规范才不会腐烂。 文档的执法者是 agent 自己——它读到过时的文档就会犯错，错误立刻暴露文档没更新；禁令的执法者是 issue 号和 smoke test；「什么样的 edit 格式好」的执法者是那个 benchmark。（停一拍）反过来说，你项目里那些只有规范没有执法者的东西——比如一份没人跑的 CONTRIBUTING、一条写在 wiki 里的命名约定——它们不是没用，它们是正在腐烂。

提词

一句话主旨

文档在编译期打包进二进制、运行时由 agent 通过 omp:// 自己懒解压查阅，目的是让检索路径和阅读路径重合。

怎么讲

标题里最重要的是后半句——读者是 agent 自己。（停一拍）左上角这行是这一页的骨架：一份来源，两个消费者。 顺着这条线看：最左边 docs/ 目录，122 篇 markdown，27,931 行；中间 compile-binary.ts 第 42 行，gzip 加 base64；右边注入成一个叫 PI_DOCS_EMBED 的常量，进编译后的二进制。

底下这个框把注入的东西摊开了，其实就两行。第 1 行是文件名的 JSON 数组，["docs/rpc.md","docs/models.md",…]，明文，不压缩。第 2 行是所有正文 gzip 之后 base64，就是这一坨 H4sIAAAA…。为什么要拆成两行？看绿框——因为这两行对应两种截然不同的访问模式。列目录的时候，只解析第 1 行，一个正文都不解压；只有 agent 真的要读某一篇，才在首次读取时到 zlib 线程池上懒解压一次，之后走缓存。这是很讲究的一个设计：目录是高频操作，正文是低频操作，把高频的那部分留成明文。第三行还有一个细节别漏：dev 树、源码 checkout 的时候绕开嵌入，直接读磁盘上的 docs/。所以开发者改了 md 立刻生效，不需要重新编译；同一份 md，人读磁盘，agent 读嵌入，永不分叉。

（停一拍）现在讲为什么。这一段我建议大家把原话记下来，写在 DEVELOPMENT.md 第 7 到 10 行：「曾经住在这里的长篇架构走查，过时的速度比任何人重读它的速度都快。」 所以他们做了什么？把这个文件里的架构描述删了，改成链接过去，而不是留一份会腐烂的散文副本。（停一拍）这句话请对照一下你自己的 README——你那份「架构概览」上次更新是什么时候？

最下面这个青框是真正的收益，也是给大家的可执行版本。收益是这一句：检索路径和阅读路径重合，所以文档不更新，会立刻被 agent 的错误暴露出来。 这就是我上一页说的「规范和执法者成对出现」——agent 就是文档的执法者，你的文档写错了，它照着做就会犯错，你当场就知道。而且请注意最后这行：你不需要抄编译期注入这一步。 最小形态是：把 docs/ 定成唯一权威，AGENTS.md 或 CLAUDE.md 里不写架构描述、只放一张「子系统 → 文档路径」的索引表。成本是一次目录整理加一条 review 规矩。

（停一拍）右边这一栏是同源的另外两条。第一条，AGENTS.md 282 行，是一份执行契约，不是风格指南。全篇 NEVER / MUST，而且每条禁令必须配一个替代物——「不要用 ReturnType<>」后面必须跟「用真实类型名」。为什么？因为禁令没有替代物，agent 会自己发明一个。但最独特的一招是这个：禁令后面挂着它诞生的 issue 编号。看这个例子：worker 入口用 with { type: "file" } → 编译二进制里 worker 静默崩溃，issues #1011、#1027；后来换成字面路径的方案 → 又要求两个构建脚本保持同步，issue #1150。（停一拍）这个 issue 号同时服务两边：人类 reviewer 知道这条不能删——它不是某人的洁癖，是两次线上事故换来的；agent 遇到 edge case 时知道边界在哪。而且它还配了活体执法者：omp --smoke-test 会真的 spawn 一个 worker、ping 它、退出，这个探针接进了 ci:test:smoke。

第二条，测试禁令：Never source-grep。禁止写那种读实现文件源码、然后断言它文本内容的测试——expect(src).toContain("someCall()")、expect(src).not.toContain("oldName")、「注释里必须写 X」。理由写得极清楚：它测的是代码长什么样，而不是代码做什么。 后果是双向的：无害的重构——重命名、换行、import 重排——会把它打挂；而行为真的坏掉的时候它照样通过。这是最坏的一种测试，两个方向的错误都占了。替代方案在底下：结构性不变量用类型测试或者 lint 规则去守，不要用字符串扫描。

最后绿框，三条收在一起：docs 有 omp:// 兜底，禁令有 issue 号和 smoke-test 兜底，测试哲学有 review 契约兜底——规范和执法者成对出现。只写规范不给执法者，规范就一定会腐烂。

  • 「dev 树绕开嵌入」这个细节别省，它是「一份来源」这个说法成立的关键，否则就是两份会分叉的拷贝。
  • 那句 DEVELOPMENT.md 的原话建议念两遍，一遍英文一遍中文——它是本页的情绪高点。
  • 「你不需要抄编译期注入」这句必须说，否则听众会觉得这一页跟自己没关系。最小形态是这一页真正的交付物。
  • issue 号那一招要讲「同时服务两边」，只讲一边（人或 agent）都会显得平淡。

一句话主旨

怎么讲

上一页说执法者。这一页的执法者是一个基准测试。（停一拍）标题里我用了「可测量问题」这五个字，是因为「哪种 edit 工具格式对模型更友好」——用 diff、用 str_replace、用行号、用 patch——这在绝大多数团队里是一个纯口味问题，谁嗓门大听谁的。omp 的做法是：自建一个叫 typescript-edit-benchmark 的包，4,645 行，跑 6 个模型，然后把成绩以 JSON 签进仓库，换模型、换 prompt 就重跑一遍对比。

在念数字之前我先把口径说清楚，右上角这行小字：这是仓库内快照，不是我本次实跑的。 我本机没有 bun，跑不了。而且页脚我也标了，这份 JSON 没有标注样本量和生成时间——从 success 都是 5 的倍数可以推测每个模型 20 个 task，但那是推测。所以下面这些数字请当成「这个团队的一次内部实验记录」来听，不要当成模型排行榜。

（停一拍）现在看表。第一行绿色的是 claude-haiku-4.5，success 90，最高。往下 kimi-k2.5 85，gemini-3-flash 80，minimax-m2.5 75，glm-4.7 65。然后是最后这行红的，我认为这一行值回整页票价：deepseek-v3.2，success 只有 55，全场最低；但它的 edit_success 是 100.0，全场唯一的满分；同时有 9 次 ghost run，也就是空跑。

（停一拍）这三个数字放一起是什么意思？看下面这个红框：它每一次 edit 调用都成功了，但任务成功率最低。 翻译成人话——它落刀很准，但它失败在「决定该编辑什么」这一步。 你让它改，它一改一个准；问题是它经常改错地方，或者干脆什么都不改（那 9 次 ghost run）。（停一拍）这行的最后半句是我最想让大家带走的：这种诊断只有量化才看得见，人肉试用是看不出来的。 你手动试几次 deepseek，感觉「诶它挺听话的呀，每次都改成功了」，你永远发现不了真正的瓶颈在定位而不是在编辑。这就是把口味问题变成测量问题的价值——它不只给你排名，它给你归因。

再看怎么造题，因为这决定了这份数据能说明什么。第一句：测的是编辑精度，不是找 bug 能力。 做法是从真实的 TypeScript 仓库取源文件，做 AST 级的平凡变异——注意「平凡」两个字，变异本身要简单，改个标识符、挪个语句就行，因为重点不是难度，是能不能在困难上下文里外科手术式地打上这个补丁。然后是四档难度，这一条设计得很聪明：四档难度不改任务难度，只改「要模型自己定位多少」。easy 直接给精确行号；medium 给所在函数；hard 是长文件加相似块，不给位置；nightmare 是近似重复的区域反复出现，还是不给位置。（停一拍）所以它隔离出来的变量非常干净——同样的修改内容，只改变「你得自己找多远」，测出来的就是定位能力。

判分在最下面：逐字节比对期望产物，同时记一个 formattedEquivalent——就是用 prettier 归一化之后是否等价。为什么要记这个？为了区分「改错了」和「只是缩进不对」。这两种失败的严重程度完全不同，混在一起统计你就什么都看不出来了。

（停一拍）右边这一栏是同一种做法用在另一个地方——CI。上面这个框是他们测试分片崩溃的排查结论，直接写在代码注释里，英文原话："Bisection showed no single file is at fault — the crash is cumulative heap volume." 没有哪个文件有问题，崩溃是累积堆体积导致的。下面红框是这次二分实验的对照数据，在强制 256MB 堆的条件下：10 个文件一个 chunk，约 50% 的运行会 abort；切成两个 5 文件的半区，各自 0 比 20，一次都不崩。 崩的位置也定位到了：bun 1.3.14 的 GC 标记阶段，exit 133 或 134，堆积的是 native 的 ghostty-vt cell。

所以下面这个框——chunkSize 不是拍脑袋定的。UI / TUI 桶 chunkSize 是 5，runtime / native 桶是 10，singleton 桶故意不切，因为全局状态必须共进程。每一个数字背后都有一次实验。

最后绿框三条可搬走的：① 分片逻辑离开 YAML，进一个能本地跑、自己还有单测的脚本——他们真的有一个 ci-concurrency.test.ts 在守着 CI 的并发组规则。② 每个魔数旁边写清它是怎么测出来的，这一条我觉得所有人今天回去就能开始做。③ 送一个具体的坑：验证动态库加载别用 -e。bun -e 'require("./x.node")' 对一个损坏的 addon 也返回 exit 0，会把 dlopen 失败吞掉；写成脚本文件才会真的失败——而且他们是用一个损坏的 .node fixture 实测验证过的，不是猜的。

别漏了说

  • deepseek 那一行要念全三个数字（55 / 100 / 9），少任何一个归因就不成立。
  • 「四档难度只改定位距离，不改任务难度」是这份基准科学性的关键，别讲成「四档难度递增」。
  • formattedEquivalent 这个字段要讲它解决什么问题，否则听起来只是个实现细节。
  • 右栏的 0/20 这个对照数据要念出来，它是「魔数旁边写清怎么测出来的」这条建议的活样本。

  • A：不能。它没标样本量、没标生成时间、没标 fixture 版本，而且只测编辑精度这一个维度。它的价值在于方法，不在于排名。另外仓库 README 里还有另一张表（Grok Code Fast 1 从 6.7% 提到 68.3% 那组），跟这份 JSON 的模型集合交集为空——是两个不同批次的实验，我没有找到能复现 README 那组数字的脚本，所以我今天不讲它。

怎么讲

最后一页。前面七章我给了大概一百多个细节，现在我把它们压成两栏。副标题先说清这两栏的写法差异，因为这个差异本身就是我的态度：左边每一条都有仓库坐标和成本估算；右边每一条都注明它在解什么问题——你没有那个问题，就别付那个代价。（停一拍）我不写「好的实践」和「坏的实践」，因为右边这六条在 omp 自己的语境里全都是对的。

先看左边五条。

第一条，把 AGENTS.md 写成带故障史的执行契约，而不是风格指南。 具体怎么写：第一段先消歧义——原文那句我很喜欢，「用户说 agent 的时候，指的是仓库里的那个 CLI 实现，不是你（助手）自己」，这一句解决的是 agent 在自指仓库里最容易犯的错：把用户的 bug 报告当成对自己行为的抱怨。然后是包结构表、默认工作区。规则一律 NEVER / MUST，每条禁令必配替代物。API 选择用「操作 | 用什么 | 不要用什么」的对照表——这种形式对 LLM 极其友好，它把「我该用哪个 API」从检索问题降级成了查表问题。最后是那一招：每条非显然的规则挂 issue 号，并且配一个活体执法者。成本写在底下：一天写初版，之后每次事故补一行。 我标了一句话——投入产出比最高的一条。如果今天你只做一件事，做这个。

第二条，给你的 agent 建一个编辑精度基准，哪怕只有 20 个 case。 上一页讲透了，这里只强调三个要点：从你自己的代码库取源文件，不要用合成代码；四档难度只控制上下文难度，不控制任务难度；结果签进仓库，换模型就重跑。成本一个周末，最小版本 200 行。

第三条，用契约测试取代覆盖率测试，并明令禁止 source-grep。 核心是这一句：每个新测试要能一句话说出它守护的那一个外部可观察契约，说不出就别加这个测试。 加上禁止断言源码文本，加上测试必须「全量套件安全」——不能做文件级的长期改写 env 或 platform，要用 spyOn 加 restoreAllMocks。（停一拍）这一条我特意标了：它适用于任何项目，跟 agent 完全无关——这是纯粹的软件工程收益。 你今天就算不做 agent，这条也该抄。
