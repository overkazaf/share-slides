## P2 · 关于这一篇：一个人的 fork，凭什么值一整讲

**一句话主旨**：值得花一整讲，是因为它和 pi 同源，所以每一处差异都是一个可归因的工程决定；但它不是推荐给你用的产品。

**提词**：
- 三张卡：为什么是它 / 你能带走什么 / 这一讲不做什么
- 关键词：**同一份基座 ⇒ 可归因** [重]
- 它把失败也留在仓库里 —— 回滚、issue 号、"这条更慢别切"
- 中间卡按可迁移性排，不是按精彩程度
- 右卡最重要：不推荐产品 / 不跑分 / 未实跑一律标注 [慢]
- 「omp 口味很重，多数人不该用」要原话说出来 [停]
- 底下那行是仓库和 discord，笔记全开源

**怎么讲**：
（停一拍）先回答一个合理的质疑：一个人写的 fork，凭什么占你们一个小时。（指左边这张青色卡）三个理由。第一，第一讲那张 harness 七层地图，我找了一圈，**omp 是我能找到的唯一一个七层全点满的公开样本**——上下文管理、工具层、权限、多模型适配、记忆、TUI，它每一层都有自己的、明显不是抄来的做法。第二个理由才是关键，这也是我为什么把它排在 pi 后面讲：**它和 pi 是同一份基座**。这意味着什么？意味着两边的**每一处差异都是一个可归因的工程决定**，不是风格差异，不是「这个人喜欢这么写」。上游有的它删了，那是它判断不值；上游没有它加了，那是它判断值。你等于拿到了一份带对照组的实验记录，这在开源项目里是很稀有的。第三个理由——（重）**它把失败也留在仓库里**。这个我要特别强调，因为大部分项目只留成功：仓库里有回滚记录、有引用具体 issue 编号的注释、CH5 里你会看到一条 benchmark，作者自己测出来 Rust 版本在小 payload 上比原来还慢，他没删这个结果，而是在代码里写了一句规矩——「**若更慢，不要切换调用点**」。（停一拍）能看到人家怎么面对自己的失败，这比看功能列表有用得多。

（指中间绿卡）那你今天能带走什么。这四条我是**按可迁移性排的，不是按精彩程度排的**——也就是说，越靠上的越可能明天就用得上，跟你用什么语言、什么框架关系越小。第一条**规则三桶路由**，同一份 markdown 规则文件，按 frontmatter 分流到三种不同的执行时机，这个想法脱离 omp 也成立。第二条**逐工具并发调度**，核心逻辑十三行，你抄完就能用。第三条是个方法而不是代码——**把口味问题变成可测问题**：编辑工具怎么写更好，这本来是个吵不完的事，他自建了一套 edit benchmark 把它变成有数的事。第四条是那份**别抄清单**，六项我认为的过度工程，每项我尽量附了代价数字。

（指右边玫红卡，慢下来）但是——这张卡我讲得最慢，因为它划的是边界。第一，**这一讲不做产品推荐**。我不劝你换工具。我把话说明白：**omp 的口味很重，多数人不该用它**。它有大量为作者一个人的工作流做的取舍，你照搬会很难受。今天讲它，是把它当研究样本，不是当推荐位。第二，**这一讲不跑分**。所有性能数字都只引用仓库里自带的 benchmark 和代码注释——原因很实在，**我本机没装 bun**，跑不起来。所以凡是我没实跑过的，页面上一律有标注，你看到那个标注就知道那是转述不是实测。这条我宁可讲得难听一点，也不想让你把二手数字当成我验过的。第三，**先认错再讲课**——下一页就是上一讲的三处更正。（指底下那行小字）另外，这一讲背后的**八份研究笔记同步开源**，仓库和 discord 都在这行，页面上放不下的细节全在里面。

**别漏了说**：
- 「同一份基座 ⇒ 每处差异都可归因」是这一页的核心，也是回答「凭什么讲一个 fork」的正面答案。别只念卡上的字，要把「带对照组的实验」这个比方说出来。

- 「本机没装 bun，未实跑的一律标注」也必须说出口，而且要在第一次出现 benchmark 数字之前就说。这是本讲诚实度的底线，第一次说清楚，后面每次引用就不用重复道歉。
- 中间那张卡要交代「按可迁移性排序」这个排法本身，否则听众会以为你把最精彩的放前面，然后对后面失去注意力。

## P3 · 上一讲的三处更正：先认错，再讲课

**一句话主旨**：上一讲讲 omp 的那一页错了三处，根因是同一个——我用的是旧笔记，而结论没有和取证日期绑在一起。

**提词**：
- 这是全场的态度页，慢，不要赶 [重][慢]
- 三处：FORK.md 归属错 / 「点阵图」措辞误导 / BM25 已删
- ① 最严重：张冠李戴。全史 16,613 commit，`git log --all -- FORK.md` **零命中**
- ② 不是信息可视化，是**缩微胶片**：点阵字体印成 PNG，vision 模型 OCR 读回
- ② 「零 LLM 调用」限定为零**额外**调用；帧此后每轮重附，按 vision token 计费
- ③ BM25 工具发现已删除，改 `xd://` 虚拟设备挂载
- 根因：依据 v16.3.12 旧笔记，omp **2.4 天一个版本号**
- 教训一句话：**讲快速演进的项目，取证日期必须和结论绑在一起** [停]
- 不辩解，不找补，说完就走

**怎么讲**：
（停一拍，不要笑场，正常语速开始）上一讲我有一页讲 omp，那一页，**错了三处**。今天开讲之前先把它改掉。（停一拍）三处我一条一条说，说错在哪、为什么会错。

（指第一张卡）第一处，也是最严重的一处。上一讲我说，omp 最值得抄的东西是它的 **FORK.md**，里面有一套 tier 成本模型——把 fork 相对上游的改动按维护成本分层。我甚至在页脚标了出处，写的是 `oh-my-pi/FORK.md`。（停一拍）**这个文件从来没有存在过。** 我这次把仓库 unshallow 拉了全史，一万六千六百一十三个 commit，`git log --all -- FORK.md`，**零命中**。它不在 HEAD 里，也不在任何一个历史版本里。那份 tier 模型是真实存在的，但它出自**某个私有下游 fork 自己写的维护手册**——我当时手上同时开着两个仓库的笔记，把它安到了 omp 头上。这是张冠李戴，属于最不该犯的一类错，因为它不是判断错误，是取证错误。（指卡底那行小字）那套 tier 模型本身我今天仍然认为成立，但今天开始它归属于「某个下游 fork 的做法」，不再挂在 omp 名下。

（指第二张卡）第二处，措辞误导。上一讲我说 snapcompact 把旧的对话记录「**画成点阵图**」，还说它零 LLM 调用。（停一拍）方向是对的，但「画成点阵图」这个说法会让人往错的地方想——听着像是信息可视化，像是把内容抽象成图表。**不是。** 它做的事更接近**缩微胶片**：把文本用**点阵字体直接印成一张 PNG**，需要的时候，让 **vision 模型 OCR 读回来**。信息一个字都没有被抽象掉，只是换了个存储介质。另外「零 LLM 调用」我也得加个限定——是零**额外**调用，压缩这个动作本身确实不需要再叫一次模型；但那张帧此后每一轮都要重新附在上下文里，是**按 vision token 计费**的。（指卡底）这个区别不是抠字眼——**它直接决定了压缩率该怎么算**，CH3 那一章我会拿真实数字回来讲，你会看到压缩率其实并不是这个设计的卖点。

（指第三张卡）第三处，过时。上一讲我说 omp 默认只给模型 6 个必备工具，其他工具让模型自己用 **BM25** 检索出来。这个机制**已经被删除了**，CHANGELOG 里有明确的删除记录，现在改成了 `xd://` 虚拟设备挂载这套做法。（停一拍）那我为什么会讲一个已经不存在的机制——因为我写上一讲的时候，依据的是我在 **v16.3.12** 时期做的旧笔记。而这个项目，（重）**平均 2.4 天出一个版本号**。（停一拍，慢）所以这三处错误，前两处是我自己不细致，第三处不完全是——但它们其实是同一个根因：**我的结论没有和取证日期绑在一起**。一条关于快速演进项目的结论，脱离了「我是在哪个 commit 上看到的」，它的保质期可能只有几天。这是我这次最大的收获，也是我今天想让大家带走的第一件事：**讲快速演进的项目，取证日期必须和结论绑在一起**。（指页脚）所以你会看到，今天**每一页页脚都标了取证基准 HEAD**，就是为了防这件事。这不是仪式感，是我交过学费的。

（停一拍，收）好，认完了，我们开始讲课。

**别漏了说**：
- **不要辩解**。尤其是第三条，很容易顺嘴说成「这不怪我，它更新太快」——那就把这一页毁了。正确的说法是「根因是我没把日期和结论绑在一起」，把责任收回自己这边。

- ② 里「零 LLM 调用 → 零**额外**调用 + 按 vision token 计费」这个限定必须补上，它是 CH3 压缩率那两页的前提。
