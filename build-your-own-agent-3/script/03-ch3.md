## P15 · snapcompact 是缩微胶片，不是点阵图

**一句话主旨**：它不是把历史画成信息图，是用点阵字体把历史**印**成 PNG，让 vision 模型 OCR 读回——排版印刷，不是可视化。

**提词**：
- 先念常见讲法：把历史「画成点阵图」
- 上一讲就是我这么讲的 [重]
- 实情：印刷，不是画图；模型做的是 OCR
- 四步：序列化归一化 / 中央凹排版 / Rust 光栅化 / 模型读回
- 真点阵字体文件：X.org 5x8、unscii 8x8、Silver 兜底
- 名字 = microfiche，注释自称档案管理员翻胶片
- 右栏：零 LLM 调用要加限定词——零*额外*调用 [慢]
- 帧此后每轮重附，按 vision token 计费
- 三重夹逼：80 帧 → 3MB 预算压到 17 帧
- 怎么念才不误导：✓「压缩这一步零额外调用」 ✗「这套方案零成本」 [停]

**怎么讲**：
先看左上角红框，我把常见讲法原样念一遍：**"把丢弃的历史画成点阵图"**。这句话里"点阵"两个字是对的，"画成图"是误导的。（停一拍）我得先认个错——**上一讲这一页就是我这么讲的**。第 3 页那三条更正里的第二条就是它。为什么这个措辞会误导？因为你听到"画成点阵图"，脑子里浮出来的是热力图、散点、色块矩阵，是**信息可视化**——好像它把一段对话抽象成了某种视觉编码。不是的。看右上角紫框：实际做的事是**把历史用点阵字体印成缩微胶片**。PNG 上就是一行行逐格印出来的、你我肉眼也能读的文字。模型读回的时候做的是 **OCR**，不是读图表。所以正确的比喻是排版印刷，不是数据可视化。（停一拍）为什么我要为这三个字较真？因为它直接决定了后面两页怎么算账——如果是可视化，那"压缩率"就是个信息论问题；既然是印刷，压缩率就变成了一个很土的问题：**一张图能印多少字符、这张图按多少 token 计费**。这就是下一页那张表的全部内容。

往下看这四步流水线，我快速过。① 序列化加归一化：把要丢弃的消息压成 `¶user` `¶think` `¶ai` `¶call` 四种前缀的紧凑文本，然后剥掉 ANSI 颜色码、折叠空白，换行折成一个实心方块 `█`——注意这一步**已经是有损的**，工具结果每条封顶 2000 字符，而且是掐头留尾，注释说理由是"报错和测试失败通常落在尾部"。② 排版，这一步最值得看，叫**中央凹**布局，foveation，就是人眼视网膜中央清晰、周边模糊那个词：时间轴的**两端**——会话最开头和最近这一段——保留纯文本，因为这两块要能被精确检索；**中段**才成像；中段的中段再降质，超预算就从最老的那一端整段丢。③ 光栅化，这一步在 Rust 里，一千七百多行，用的是**真实的点阵字体文件**——X.org misc 的 5x8、6x12、8x13，unscii 的 8x8，还有个 TrueType 兜底字体叫 Silver。这些是字体文件，不是他们自己画的像素。④ 模型读回，前置条件写在这儿：模型的 input 必须包含 `image`，不支持图片的模型直接降级回 LLM 摘要。而这一步是 OCR，所以"读不读得出来"就变成了一个**可以打分的指标**——下下页整页都在讲它怎么塌的。底下这个紫框是名字的由来：snapcompact 约等于 microfiche，缩微胶片；注释原话是 "like an archivist at a snapcompact frame reader"，作者自己就把这套东西比作档案管理员在阅读器上翻胶片。名字已经把意图说完了，是我们上一讲没读到位。

（停一拍）现在看右边这一栏，这是本页第二个要纠的说法，而且是我更在意的一个。红框：**"零 LLM 调用 = 零成本"**。第一句"零 LLM 调用"我上一讲也说了，它**准确**，但少了一个限定词，少了这个词就会把人带沟里。紫框给限定词：是零**额外**调用。压缩这一步确实完全本地完成——Rust 光栅化，不要 API key、不走网络、没有推理延迟、结果可复现，这几条都是真的，含金量也很高。但是——看下面这三个盒子：轮 T 压缩发生，额外 LLM 调用 0 次；轮 T+1，这 N 帧图要**重新附上去**，按 vision token 计费；轮 T+2，再附一次，再计一次费，一直到下次压缩重排为止。所以省的是**一次推理、一次不确定性、一次幻觉机会**，不是 token。token 该花还得花，而且是每轮都花。正因为如此，帧数必须被夹住，看这个琥珀框：`MAX_FRAMES_DEFAULT` 是 80，注释说这个数是按"装下大约 400k token"选的；但真正生效的是下面这条——`FRAME_DATA_BYTES_BUDGET` 3 MB，把上限**实际压到了 17 帧**。理由写得特别实在，我念原话的意思：*一个 100 万 token 的模型纸面上放得下 70 张图，但放不下每轮 11 MB 的 JSON payload*。这是一句非常工程的话——约束不在 token 数上，在 HTTP body 上。另外还有一条我觉得挺有意思：未知 provider 的图片张数预算只有 5 张，也就是它对没见过的服务商是极度保守的。最后念一下绿框，这是我给自己定的口径，也建议大家这么念：说**"压缩这一步零额外 LLM 调用"**是对的；说**"这套方案零成本"**是错的。

**别漏了说**：
- **必须当众提一句上一讲讲错过**，并且点名是第 3 页更正卡的第二条。这一页的可信度全靠这个动作立起来。
- "零 LLM 调用"务必加"额外"两个字，并把"帧此后每轮重附、按 vision token 计费"说出口——这是本页最容易被人带走的一句话。
- 中央凹布局要讲清楚"两端留原文"的动机是**可精确检索**，不是随便留的。
- 4 个信息丢失点在页脚小字里，至少点一下"序列化截断是量级最大的那个"，别让人以为成像才是主要损失来源。
- `¶think` 段必然丢失这一条值得单独说半句：把 reasoning 原样喂回 Claude 会触发它的分类器，所以思维链在 compaction 之后是**必然**没了的，不是可选项。

**可能被问**：
- Q：为什么不直接存文本？文本不是更好检索吗？
  A：这正是下一页要回答的。剧透一句：在 Claude 上确实几乎没差，它换的不是空间，是"不需要模型参与"这件事。
- Q：模型 OCR 读图会不会读错？读错了怎么办？

- Q：这些点阵字体是自己画的吗？
  A：不是，是现成的字体文件——X.org misc 那套和 unscii，外加一个 TrueType 的 Silver 做兜底。所以这块没什么魔法。
- Q：本地跑过吗？有没有实际生成的 PNG 可以看？
  A：没有。本机没装 `bun`，snapcompact 的测试一行没跑，我看到的全是代码。这一页的所有说法都是读码所见，页脚标了文件行号。

**过渡到下一页**：那既然是印刷，账就好算了——一张图印多少字、按多少 token 收费，除一下就完了。下一页这张表是本章最反直觉的一页，我先给结论：**在 Claude 上，它几乎不省 token。**

## P16 · 压缩率不是重点，确定性才是

**一句话主旨**：Claude 上 4.2 vs 纯文本 4.0 chars/token，几乎打平；真正的卖点是"上下文已经爆了、摘要式压缩恰好失效"的那一刻它还能跑。

**提词**：
- 先念常见讲法：变成图就省 token，一图胜千言
- 实情：省不省完全取决于 provider 的图片计费模型 [重]
- 表从上往下念：Gemini 21.26（×5.3）→ Kimi 6.66 → GPT 4.83 → Claude 4.20（×1.05）→ 纯文本 4.00
- Gemini 为什么白嫖：每图恒定 1120 token，与像素无关
- Anthropic 走 (size/28)² × 1.05，放大就加钱
- ⚠ 这张表是按代码公式**手算**的，不是实测 [重][慢]
- 右栏对照表，重点只在第 4 行：上下文已经爆了 → 摘要不可用 / snapcompact 可用
- 鸡生蛋：摘要请求要复用已经溢出的上下文
- 卖点是**确定性**，不是压缩率 [停]
- 代价三条：绑死 vision / MB 级 base64 伤缓存 / 降级成 OCR 可读性

**怎么讲**：
上一页说了，既然是印刷，那就该算账。这一页是本章、可能也是本场最反直觉的一页，所以我讲慢一点。（停一拍）还是先念左上角的常见讲法：**"把文本变成图，token 立刻省下来"**，理由通常是那句"一张图胜过千言万语"——图肯定比文本便宜。右边紫框，实情：**省不省，完全取决于 provider 的图片怎么计费**。不是取决于这个算法有多聪明，是取决于人家的价目表。

看这几根条。我从上往下念，右边这一列是 chars/token，就是"一个 token 能装多少个字符"，越大越省。**Gemini 3.x，21.26**，对比纯文本基线是 5.3 倍，这根条最长，是唯一一个吃到大红利的。往下 Kimi 和 GLM，6.66，1.67 倍，还行。GPT / Codex，4.83，1.21 倍，聊胜于无。然后是这一根——**Claude Opus 4.7 以上，4.20**。最底下这根虚线框是纯文本基线，**4.00**。（停一拍）4.20 比 4.00，**×1.05**。也就是说，在 Claude 上，你把整段历史印成图，省下来的 token 是 **5%**。基本等于没省。这个数第一次算出来的时候我以为自己算错了，回去把公式又对了一遍。

为什么会这样？看这个紫框，答案很简单，简单到有点好笑：`familyBilling()` 这个函数的 google 分支，`frameTokenEstimate` 是**恒定的 1120，与像素无关**。一张图 1120 token，不管你这张图是 512 还是 2048。那作者当然就把 Gemini 那条线的帧放大到 2048px——这是**纯白嫖**，代码注释里就是这个意思。而 Anthropic 这条线走的是 `ceil((size/28)²) × 1.05`，是随面积走的，你把图放大，token 就等比涨上去，怎么调都在原地。所以这不是算法差距，是计费模型差距。

（停一拍）现在讲这一页我最需要说出口的一件事，看底下这个琥珀色的框：**这张 chars/token 表是我按代码公式手算的，不是实测**。依据两处：几何在 `geometry()`，计费在 `familyBilling()`，两个函数的行号都在框里；基线那个 4.0 chars/token 也不是我拍的，是**仓库自己注释里的换算口径**——它自己的 token 计数器默认就是 `bytes/4`，所以我用 4.0 做基线，和它自己的会计口径是一致的。但我必须说清楚局限：本机没有 `bun`，仓库的测试和 `research/` 下那 80 个 eval 脚本我一个都没跑，那些脚本要真实 API key，结果目录也没入库。如果真实 transcript 更密——里面全是 JSON 和代码，实际可能落在 3.5——那所有比值会上浮 5% 到 25%。**方向不会变，Claude 那一行还是打平，但精确到小数点第二位你别信我。**

那省不下 token，它到底换来了什么？看右边这张对照表。额外 LLM 调用，摘要 1 次，它 0 次；确定性，摘要每次都不一样，它是纯函数；幻觉风险，摘要有，它没有，因为原文逐字保留只是换了个载体。这三行都好，但都不是决定性的。**真正的卖点在第 4 行**，我把它标成紫色了：**"上下文已经爆了"**——LLM 摘要在这一格是**不可用**，snapcompact 是**可用**。为什么摘要不可用？看这个紫框：摘要式压缩要先发一次请求让模型写摘要，可**那次请求本身要复用已经溢出的上下文**。上下文都爆了，你还怎么发这个请求？这是个鸡生蛋。docs 里写得很直白，handoff 策略不用于 overflow 场景，理由就是这个。而 snapcompact 在那一刻依然能跑，因为**它根本不需要模型**。（停一拍）所以这一页的标题才叫"压缩率不是重点，确定性才是"。这套方案的价值不是"更省"，是"**在别的方案失效的那一刻它还在**"。这是两种完全不同的价值——一个是效率，一个是**兜底能力**。工程上后者往往更贵。

代价我也得对称地念完，看红框：① 绑死 vision 模型，纯文本模型自动降级回摘要；② 每轮重附 MB 级 base64，前缀缓存吃亏——这条挺疼的，因为现在大家都靠 prompt caching 省钱；③ 信息不是被压缩了，是被**降级成了 OCR 可读性**，f1 在 .287 到 .973 之间剧烈波动，下一页整页讲这个。最后一句看页脚小字：omp 并没有二选一，`context-full`——也就是 LLM 摘要——完整保留为 fallback，非 vision 模型自动切回去。**是互补，不是替代。**

**别漏了说**：
- **"这张表是手算的、不是实测"必须讲出口**，不能只留在页面上让人自己看。这一页是全场数字密度最高的一页，口径不交代干净，后面所有数字的可信度一起塌。
- 基线 4.0 的来源要说清楚是**仓库自己的注释**，不是我随手取的——这是这张表唯一站得住的支点。
- 第 4 行"上下文已经爆了"要专门停一下，这是全页唯一必须被记住的东西。前三行都是铺垫。
- 代价三条要念完，不能只夸。特别是"伤前缀缓存"这条，对成本敏感的团队这条可能比 token 本身更重要。

**可能被问**：
- Q：既然 Claude 上不省，为什么还默认用它？
  A：因为默认策略选的不是"最省"，是"最不会失败"。overflow 那条路径上摘要根本发不出去，而这个能跑。另外 omp 是多模型的，同一份代码要同时服务 Gemini 那条线，那边是真省。
- Q：4.2 和 4.0 差这么小，会不会是你算错了？
  A：有可能。这就是我标"手算"的原因。公式我核了两遍，几何和计费两个函数都读过，但没实跑。要是有人跑出实测数，我很想知道。
- Q：为什么不用更密的字体把 Claude 那条线也堆上去？
  A：**试过，失败了**。这正是下一页的全部内容——他们试过 33 chars/token 的方案，模型读不出来。
- Q：MB 级 base64 每轮重发，网络和延迟不会有问题吗？
  A：会，而且他们撞过。`FRAME_DATA_BYTES_BUDGET` 那个 3 MB 的硬保护就是为这个加的，注释里说不加的话会出现"HTTP body 收下了，但流到一半 5xx"。
- Q：那 Gemini 那个 1120 恒定计费，是不是随时会变？

## P17 · 他们主动把压缩率降了一个量级，换可读性

**一句话主旨**：作者主动放弃了近一个量级的压缩率去换 OCR 可读性；而更值钱的是元层面的那件事——**eval 数字被写进代码注释，和它决定的参数住在一起**。

**提词**：
- 先念常见直觉：压缩率当然越高越好，字印得越小越省
- 实情：压得太狠，模型不是读错，是**直接摆烂** [重]
- 左卡旧线 5x8-sent@2576：165,830 字符/帧，33.0 chars/token，f1 **.351**
- 右卡当前 11on16-bw@1568：13,916 字符/帧，4.23 chars/token，f1 **.806**
- **两个口径别混**：字符/帧 11.9×；chars/token 7.8× [慢]
- 失败机理：低于 OCR ~16px/char 下限 → abstained，模型拒答
- 不是缓慢劣化，是过线断崖 —— 调参找的是那条线在哪 [停]
- ⚠ f1 来自代码注释，不是本次实测
- 右栏才是重点：eval 写进代码注释，和参数住在一起
- 对照我们自己：参数在代码里，结果在某人 notebook 里
- 能搬走的一条：魔数旁写清对照组 / 指标 / 时间

**怎么讲**：
上一页最后我说他们试过更狠的，这一页就是那次的记录。（停一拍）先念左上角的常见直觉——注意这次我写的是"直觉"不是"讲法"，因为这条基本没人会质疑：**"压缩率当然是越高越好，字印得越小，一帧塞得越多，越省钱。"** 听起来天经地义。右边实情：**压得太狠，模型不是读错，是直接摆烂。** 于是他们主动把压缩率砍掉了将近一个量级，换回可读性。

看这两张对照卡。左边红卡是**已废弃**的老方案，shape 叫 `5x8-sent`，帧尺寸 2576px。它有多猛？**每帧 165,830 个字符**——十六万五千字，一张图。换算成 chars/token 是 **33.0**，是纯文本的 8.3 倍。这是一个非常漂亮的压缩率。然后看底下这个数：在 opus-4.8 的工具输出 benchmark 上，f1 只有 **.351**。右边紫卡是当前默认，`11on16-bw`，1568px：每帧 **13,916** 字符，chars/token **4.23**，也就是上一页那个"几乎不省"的数。f1 **.806**。同一个 benchmark，同一个模型。

（停一拍）这里我要特别小心地说一件事，因为很容易讲混：**这里有两个口径，别混着讲。** 按**字符/帧**看，从 165,830 掉到 13,916，是掉了 **11.9 倍**；按 **chars/token** 看，从 33.0 掉到 4.23，是掉了 **7.8 倍**。这两个数不一样，因为两条线的帧尺寸不同，计费也不同。页面上这个"净换算"框我写的是 **压缩率 ÷ 7.8，f1 × 2.3**，用的是 chars/token 这个口径，因为它才是真正的"省不省钱"。要是你想说"每帧塞的字少了多少"，那是 11.9 倍。标题写"降了一个量级"是取了个不刺激的说法，你们照哪个口径讲都行，但**别在同一句话里混着用**。

失败机理写在注释里，而且非常具体，看这个紫框：`"fell below the OCR ~16px/char floor and abstained"`。翻译过来是：字号掉到了 OCR 大约每字符 16 像素这条下限以下，然后模型 **abstained**——**弃权**。（停一拍）这个词很关键。字太小的时候，模型不是读岔了、认错字了，**它是判断自己读不了，然后拒绝回答**。所以这条曲线不是缓慢劣化，是**过了门槛就断崖**。这对调参的含义完全不同：你要找的不是一个最优点，你要找的是**那条线在哪儿**，然后站在线的安全一侧留出余量。旁边那行小字给了同批的对照组：`8on16-bw` 是 .755，还不错；而 Gemini 那条线上 `doc-8on16-sent-dim` 只有 **.287**——换个模型，同一个现象再现一次，说明这不是 Claude 特有的脾气。

底下这个琥珀框我必须念：**上面这些 f1 来自代码注释，不是本次实测**。是作者跑完 bench 之后手写进注释的结论，行号我标了。仓库里**没有**可复跑的结果文件，`research/` 下 80 个 eval 脚本全要真实 API key，`results/` 没入库，本机无 `bun`，我一行也没跑。所以这些数字的可信度取决于你信不信作者的注释——我倾向于信，因为它连失败机理都写了，但**这是引用，不是验证**。

（停一拍）好，现在讲这一页我真正想讲的东西。前面那些数字都是铺垫，右边这一栏才是我把这页放进来的理由。看这个大字：**eval 数字被写进代码注释，和它决定的那个参数住在一起。** 位置就在 shape 表的**正上方**——不是 README，不是 wiki，不是某个 Notion 页面。下面这个代码框是节选，你看它长什么样：opus-4.8 配 11on16-bw f1 .806，下面跟着对照组 8on16-bw .755、6x12-dim .351，再下面是 gemini、kimi 各自的胜出项。这意味着什么？**意味着任何一个来改这个参数的人，一定会看见当初为什么选它、对照组是谁、差多少。** 他不需要去问人，不需要考古。

对照一下我们自己通常怎么做，看这个红框：参数留在代码里，实验结果留在某个人的 notebook 里、或者某个群的聊天记录里。半年后，`1568` 这个数是怎么来的没人知道了。**然后就没人敢改它**——不是因为它对，是因为没人知道动了会怎样。这是我见过最常见的一种技术债，而且它不报警。

所以能搬走的一条在最下面这个绿框：**任何魔数旁边写清三件事——对照组是谁、指标是什么、什么时候跑的。** 最后这句我很喜欢，念一下：**它不如测试严格，但比测试耐放。** 测试会因为环境变了跑不起来、会被人 skip 掉；注释不会，注释跟着代码走，只要那行参数还在，那段注释就还在。

## P18 · hashline 的防线是 seenLines，不是那 4 个 hex

**一句话主旨**：真正的约束是"你只能改你亲眼看过的行"；4-hex 指纹只有 16 bit、必然碰撞，作者自己说它只是索引，不是身份。

**提词**：
- 先念常见讲法：靠 4 位内容指纹防改错文件
- 上一讲也是这么讲的 [重]
- 实情：指纹只是索引，真防线是 seenLines
- 哪怕指纹对得上，没看过的行照样改不了 [慢]
- 流程图从上往下：edit 带 tag 进来 → hash 对得上 / 对不上
- 左路正常，但还有一道闸门：锚点行都在 seenLines 里吗
- 右路漂移三级：头尾插入放行 → Recovery 重映射 → MismatchError
- Recovery 铁律：所有锚点必须同一偏移量，否则放弃 —— fails closed
- 两种报错文案别混：编造 tag vs 文件漂移
- 右栏：为什么敢用 16 bit —— 身份是 SnapshotStore 里的全文
- 去重条件 hash 相等 **且** 全文相等，issue #4075
- 防绕过：40 行 / 512 列，截断就一行都不并入 [重]
- 收尾：指纹答「是不是同一份」，seenLines 答「你有没有资格改」 [停]

**怎么讲**：
最后一页，换一件事讲：文件编辑的安全。（停一拍）老规矩，先念左上角常见讲法：**"靠 4 位内容指纹防止改错文件"**——读文件的时候给它一个 tag，编辑的时候带上 tag，对不上就拒改。**上一讲我就是这么讲的**，这是本讲第二次、也是最后一次认错。这个说法不算错，但它把重点说反了。右边实情：**指纹只是索引，真防线是 `seenLines`**。而且这句话要说得更狠一点——**哪怕指纹对得上，你没看过的行照样改不了。**

跟着这张流程图走一遍。最上面：一个 edit 请求进来，带着 `[src/foo.ts#1A2B]` 这样一个 section header，`1A2B` 就是那 4 位 hex。第一个分叉：全文 hash 对不对得上。先走左边这条顺路——对上了，文件没变。按常见讲法，到这儿就该放行了对吧？**不放。** 看这个紫框，还有一道闸门：**锚点行，是不是每一行都在 `seenLines` 里？** `seenLines` 是什么？是 `read` 和 `search` **实际显示给模型看过**的行号集合，1-indexed。注意这里有个细节：范围读、折叠式的结构摘要，只会填一个**稀疏集合**——你 read 了 100 到 120 行，那 seenLines 里就只有这 21 个数，别的行你没见过。过了这道闸门才 applyEdits；有没看过的行，直接拒绝，而且**把那些行的真实内容贴回去给模型**。

它防的是什么？看右下角这个框，注释原话：`"editing lines the model has not seen is the off-by-memory mistake that mangles files"`——**模型凭记忆去改它没看过的行，这是把文件搅烂的那类错误**。这句话我觉得说得特别准。模型对一个文件"大概长什么样"是有先验的，它见过一万个类似的文件，所以它很敢下手。`seenLines` 干的事就是把这个先验掐掉：你**这一次**看到了什么，你才能改什么。

再走右边这条路，hash 对不上，文件漂移了。这里是个三级台阶，不是一刀切拒绝。① 先问：这次编辑是不是只在头部或尾部插入？如果是，那它没有锚点作用域，插在哪儿都不会改错地方，**带个警告放行**——这是个很务实的口子。② 不是的话进 `Recovery`，三方重映射：拿旧文本和新文本做 diff，只收录**未改动**的行段建映射表，锚点必须落在这些未改动的行上，锚点上下相邻的非锚点行也必须同步位移；然后是这条铁律——**所有锚点必须是同一个偏移量，否则整个放弃**。文件头写的原则叫 `fails closed`：**只要目标变了或者变得有歧义，就失败**，宁可不修。③ 还不行才抛 `MismatchError`。这里有个细节我很喜欢：报错文案分两种，**别混**。如果这个 tag 根本不是本会话产生的——查快照库查不到——报错是"你把 tag 编出来了，或者用了上一次会话的 tag，永远不要发明 tag"；如果 tag 认识但文件变了，报错是"文件在你读完之后被改了，去抄上一次响应里的新 header，或者重读"。**这是两个完全不同的失败模式，给模型两句完全不同的话。** 这个区分很值钱——大部分工具报错只有一句"hash mismatch"，模型看了不知道该干嘛。

（停一拍）现在看右边这一栏，回答那个最容易被问的问题：**为什么敢只用 16 bit？** 上面这个代码框：先归一化——每行去掉尾部空白、吃掉 CR，这样 CRLF 和显示时被裁掉的尾空白不会让 tag 失效；然后 `xxHash32` 取低 16 位，输出 4 个大写 hex。取值空间只有 **65,536**。这个空间小到什么程度？一个会话里读几十上百个文件版本，撞上的概率是完全不能忽略的。所以看下面这个框：**会碰撞，但无所谓。** 因为 tag 只负责一件事——**快速认出"这次读的是哪一版"**；认出来之后，真正拿去比对的是快照里**逐字保存的全文**。注释原话：`"the tag is only a fast index, never the identity"`。回到左边这个紫框验证一下：`SnapshotStore` 的去重条件写死成 `v.hash === hash && v.text === fullText`——**hash 相等还不够，全文也得相等才算同一版**。注释还点名了 issue #4075：如果只按 tag 合并，两段不同的内容撞了同一个 tag，就会把 B 的 `seenLines` 挂到 A 的文本上，patcher 从此开始误判。这是个真实踩过的坑。

最后这个红框是我最想让大家记住的一个设计细节，**防绕过**。刚才说拒绝的时候会把没看过的行的真实内容贴回去，让模型一次就能自纠——这很贴心。但这里藏着一个漏洞：如果贴回去的行自动就算"看过了"，那模型只要**反复触发拒绝**，就能一点点把整个文件"看"完，盲改照样塞进去。所以上限卡死：**一次最多揭示 40 行、每行最多 512 列**。而且——**只有当揭示是完整覆盖的时候，这些行才并入 `seenLines`；一旦碰到上限被截断，就一行都不并入**。一行都不。为什么？因为如果截断了还并入一部分，模型就可以**把请求切成 40 行以下的小块反复重试**，把盲改硬塞进去。（停一拍）我觉得这个细节能说明作者是真的在跟模型的行为对抗，而不是在写一个理想化的校验器。他假设了模型会尝试绕过——不是恶意，是模型天然会"再试一次换个写法"。

收尾看绿框这一句，这也是整章的收尾：**指纹回答"是不是同一份"，`seenLines` 回答"你有没有资格改"。** 这两个问题不是一个问题。而这，就是我在章扉页说的那句话——**这一章的两个设计都不聪明，只是把"模型可能骗你"写成了代码约束**。snapcompact 不信模型的摘要，hashline 不信模型的记忆。都不是什么高级算法，就是在关键位置上装了一道不讲情面的闸门。

**别漏了说**：
- **必须提上一讲讲错过**，这是本讲第二次也是最后一次认错，和第 3 页的更正卡呼应。
- "哪怕指纹对得上，没看过的行照样改不了"这句要说出口——这一句就把常见讲法和实情的差别讲完了。
- 16 bit 会碰撞这件事要主动挑明，并立刻给出为什么无所谓（身份是全文快照）。不主动说，听众会自己在心里给这个设计判死刑。
- **防绕过那 40 行 / 512 列、以及"截断就一行都不并入"必须讲**，这是全页最能体现设计水平的地方，也是最容易被略过的地方。
- 两种 MismatchError 文案的区分要说，别只说"会报错"。
- `fails closed` 这个词值得点名，它是 Recovery 的设计哲学，一句话能带走。

**可能被问**：
- Q：`seenLines` 会不会太严了？模型改个大文件得先全读一遍？
  A：不会全读，但确实要读到你要改的那一段。仓库里有一份真实会话统计：**一半的编辑只有一个 hunk，中位数只改 5 行**。所以绝大多数情况下这个约束根本不碰边。这个数据也正好解释了为什么值得为"改错行"做这么重的防护——改动本身很小，改错的代价很大。
- Q：这套东西实际效果怎么样？有数据吗？
  A：有一份**真入库**的 benchmark，`packages/typescript-edit-benchmark/all_models_results.json`，是编辑维度不是压缩维度。haiku-4.5 单次编辑成功率 88.5%，minimax-m2.5 88.2%，deepseek-v3.2 是 100% 但只编辑了 13 次、任务成功率只有 55%——它大量在空转。这份数据我没跑，是仓库里带的。
- Q：4 位 hex 换成 8 位不就没这问题了吗？
  A：可以，但没必要——因为它本来就不承担安全责任。加长它只会让 tag 更难被模型正确复制，而正确性由全文快照保证。这是个"故意做短"的选择。
- Q：如果文件是被外部（比如另一个终端）改的，会怎样？
  A：走 Recovery 那条路，成功的话会带一条专门的警告文案区分成因——外部改的、本会话前一次编辑改的、只是行号位移，三种警告文案不一样。
- Q：`seenLines` 存在哪儿？会不会很占内存？
  A：在 `SnapshotStore` 里，有边界：30 个路径 LRU、每个路径最多 4 个版本、总计 64 MiB，单文件超过 4 MB 直接不做快照。页脚小字有。
- Q：这套设计能直接搬到我们自己的编辑工具上吗？
  A：`seenLines` 这个思路能搬，而且成本很低——你只要记住 read 返回过哪些行号就行。指纹那套要不要搬看你，但记住它不是防线。
