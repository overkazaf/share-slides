## P20 · 靠猜必错：543 个同名模型里，376 个价格对不上

**一句话主旨**：同一个模型名在不同网关下价格、窗口、id 全都不一样，靠猜必然错，所以模型元数据得当成软件制品来造。

**提词**：
- 63 家 provider / 4,106 条模型 / 2.1 MB 提交进仓库
- 543 个同名 → 376 个价格不一致（69%）、254 个窗口不一致（47%）[重]
- Kimi K2.7 Code：18 条 / 18 家 / 4 种 wire id
- Claude Sonnet 4.5：18 条 / 15 家 / 8 种 wire id
- maxTokens 8192 ↔ 64000，差 8 倍 [慢]
- **wire id 那一排念的是 Sonnet 5，不是 4.5**，别串
- 猜小 → 白白截断；猜大 → 上游 400
- 右边：三路合流，`bun run gen:models`，禁止手改
- 对比锚点：pi 当构建产物 gitignore；omp 当源代码提交 [停]
- 56% 条目来自聚合网关——这才是必须建库的理由

**怎么讲**：
上一页我说"每条假设都得有人替你验过"，这一页就是那句话的证据。（停一拍）先看标题下这行：omp 的 `packages/catalog` 里内置了 **63 家 provider、4,106 条模型记录**，一个 2.1 MB 的 JSON，**直接提交进仓库**。听到这儿很多人的第一反应是"这不就是一张表吗，抄一份不就完了"——这一页就是要打掉这个反应。看左上角三个方块：4,106 条记录去重之后有 2,275 个展示名，其中 **543 个名字被两条以上记录覆盖**，也就是同一个模型名，有两家以上在提供。然后是两个玫红色的数字：这 543 个里面，**376 个各家标出来的输入价不一致，占 69%**；**254 个各家标的上下文窗口不一致，占 47%**。请注意这不是"差一点点"，我们往下看两个具体样本。（停一拍）第一个是 `Kimi K2.7 Code`，18 条记录、18 家 provider。输入价这一行，去重之后的取值集合是——0、0.71、0.73、0.75、0.95。有人标 0，那是订阅制或者促销条目。contextWindow 四个值：20 万、25.6 万、26.2 万、262144。maxTokens 六个值，从 32000 一路到 262144。第二个样本是 `Claude Sonnet 4.5`，**18 条记录、15 家 provider**。输入价 0 / 2.992 / 3 / 3.75。contextWindow 三个值并存：198000、200000、1000000。maxTokens 这一行请大家盯一下：**8192、32000、64000——头尾差 8 倍**。（停一拍）差 8 倍意味着什么？看下面这个玫红色的结论框：**猜错的代价不是"差一点"**。maxTokens 你猜小了，模型的输出被你自己白白截断，用户看到半截答案；你猜大了，上游直接给你一个 400，整轮请求作废。contextWindow 三个值并存，你的压缩触发点必然算错——按 100 万算，实际是 20 万，那就是爆窗；按 20 万算，实际是 100 万，那就是每隔一会儿白压缩一次，压缩本身是最贵的操作之一。再看中间这一排四个盒子，讲的是 id 的分裂——这里我要提醒自己一句，**这一排的例子是 Claude Sonnet 5，不是上面那个 4.5**，别念串了。同一个模型落到线上的 wire id：first-party 是 `claude-sonnet-5`，聚合网关加个前缀变成 `anthropic/claude-sonnet-5`，Bedrock 把斜杠换成点变成 `anthropic.claude-sonnet-5`，Vertex 再加个后缀 `claude-sonnet-5@default`。四种写法。而刚才那个 Sonnet 4.5，跨 15 家一共 **8 种** wire id。（停一拍）现在看右边这一栏，回答"那这份数据从哪来"。三路合流，一条命令 `bun run gen:models`，README 第一句就是 **Never edit src/models.json by hand**——它是产物，不是一张能手工维护的表。第一路是 stencil.so 镜像，也就是 models.dev 裁完字段再 zstd 预压缩的版本，93 KB 对 3.3 MB 的 raw；第二路是 40 家 provider 的实时 `/v1/models` 抓取，67 条 descriptor 里有 40 条带 catalogDiscovery，生成的时候拿真实凭据去拉；第三路是手写的 curated 种子，理由写在注释里——**不想让自己的库被 models.dev 的更新节奏卡住**，官方刚放出来的新模型先进库。（停一拍）下面这个对比锚点是我最想让大家看的一格，因为它是**同一份数据的两种定位**。**pi 把它当构建产物**：`.gitignore` 掉 `providers/data/`，构建的时候现拉 models.dev。**omp 把它当源代码**：4,106 条快照提交进仓库，可以 diff、可以 review、离线可用；代价是仓库多 2.1 MB，而且得定期来一个 `chore: bump models` 的提交。这两种做法没有对错，它们对应两种不同的信念——你信不信"模型元数据是你产品行为的一部分"。如果信，那它就该像代码一样被 review；如果不信，那它就是个缓存。最后看右下角这个玫红框，是"为什么非建不可"的最硬那条证据：**4,106 条里有 56% 来自聚合网关**——nanogpt 810 条、kilo 498、openrouter 411，前五家就占了 2,302 条。而恰恰是网关，才是 id 最乱、价格最乱的地方。相比之下 anthropic 官方只有 26 条、openai 51 条。**你的数据里绝大多数条目来自最不可信的来源，这就是这个库必须存在的全部理由。**

**别漏了说**：
- 中间那排 wire id 用的是 **Claude Sonnet 5**，而上面样本 B 是 **Claude Sonnet 4.5**，页面上是两个不同的模型。念的时候一定要交代一句"这一排换了个例子"，否则听众会以为 4.5 有四种 id（实际是八种）。
- 543 这个数和 research 里另一处的 527 口径不同：**543 是"被 ≥2 条记录覆盖的名字"，527 是"被 ≥2 家 provider 提供的名字"**。同一家可以有多条记录（比如不同 effort 档），所以 543 更大。被问到要能答上。
- "猜小截断 / 猜大 400"必须说出口，这是把统计数字翻译成工程后果的唯一一句。
- pi vs omp 那格要**对称地讲完代价**，不能只夸 omp。2.1 MB 进仓库 + 定期 bump 是真代价。
- 0 这个价格值要解释一句（订阅制/促销条目），否则听众会以为是数据错误。

**可能被问**：
- Q：这些数据是 omp 自己测的吗？会不会它自己也是错的？
  A：不是它测的，是它从三个上游合流的，所以它同样可能错。但区别在于：错了之后你能在 git 里看到是哪一次 bump 引入的，能 diff、能回滚。这不是"保证正确"，是"把错误变得可追溯"。
- Q：4,106 条会不会大部分是垃圾条目？
  A：坦白说有相当一部分是重复和别名，这也是它为什么要做 canonical 归并和 effort 变体折叠。变体折叠有一条自我约束我很欣赏——"价格不同的孪生条目是不同的 SKU，必须分开存，**这样计费归因永远不会说谎**"。
- Q：我自己做 agent，需要建这么大的库吗？
  A：不需要。但你至少需要给你实际会用到的那几个模型，把 contextWindow 和 maxTokens **写死在代码里并且标上来源日期**，而不是从模型名去推。这页真正的可迁移结论就这一条。
- Q：那 543 里剩下的 167 个价格一致的，是不是说明大部分还好？
  A：反过来看更准：69% 不一致。而且你事先不知道你要用的那个落在哪一边。
- Q：为什么 63 家和 67 条 descriptor 对不上？
  A：有 4 类本机自托管的 provider（ollama / vllm / lm-studio / litellm）被排除了，理由写在生成脚本注释里——打包它们会把 `http://localhost:4000/v1` 这种机器相关的端点泄漏进提交的快照。另有两家已退役。

## P21 · dialect 兜的不是语法，是 native 通道不会出现的失败模式

**一句话主旨**：把工具调用从结构化字段挪进正文，你就得自己收拾三种 native 通道里根本不存在的烂摊子。

**提词**：
- 11 种方言，显式 `PI_DIALECT` opt-in，不设就走 native [重]
- 这一页的钥匙：**native 通道里根本不存在的三种失败模式**
- A 伪造工具结果：登记「结果开启 token」，撞见即 abort 上游止损
- B GLM 把 `</arg_value>` 写成 `</arg_key>` → 吞掉后续全部参数
- B 难在流式：三态 none / partial / heal，partial 要 hold 住
- C 双通道抢答：Gemini via OpenRouter，tools 空了照样吐 functionCall
- C 对策：先出真调用的通道锁死，另一条整轮丢弃 [慢]
- 右边：opt-in 之后请求侧三件事一起做
- 对比锚点：pi 的 packages/ai grep dialect 零命中
- 它不是「更好的 tool calling」，是兜底通道 [停]
- 被删的 pi 自研方言曾宣称省 46% token——没留住

**怎么讲**：
上一页讲数据，这一页讲协议。（停一拍）先把定位说清楚，看标题下这行小字：**11 种方言，显式 `PI_DIALECT` opt-in，你不设它就走 native**。所以它不是默认路径，是一条备用车道。什么时候走这条道？三种情况：上游根本不支持 function calling，比如你自己跑的 llama.cpp、vLLM，或者某些便宜网关；上游说支持但解析做坏了；或者你就是想把 tool 描述的裁剪、示例的渲染、token 预算全部拿回自己手里。仓库自己在 TUI 的 tips 里有一句大白话："没有 native tool calling？推理服务把解析搞砸了？`PI_DIALECT=glm|kimi|anthropic` 帮你在本地滚一遍。"（停一拍）现在，这一页真正的钥匙在最上面那行小字，我念一遍：**这三种失败模式，native 通道里根本不存在**。大多数人讲 in-band tool calling，讲的是"用 XML 还是 JSON、哪种更省 token"——那是语法问题。这一页说的是：**当你把工具调用从结构化字段挪进正文，你就把一整类新的失败模式请进了门**，而这三种失败模式，恰恰是 native 通道白送给你的保护。我们一个一个看。

A，**模型伪造工具执行结果**，英文叫 fabrication。在 native 通道里这事不可能发生，因为工具的返回值是 runtime 注入进对话的，模型压根没有机会编。但在 in-band 通道里，模型吐完调用之后手一滑，把"工具返回了什么"也一起编出来了——它编了一段 `<tool_response>` 里面写着"测试全部通过"，然后基于这个幻觉继续往下推理。你不管它，它能编一整篇。omp 的对策看这行：**每种方言登记一组"工具结果开启 token"**，下面这排就是——glm 是 `<tool_response>`，kimi 是 `<|im_system|>`，anthropic 是 `<function_results>`，gemini 是 ` ```tool_outputs `，deepseek 是那个全角的 `<｜tool▁outputs▁begin｜>`。流式扫描器一旦在文本里撞见这些 token，立刻停。而且有两种模式：默认的 abort 模式**直接掐断上游请求**，注释原话是"so the provider stops spending tokens on the hallucinated continuation"——**这是一条止损，不是一条正确性措施**。你已经知道这轮废了，那就别再为幻觉付钱了。另一种 discard 模式是把流排干但丢弃边界之后的一切。还有一个细节值得一提：这些 token 可能被 SSE 的 chunk 边界切成两半，所以扫描器保留了一个重叠窗口，避免漏检。

B，**GLM 把 `</arg_value>` 写成 `</arg_key>`**。这个更具体。native 通道里参数的闭合是结构化字段保证的，压根不存在"标签写错"这回事。in-band 里，模型一个字符打错，后果是什么？看这句——**后续所有参数被吞进同一个字段**，一直吞到流里下一个 `</arg_value>` 为止。也就是说你以为你拿到了五个参数，实际上你拿到一个巨大的字符串，里面塞着另外四个。对策是流式的"愈合扫描"：识别两种修复签名，一种是闭错了（`</arg_key>` 后面紧跟着 `<arg_key>` 或者 `</tool_call>`），一种是压根忘了闭。（停一拍）真正难的地方在下面这行：**难在流式**。签名可能只写到一半，chunk 就断了——你看到一个 `</arg_k`，你不知道它是要闭错还是正常的 key 结束。所以这个函数返回**三态**：none、partial、heal。partial 的时候调用方必须 **hold 住这一段，不能往下游 emit**，等下一个 chunk 来了再判。这三态设计是整页最见功力的一处。另外还有防误伤的边界：标签之间最多容忍 32 个空白，key 最长 128 字符，超了就放弃愈合——因为你不能为了修 bug 把用户正常的文本改坏。他们甚至专门写了一条反向保护测试，叫 "leaves values containing tag-like prose intact"，就是说**参数值里本来就写着像标签的散文时，不许动它**。

C，**native 和 in-band 双通道同时开火**。这条最荒诞。omp 已经把请求里的 `tools` 字段置成 undefined 了，按理说上游不可能返回 native 的工具调用。但注释里点名了一个真实案例：**Gemini 经由 OpenRouter，即使你没发 tools，它照样返回 functionCall parts**。那你转发不转发？不转发，这一轮就没有任何可执行的内容，agent loop 拿到一条只有 reasoning 的消息，**会无限重试下去**。对策是：**哪条通道先产出"真"调用，就锁死哪条，另一条整轮全部丢弃**。还要处理"ghost"——一个没有 name 的空 native 块不算数，不锁通道。测试名字就叫 "drops a nameless native ghost but keeps the real native call"。（停一拍）

右边这一栏收尾。上面是 11 种方言的清单：anthropic、glm、gemini、gemma、kimi、qwen3、deepseek、minimax、harmony 对 gpt-oss、hermes 需要显式指定、最后 `xml` 是 FALLBACK，遇到不认识的模型就用它。中间这格讲 opt-in 之后请求侧要**三件事一起做**：系统提示里追加工具清单加方言语法说明、历史里的调用和结果按方言回写成文本、然后 tools 置 undefined、toolChoice 清空、描述裁剪关掉。少做一件就会前后不一致。再往下是对比锚点：**pi 完全信任 native tool calling**，它的 `packages/ai` 里 grep dialect 和 inband，**零命中**。这条柱子对比是 21,429 行对 99,265 行——四倍多，dialect 只是其中一块。最后这个琥珀框是这一页的落点，我照念：**它不是"更好的 tool calling"，而是"上游把 native tool calling 做坏了"时的兜底通道，所以它必须处理 native 通道里不会出现的失败模式。** 底下还有一行很有意思的脚注：pi 曾经有一套自研方言，宣称比 legacy 格式省 46% 的 token，最后被删掉了。**省 token 没能留住它**——我的理解是，模型没见过你自研的格式，你省的那点 token 换来的是更高的出错率。这条因果是我的推断，不是仓库明说的。

**别漏了说**：
- 开场必须先说"显式 opt-in，不设就走 native"，否则听众会以为 omp 默认不用 native tool calling，那是完全错误的印象。
- "native 通道里根本不存在"这句话在三个失败模式里各说一遍，这是本页的结构，不能省。
- fabrication 的 abort 是**止损**不是纠错——这个区分要说出来，否则听众会问"掐断了不就丢了这轮吗"。答案是这轮本来就已经废了。
- B 的"三态 + partial 要 hold"是整页技术含量最高的一处，别赶时间跳过。
- 46% token 那条要**明确标为推断**，不要说成仓库结论。
- 如果时间紧，C 可以压到 30 秒，A 和 B 不能压。

**可能被问**：
- Q：那我到底该不该用 in-band？
  A：默认不该。这一页的完整读法是"能用 native 就用 native"，dialect 是当你没得选的时候的逃生舱。omp 自己也是这么设计的——你得显式设环境变量它才走。
- Q：伪造工具结果这事，native 通道真的完全不会发生吗？
  A：结果注入这条路上不会。但模型在自己的文本里"假装"某个工具跑过了、编造一段输出当叙述，这在任何通道里都可能发生。这一页说的是**结构化的伪造**——模型吐出一个语法上合法的结果块，被你的解析器当真。这个只在 in-band 里有。
- Q：11 种方言要维护，成本不高吗？
  A：高。而且这个数字是会变的——旧的 pi 方言被删了，minimax 是新加的。这就是"兜底通道"的代价：上游每出一个新脾气你就得加一条。所以我才强调它是 opt-in 而不是主路。
- Q：GLM 那个 bug 现在修了吗？
  A：不知道。仓库的 CHANGELOG 记录说这个症状"in-band 和 native 都中招"，说明问题出在网关那一层而不只是 in-band。修没修我没验证。
- Q：愈合扫描会不会把用户本来就想传的 `</arg_key>` 改掉？
  A：这正是那条反向保护测试在防的事，加上 32 空白 / 128 字符两条边界。但严格说，任何启发式愈合都存在误伤的可能，他们的做法是把误伤面缩到最小，不是消除。

## P23 · 4 万行 shell 里，69% 不是 shell

**一句话主旨**：pi-shell 最大的一块是把命令输出压小的 minimizer，它省的是 token 和注意力，不是 CPU。

**提词**：

- 单文件前七名全是"针对某个工具"的过滤器：jvm 3,117、git 2,842、listing 2,032…
- 另有 67 个 TOML 声明式管道，build.rs 构建期拼接
- 常见讲法：「自己写了个 shell，为了性能」—— **两句都错**

- 那 2.8 万行是让 mvn test 的 3000 行变 30 行 [慢]

**怎么讲**：
这是最大的一个 crate，`crates/pi-shell/src`，实测 41,207 行，含内联测试。（停一拍）先看这条横条——它被切成了很不对称的两块。橙色那块，**28,266 行，68.6%，写的是 minimizer**，也就是按工具写的输出压缩器。右边灰色那块 12,789 行，31.4%，**shell 宿主的真身在这里**。也就是说，你以为的"他们写了个四万行的 shell"，其实那个 shell 只有一万二，剩下三分之二在干一件跟执行完全无关的事。下面这个排行榜可以佐证：单文件前七名，**全是针对某个具体工具的过滤器**——`filters/jvm.rs` 3,117 行，专门对付 Maven 和 Gradle 的输出；`filters/git.rs` 2,842 行；`filters/listing.rs` 2,032 行，折叠 ls、tree、find 的输出；docker 1,702；cloud 1,676，管 aws、curl、psql；pkg 1,215，管 npm、pnpm、yarn；cargo 1,001。这七个加起来就一万三了。另外还有 67 个 TOML 写的声明式管道，构建期由 build.rs 拼进去。而且所有过滤器都跑在 `catch_unwind` 下面——**写坏一个过滤器，不应该炸掉整条命令**。（停一拍）

现在看下面这两个框，这是本页的核心，也是本篇一直在用的那个格式：先写常见讲法，再写实情。**常见讲法**：「他们自己写了个 shell，四万行 Rust，为了性能。」于是这一页就被归进了"Rust 性能优化"。**两句都错。** 先看第一句错在哪：橙色框里第一行——**shell 解析器直接用的是 crates.io 上的 `brush-parser 0.3`，连 vendor 都没做，就是一行依赖声明**。原始的命令文本整段交给 brush，解析和词展开 100% 不是自研。它自研的只有三样：60 个进程内 builtin、进程树和取消语义、还有输出压缩。（停一拍）所以"为什么要自己实现一个 shell"这个问题，正确的答案是——**它没有实现 shell，它实现了一个 shell 的宿主**。这两件事的工作量差着一个数量级。第二句错在哪？看这行加白的字：**那 2.8 万行是让 `mvn test` 的 3000 行输出，变成 30 行再进 context window。** 它省的是 token，是模型的注意力，**不是 CPU**。你把它当性能优化讲，你就讲错了这个仓库里最值钱的一个设计。而且下面这行小字是个很强的旁证：**pi-shell 没有 benches 目录、没有 criterion、没有任何 benchmark**。这个 crate 里所有的时间常数——250 毫秒、2 秒、75 毫秒、150 毫秒——**全都是设计值，不是测量值**。一个真的以性能为目标的 crate，不会长这样。

（停一拍）右边这一栏讲动机的另一半：**为什么不 fork/exec**。上面这格是上游 pi 的做法：第一次要 grep，先看本地 bin 目录里有没有 ripgrep；没有就去 GitHub Releases 下载预编译二进制；拿到之后，每次工具调用 spawn 一个子进程。玫红那行是代价：**离线、内网、企业代理环境，这一步直接失败**。下面这格是 omp：grep、diff、jq 变成 `.node` 里的一次函数调用；目录扫描的结果进 `fs_cache`，**跨调用复用**。这第二条我要多说一句——加白那行写着"在 fork/exec 模型下，架构上不可能"。为什么？因为子进程模式下，每次 `rg` 跑完，它遍历目录的成果随着进程退出一起蒸发了，下一次从零再来。进程内化之后，这份成果可以留下来给 glob、给 fuzzy find、给 AST 扫描共用。**这才是进程内化真正的复利来源。** 再往下是顺带的收益：删掉了 6 个 npm 运行时依赖——glob、ignore、minimatch、cross-spawn、diff、highlight.js。其中 diff 那个有意思，是**逐位兼容重写**的，模块注释说它产出的字节和 jsdiff v9 一模一样，Myers 算法的核心是照着 jsdiff 的 `base.ts` 移植的。最后这个落点框我照念：把 rg 和 bash 从"另一个进程"变成"本进程的函数"，**省下的第一笔是外部依赖，第二笔是 token——CPU 排第三**。这个排序就是这一页全部的意思。

**别漏了说**：
- "解析器是 crates.io 的 brush-parser，连 vendor 都没做"必须说出口，这是纠偏最有力的一句。
- "它实现的是 shell 的宿主，不是 shell"——这句话要慢，是本页的题眼。
- "没有 benches、时间常数全是设计值"是佐证"这不是性能项目"的最硬证据，别漏。
- 3000 行变 30 行这个例子要具体说 `mvn test`，抽象说"压缩输出"没有画面感。
- fs_cache 跨调用复用"架构上不可能"要解释清楚为什么（进程退出成果蒸发），否则听众只当是一句夸张。

**可能被问**：

- Q：为什么不用模型自己去总结输出？

- Q：67 个 TOML 管道和 Rust 过滤器怎么分工？

- Q：那 60 个 builtin 都是自己写的吗？
  A：不是。44 个是 vendored 的 uutils，4 个是自研重写（grep、rg、diff、jq），6 个 moreutils，6 个是 pi 独有的（fd、which、cmp、sleep、timeout、nohup）。而且 `exec` 和 `suspend` 被显式禁用了，因为它们能让命令逃出这个内嵌会话。

## P24 · 一行 assert 讲清整件事

**一句话主旨**：进程边界一消失，POSIX 白送的 fd 表、cwd、信号三样保证同时失效，446 行 `pi-uutils-ctx` 就是补这三个洞的全部代码。

**提词**：
- `shell.rs:2598` 一行：`assert!(!Path::new("a/b/c").exists(), "mkdir leaked into process cwd")`
- 它防的是：builtin 按进程全局 cwd 解析相对路径 → 目录落到宿主当前目录
- 同一句话可以换成 fd 或信号再说两遍 [重]
- ① fd 表：函数没法 dup2(1)，重定向拿不到 → 从 brush 取真 fd 装进 thread-local，一次调用一条线程
- ② cwd：全 crate `set_current_dir` 命中数为 0；cwd 挂在 shell 实例上，路径参数逐个过 resolve
- ③ 信号：你没法给函数发 SIGKILL → 原子标志位 + 合成 EOF + 200ms 分片 poll
- 补三个洞的全部代码：pi-uutils-ctx，**446 行，全仓最小的 crate** [慢]
- 右边 Ctx 结构体：三行 stdio + cwd + cancel，**注意是节选**
- 高潮：`if !ctx::is_active() { 丢弃 }` —— 不是落到宿主 fd 1/2
- 因为宿主的 fd 1/2 是 TUI 的画布，泄漏一个字节整屏就花 [停]
- 第四样：panic 隔离，真实事故是 uu-tail 对 BrokenPipe 做了 unwrap

**怎么讲**：
这一页我只有一个论点，而且它可以被一行代码讲完。（停一拍）看左上角这个框，这是回归测试里的一行，位置是 `crates/pi-shell/src/shell.rs` 第 2598 行。上面一行注释我先说：**mkdir 走的是进程内 builtin，不是子进程**。然后跑一条命令 `mkdir -p a/b/c`，工作目录指定成一个临时目录。接着是这个断言——`assert!` 括号里是 `!Path::new("a/b/c").exists()`，**注意那个感叹号，它断言的是"不存在"**。失败信息写着：`"mkdir leaked into process cwd"`——mkdir 泄漏到进程的当前目录去了。（停一拍）这一行在防什么？看下面这句：如果 builtin 按**进程全局的 cwd** 去解析相对路径，那 `a/b/c` 这个目录就不会落在你指定的临时目录里，而会落在宿主进程的当前目录下——也就是用户正在工作的那个仓库根目录。你让 agent 在一个隔离目录里建目录，结果它在你的项目根目录里拉了一坨。**而且这不是 bug，这是子进程模型给你白送的东西，在你换成函数调用的那一刻，静悄悄地不见了。** 下面这行是我最想让大家记住的：**同一句话，可以换成 fd 说一遍，换成信号再说一遍——进程边界一没，三样保证一起没。**

（停一拍）中间这三格就是那三样。**第一样，fd 表**。子进程模型里，重定向是怎么实现的？父进程 `dup2` 一下，子进程什么都不用管，它写 fd 1 就自动进了文件。函数调用没法 dup2，你写 `println!` 它就是往进程的 stdout 去了，重定向根本拿不到。omp 的做法：**在任何 await 之前**，从 brush 的执行上下文里把这条命令真正的 fd 取出来，装进 thread-local；而且**一次调用配一条专属线程**，这是刻意的——因为管道的并发各段不能互相串流。**第二样，cwd**。全进程只有一个当前目录，但一个 agent 可以同时开很多个 shell 会话。这里有一个数字我很喜欢：**整个 crate 里 `set_current_dir` 的命中数是 0**——它从来不改进程的 cwd。cwd 挂在每个 shell 实例上，然后**每一个路径参数都逐个过一遍 `ctx::resolve`**。注意这句话的含义：vendored 进来的那 44 个 uutils 工具是被**打了补丁**的，每次碰文件系统之前都要先走这个解析。**第三样，信号**。这条最有意思——**你没法给一个函数发 SIGKILL**。子进程超时了你 kill 掉就完事了，函数跑在你自己的线程里，你杀了它整个 agent 也没了。所以取消从抢占式改成了**协作式**：共享一个原子标志位；stdin 那边读到取消就返回一个**合成的 EOF**，让工具自然地退栈——这个设计很聪明，因为绝大多数命令行工具遇到 EOF 都会优雅退出；实在卡在管道上的，unix 下用 `libc::poll` **200 毫秒一片**地循环重查标志位。（停一拍）下面这个橙色框：**补这三个洞的全部代码，叫 `pi-uutils-ctx`，446 行**。它是全仓库最小的一个 crate，但它是那 60 个进程内 builtin 能够成立的前提。八万四千行 Rust 里，最关键的四百四十六行。

（停一拍）看右边。上面是 `Ctx` 这个结构体，**我先声明一句，这是节选**——原定义里还有 `stdin_fd`、`stdin_is_search_input`、`exit_code` 三个字段，我为了让它和左边那三样对上，删掉了。剩下的这几行请对着左边看：`stdout`、`stderr`、`stdin` 三行——**这就是 fd 表**；`cwd: PathBuf`——**这就是相对路径解析**；`cancel: Arc<AtomicBool>`——**这就是信号**。`env` 是附赠的第四样，因为 shell 里 export 的变量在宿主进程的环境里根本不存在，也得快照进来。**一个结构体，恰好就是进程白送你的那几样东西的清单。**

（停一拍）下面这个玫红框是这一页的高潮，我讲慢一点。问题是这样的：如果某段代码跑起来了，但根本没装上下文，怎么办？直觉的做法是"那就退回默认行为，写到真正的 stdout 去"——毕竟总比丢了强。**他们选的是丢弃。** 看这行代码：`if !ctx::is_active() { /* 丢弃 */ }`。写入被丢弃，**而不是落到宿主进程真实的 fd 1 和 2**。为什么？因为**宿主的 fd 1 和 2 是 TUI 的画布**。omp 是个全屏终端界面，它自己在精确地控制每一个字符的位置。这时候有一个 vendored 的工具因为没装上下文，往 fd 2 打了一行"warning: something"——**整屏就花了**，光标位置全乱，用户看到的是一坨乱码。所以这里的 fail-safe 方向是反直觉的：**宁可丢数据，不可污染画布**。我觉得这是整个 crate 里最能体现"他们真的在终端里用过这东西"的一个设计——你不被这个 bug 咬过一次，你不会把默认行为设成丢弃。

最后这一格是顺手补回的第四样，**panic 隔离**。子进程里工具 panic 了，内核给你兜着，你只看到一个非零退出码。进程内化之后，一个 panic 直接掀桌子。而且注释里点名了一个真实事故：**vendored 的 `uu-tail` 对 BrokenPipe 做了 unwrap**——你 `tail -f | head -1`，head 一退出管道就断了，tail 那边 unwrap 直接 panic。现在 panic 被 `catch_unwind` 接住，变成 exit 1 加一行 internal error。底下这行是这一页的总结：**子进程模型里内核替你做的隔离，现在每一样都要自己写。**

**别漏了说**：
- assert 里那个**感叹号**必须点出来，否则听众会以为断言的是"存在"，整个逻辑反过来。
- 右边 `Ctx` **必须声明是节选**，页面上有小字但太小了，要口头说一遍。原定义另有 stdin_fd / stdin_is_search_input / exit_code。
- "446 行是全仓最小的 crate，却是 60 个 builtin 的前提"——这个对比要说。
- fail-safe 那段是本页高潮，讲慢，把"TUI 的画布"这个画面感建立起来。别只念代码。
- `set_current_dir` 命中数为 0 这个数字很有说服力，别跳过。
- 这一页不要展开取消的四层机制（token / 桥到 brush / 三波清理 / builtin 协作），时间不够，只讲第四层就行。

**可能被问**：
- Q：为什么不干脆还是用子进程，让内核帮你做这些？
  A：这就是上一页那个取舍。你要 fs_cache 跨调用复用、要 shell 会话持久、要精确知道哪些进程是这一轮自己 spawn 的，这些在子进程模型下架构上做不到。代价就是这一页。25 页会给这笔账的另一半。
- Q：thread-local + 一次调用一条线程，开销大不大？
  A：不知道，仓库没测。pi-shell 里没有任何 benchmark，我在上一页说过。这是一个我无法回答的问题。
- Q：协作式取消的意思是，如果工具自己不检查标志位就杀不掉？
  A：对，这是协作式的固有弱点。他们的兜底是三波信号清理外加 2 秒优雅窗口，但一个死循环里既不读 stdin 也不做 I/O 的 builtin，理论上是杀不掉的。
- Q：这些 uutils 是打了补丁的，那上游更新怎么办？
  A：这正是 vendor 48 个 crate 的代价——上游更新得自己 rebase。仓库里没写他们的同步策略。
- Q：446 行为什么这么少？
  A：因为它只做垫片，不做逻辑。三个 thread-local、几个宏、一个 resolve、一个 is_active。少恰恰是它对的地方。

## P25 · 最诚实的一张 benchmark：小批量上 Rust 更慢

**一句话主旨**：同一个核，count=10 时 Rust 是 0.86× 净亏，count=1000 时是 2.48×——变的不是代码，只是批量大小。

**提词**：
- 全仓唯一提交在册的 benchmark 结果，Apple M1 / bun 1.3.14 / **crossing-inclusive**
- `cosineSimilarityPairs @ 10` = **0.86×，Rust 更慢** [重]
- 同一个核 @100 = 2.37×，@1000 = 2.48×
- `mmrRerankIndices` = 22.44× / 30.18×，因为复杂度高
- 读法：**变的不是代码，只是批量大小**
- 规矩原话：`If native is slower, do not switch callsites.` [慢]
- 口径：这是 **mnemopi 向量核**的数，grep/shell/walker **结果未入库**
- 右边代价三条：111.2 KiB 核心包 vs 每平台 leaf 138–285 MiB
- Windows 交叉编译拉 ~3 GiB SDK；darwin 冷构建 ~40 分钟
- 最难测的平台代码（overlayfs / clonefile / ProjFS）**零测试覆盖**
- **pi-iso 是 CoW 工作区隔离，不是安全沙箱** —— 零 seccomp / landlock / namespace [停]
- 防 subagent 改坏工作树，不防它读你的 `~/.ssh`

**怎么讲**：
这一页我给它起名叫"最诚实的一张 benchmark"，理由很简单——**它把自己更慢的那一行也放上去了**。（停一拍）先交代口径，看右上角：Apple M1、bun 1.3.14，最关键的是 **crossing-inclusive**——测的时间**包含 N-API 跨越的成本**，不是只测 Rust 函数体内部。这个口径很重要，因为很多人贴的 native 性能对比是不含跨越的，那个数字没有意义。（停一拍）现在看表。前两行是 `searchExactVectorIndex`，count 10 是 1.83×，count 一万是 1.62×，都还行。然后是被玫红条框住的这一行，**`cosineSimilarityPairs`，count = 10，TS 用了 26.42 微秒，native 用了 30.67 微秒，speedup 0.86×**——**Rust 更慢**，净亏 14%。同一个 kernel，我们往下看：count 涨到 100，变成 2.37×；count 涨到 1000，2.48×。（停一拍）**变的不是代码，一行都没改，变的只是批量大小。** 这就是"读法"那一格说的：**N-API 跨越成本是个常数，payload 越小它占的比例越大**，小到一定程度就把 Rust 的全部优势吃光。最后这两行 `mmrRerankIndices` 是另一个极端，22.44× 和 30.18×——为什么差这么多？因为 MMR 重排是个 O(n²) 的算法，计算量大到跨越成本可以忽略不计。**所以能不能拿到量级的差距，取决于你的核复不复杂，不取决于你用的是不是 Rust。**

（停一拍）看下面这个橙框，我一个字一个字念仓库自己写的规矩：**"If native is slower, do not switch callsites."**——如果 native 更慢，就不要切换调用点。出处是 `docs/porting-to-natives.md` 第 173 行。这句话看起来是废话，但它在实际工程里非常难做到，因为它意味着：**你花了几周把一个函数用 Rust 重写了，测出来更慢，你得把它扔掉。** 沉没成本在这句话面前是不算数的。我觉得这才是这一页真正值钱的东西——不是那些数字，是一个团队愿意提前把"我可能白干了"这条规矩写进文档。（停一拍）再往下这两行玫红字是**口径**，非常重要，我必须说清楚：**这是 mnemopi 向量核的数字，不是 grep、不是 shell、不是 walker 的。** 后者其实有一个写得相当规范的对照脚本——真的去 spawn 一个 `rg` 子进程做对照组，先比对匹配数确保语义等价，还带了并发维度，因为并发才是 agent 的真实场景。**但是仓库里没有任何一次运行结果被提交。** 所以我在这里不给数字，**我也建议大家不要引用任何"omp 的 grep 快 N 倍"的说法**，那个数在仓库里不存在。

（停一拍）右边这一栏是代价，三条，也全都是实测的。**第一条，产物体积。** 核心的 npm 包只有一个 loader，**111.2 KiB**，很轻。但它靠 optionalDependencies 拉一个平台专属的 leaf 包，那个包是——linux-x64 因为有 baseline 和 modern 两个变体，**285.2 MiB**；其余每个平台 137 到 144 MiB。这里面装的是 56 个 tree-sitter 语法、syntect 的语法和主题、两张 BPE 表、几份位图字体、webrtc 加 opus。**对照一下上游 pi 的成本：首次用到的时候下载 rg 和 fd，几 MB。** 这是这笔投入最直观的代价，而且它是每一个用户都要付的。**第二条，构建复杂度上了一个数量级。** Bazel + rules_rust + hermetic_cc 也就是 zig 做交叉编译工具链 + crate_universe，八个构建目标；而且 cargo 和 Bazel **双轨并存**——cargo 仍然是本地开发的权威，Bazel 是产物和 CI 的权威，两套依赖图都得能跑。Rust 工具链也是两份，Bazel 钉的是四月的 nightly，本地是七月的。他们甚至还要自己写一个补丁去绕开 zig 的并发缓存损坏。加白这行是最直观的：**Windows 交叉编译要拉大约 3 GiB 的 SDK，darwin 冷构建大约 40 分钟。** **第三条，也是最扎心的一条：最难测的那部分，零覆盖。** pi-shell 有 846 个测试，听起来很多，但绝大多数落在 minimizer——也就是纯逻辑、最好写测试的那部分。而 pi-iso 只有 3 个测试、pi-uutils-ctx 3 个、pi-voice 4 个。加白这行：**overlayfs、clonefile、ProjFS 这些平台相关的代码，测试为零。** 测试覆盖的分布和风险的分布**正好是反的**——好写的地方写满了，最容易出事的地方一个没有。这不是批评，这是所有做跨平台原生代码的人共同的处境，但把它摊开来看还是有点吓人。

（停一拍）最后这一格，也是我今天在这一章一定要说清的一件事，因为它最容易被讲错。**`pi-iso` 是 CoW 工作区隔离，它不是安全沙箱。** 我把整个 crate 翻了一遍：**零 seccomp、零 landlock、零 namespace、零 cgroup、零 ptrace、零 job object、零 sandbox_init。** 它做的事情是：用 APFS 的 clonefile、Linux 的 overlayfs、Windows 的 ProjFS 这些机制，给 subagent 一份写时复制的工作区副本，跑完再把改动 diff 出来。所以它**防的是"subagent 把你的工作树改坏了"**，它**不防"subagent 读你的 `~/.ssh`"**，也不防它发起网络请求。这两件事经常被混为一谈，我见过不止一次有人拿"omp 有隔离"去论证"agent 执行是安全的"。**不是的。** 这个区分我必须讲，因为讲错的代价是有人真的把它当沙箱用。

**别漏了说**：
- 口径那两行是本页的诚实底线，**必须念完**：这是 mnemopi 向量核的数，grep/shell/walker 结果未入库。别让听众带走一个不存在的数字。
- "crossing-inclusive"要解释一句，否则 0.86× 这个数会被质疑口径不公。
- "If native is slower, do not switch callsites."要念英文原句，并且解释它对沉没成本的杀伤力——这是本页真正的落点，不是那些数字。
- pi-iso 不是安全沙箱这条**绝对不能省**，就算时间到了也要说。零 seccomp / landlock / namespace 要具体点名，不要笼统说"没有安全机制"。
- 285.2 MiB 那条要说明是 linux-x64 因为有双变体，别让人以为其他平台也这么大。
- 测试覆盖那条的措辞是"覆盖分布和风险分布正好是反的"，不是"他们不写测试"。

**可能被问**：
- Q：0.86× 是不是测得不对？为什么不多跑几轮？
  A：这份结果是提交在册的 JSON，我没有本机复跑（本机没有 bun）。但注意它是 crossing-inclusive，小 payload 上跨越成本占主导，这个结论在 N-API 上是通用的，不是这一次测量的偶然。仓库自己在向量核的模块注释里也写了对应的自觉——"每一次导出都处理整批候选，让跨越成本摊到整个召回操作上"。
- Q：那 grep 到底快不快？
  A：不知道，我不给数字。仓库有脚本没结果。要我猜的话，并发场景下因为能共享 fs_cache 应该有优势，但这是猜，不能写进 slide。
- Q：138 MiB 的包，用户装的时候不会崩溃吗？
  A：optionalDependencies 只会装当前平台的那一个，所以是一个 138 MiB 而不是六个。但对 CI 来说，每次冷装都是这个量级。
- Q：既然小 payload 更慢，为什么不做个阈值自动切换？
  A：仓库里没有看到这样的运行时切换机制，规矩是在**移植决策**这一层做的——测出来慢就不移植。运行时动态切换会带来两套代码路径要同时维护的问题，我猜是这个原因，但这是我的推测。
- Q：pi-iso 既然不是沙箱，那 agent 执行安全靠什么？
  A：靠权限审批和工具白名单那一层，也就是第一篇讲的护栏装在"环境真实执行"那一格。pi-iso 解决的是另一个问题——多个 subagent 并行改同一个工作树会互相踩。别把它们混在一起。
- Q：为什么 Bazel 和 cargo 要双轨？
  A：`MODULE.bazel` 里自己说了，cargo 仍然是本地迭代的权威，因为 rust-analyzer、cargo nextest、napi 的 typedef 生成都依赖它；Bazel 只负责产物和 CI 的内容寻址缓存。代价就是两套依赖图。
