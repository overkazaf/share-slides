## P9 · 第 02 章 · 内核

**一句话主旨**：这一章只盯 `packages/agent` 这一个包和它旁边那一层，回答一个问题——同一份骨架，为什么一个 792 行、一个 2,869 行。

**提词**：
- 三十秒过，只交代位置
- 七个点，第二个亮
- 章问题：792 vs 2,869 [重]
- 四页：主循环 / 切包 / abort / 打假
- 承诺句：不在它怎么想，在外包了多少 [慢]

**怎么讲**：
上一章讲完体量和血统，我们知道了 omp 是 153 万行、是 pi 的 6.45 倍，也知道了它是本地 clone 不是 GitHub fork。（停一拍）但体量这个数字本身没有意义，它只告诉你"多"，不告诉你"多在哪"。所以从这一章开始，我们钻进去看。左边这个大大的 02，标题就两个字——内核。下面这行加粗的问题是本章的钥匙：**同一份骨架，为什么一个 792 行、一个 2,869 行？**我先把答案剧透一下，免得大家带着错误的预期听：**不是因为 omp 写了一个更复杂的状态机**。恰恰相反，骨架那部分几乎一字没改。再往下这行小字是本章的范围——只看 `packages/agent` 这一个包，和它旁边那一层 `coding-agent`。整个 omp 有几十个包，这一章我只碰这两个，其它的后面几章再说。看这排小圆点，第一个已经变灰了，第二个是亮的，我们在七章里的第二章。右边是本章四页：第 10 页主循环，讲那个 792 vs 2,869 到底差在哪；第 11 页切包，这是我个人认为整个 omp 最重要的一次架构动作；第 12 页 abort 和错误恢复，这一页有全场最容易被你直接抄走的一段代码；第 13 页打假两则，我要拆两个名字特别唬人的包。最下面这个绿框是我给这一章的承诺，也是我希望大家带走的一句话：**内核的差别不在它怎么想，在它把多少决定外包给了宿主。**这句话有点抽象，第 10 页我就把它变成一个具体的数字。

**别漏了说**：
- 要提前打预防针："不是更复杂的状态机"——否则听众会带着"omp 一定是重写了个 NB 的状态机"的预期听第 10 页，然后觉得你在讲一件小事。
- 范围要交代清楚：这一章只碰 `packages/agent` 和 `packages/coding-agent` 两个包，别的包不在这章。免得有人问"那 Rust 那部分呢"——那在 CH5。
- 承诺句"外包了多少决定"要念出口，第 10 页的钩子数量、第 11 页的切包、第 12 页的四条信号，其实都是这一句的三种展开。

**可能被问**：
- Q：这一章的取证基准是哪个版本？
  A：omp 是 HEAD `09a7c8656`，2026-08-01；pi 是同一天的 HEAD。所有行数都是那天数的。有一个口径坑我在后面几页会反复交代：omp 自己文档里记的上游同步点是 3 月 22 号，所以凡是"pi 有 omp 无"的项，我只能说"本次对比基准下未见对应实现"。
- Q：为什么先讲内核，不先讲上下文？

## P10 · 主循环：骨架一字没改，钩子从 8 涨到约 40

**一句话主旨**：pi 和 omp 的主循环是同一副骨架，3.6 倍的行数差全部长在"可插拔点密度"上——8 个钩子涨到约 40 个。

**提词**：
- 左边绿虚线框 = 继承来的部分 [重]
- 双层 while，连英文注释都一样
- 循环里根本没有状态枚举 [慢]
- 三个队列：steering / aside / follow-up
- 右边点阵：8 → 约 40，一眼看密度
- 792 → 2,869，3.6×
- 钩子多 ≠ 更强 [停]
- 口径：3-22 vs 08-01

**怎么讲**：
这是本章第一页硬货，我讲得慢一点。先看左上角这行绿字——**"骨架：双层 while —— 这部分是继承，不是重写"**。这个绿色虚线框里的东西，是 omp 从 pi 直接继承下来的。（停一拍）看框底下这段代码，`while (true)` 是外层，里面 `while (hasMoreToolCalls || pendingMessages.length > 0)` 是内层。外层等排队的 follow-up 消息，内层跑一个 turn。这段在 omp 的 `agent-loop.ts` 是 1026 到 1030 行，在 pi 的同名文件是 170 到 174 行。**结构同构，连上面那行英文注释都几乎一样**——原文是 `// Outer loop: continues when queued follow-up messages arrive after agent would stop`。我特意去逐字比过。所以你要记住的第一件事是：**这不是两个不同的设计，这是同一个设计**。

那 792 行到 2,869 行，多出来的两千行长在哪？先说不长在哪。看这一行——**"循环里根本没有状态枚举"**。很多人一听"主循环"就以为里面是个 `switch(state)`，不是的。omp 这个循环的"状态"就是十来个局部变量的组合：`harmonyRetryAttempt`、`turnOpen`、`pausedTurnContinuations`……真正带 `running / idle / parked / aborted` 四态的显式状态机在**上一层**，在 `AgentRegistry` 里，那个第 13 页会讲。

再看绿框里这五格，这是我把内层一圈拆开的样子。① 暂停闸门——每圈先问一句"我是不是该冻住"，注意是**冻结不中止**，在飞的流跑完再停。② 模型调用——这里已经开始不一样了，pi 是静态 config 一把传进去，omp 是 `prepareProviderCall` 加一堆"每次现取"的 getter：模型、思考档、service tier、甚至 cwd，都能在跑的过程中改。③ turn_start——这一格特别有意思，pi 是先发 `turn_start` 再干活，omp 把它**延后到 provider 准备成功之后**才发，目的是不让 gate-stop 产生一个空 turn。这是那种"你不踩过坑不会想到"的改动。④ 工具批次——逐工具的 shared/exclusive 调度，加一个 steering watcher，这两块下一页和第 12 页各展开一次。⑤ 判停——这里有个反直觉的：`stopReason` 是 `toolUse` 要跑工具，是 `stop` **也要跑**。为什么？代码注释里写得很清楚，说 `stop_reason` 是 provider 的元数据，从来不回到线上去，所以它不该拦住继续；开了 interleaved thinking 的 Opus 经常在 `end_turn` 底下照发工具调用，这是他们对着真实 API 验过的。唯一必须不跑的是 `length`——被 max_tokens 截断了，那批工具调用是残的，只能补占位让模型重发。

右边这三个盒子是每轮重新 drain 的三个队列。青色的 steering 是用户插话；橙色的 aside 是非中断消息——IRC 邮箱、advisor 的评审意见、todo 对账；绿色的 follow-up 是唤醒外层 while 的排队消息，**外层 while 存在的唯一理由就是它**。这里有两处细节值得记：第一，检测必须是**非消费性的**——`hasSteeringMessages` 只 peek 不取走，因为如果你 poll 走了消息，而这个 run 马上就要 abort，那条消息就卡死在里面了；第二，aside 是**惰性 thunk**，注入的那一刻才求值，返回 null 就丢掉——这样"已经被新编辑取代的过时诊断"能在最后一刻自己撤回。这处设计很讲究。

（停一拍）现在看右半页，这才是这一页的论点。上面这两排点，青色的八个是 pi 的 `AgentLoopConfig` 全部可选钩子——`convertToLlm`、`transformContext`、`getApiKey`、`beforeToolCall`、`shouldStopAfterTurn`、`prepareNextTurn`、两个取消息的。就这八个。下面绿色的四十个点是 omp 的。我不念名字，我按主题给你分组：队列 6 个、模型和供应商 7 个、工具 6 个、上下文 3 个、可观测 4 个、其它 7 个。你不用记具体哪个，你要看的是这两排点的**密度差**。

再看底下这两条横条——`agent-loop.ts`，pi 792 行，omp 2,869 行，3.6 倍。**这两千行不是循环变复杂了，是外挂点变多了。**每一个钩子都意味着一句话："这个决定我不在内核里做，我交给宿主做。"用哪个模型？宿主决定。工具参数要不要改写？宿主决定。这一轮该不该停？宿主返回 `{stop: true}`。

最后这两行必须念，这是这一页的诚实度所在：**钩子多不等于更强**。它是把可变性从内核推到宿主，代价是内核的 API 表面变大、契约变难维护——四十个钩子，每一个都是一份你得永远兼容下去的承诺。pi 只有八个，pi 也能跑 agent。这是取舍，不是优劣。页脚那行灰字是口径：pi 的基准是 08-01，而 omp 文档里记的上游同步点是 3 月 22 号，所以"pi 有 omp 无"的那几项，我只能说本次对比基准下没看到对应实现，**不能说 omp 删了**。

**别漏了说**：
- "骨架一字没改"必须说到，而且要说是**逐行同源、连英文注释都一样**——这是本页最反直觉的点，也是最有说服力的证据。
- "循环里没有状态枚举"要单独说一句，破掉"主循环 = 状态机"这个默认假设。
- `stop` 也要跑工具这条，要带上"对着真实 Anthropic API 验过的"这个来源，否则听着像 bug。
- 钩子多 ≠ 更强这两行不能省。省了这一页就变成了 omp 吹捧。
- 口径那行灰字要念，或者至少要指一下。整场我会念三次，这是第一次。
- 40 这个数字要说清是"约 40"，是我按 `types.ts:142-526` 里可选钩子数出来的，不是官方公布的数。

**可能被问**：
- Q：pi 那 8 个钩子，omp 都还在吗？
  A：不全在。`shouldStopAfterTurn` 和 `prepareNextTurn` 这两个在 omp 侧 grep 是零命中——功能被拆掉了：停不停由 `beforeModelCall` 返回 `{stop:true}` 承担，换模型换思考档被拆成 `getModel` / `getReasoning` / `getServiceTier` / `getCwd` 这一组"每次现取"的 getter。所以严格说不是 8 涨到 40，是 8 里保留了 6、拆掉 2，然后新加了三十来个。
- Q：40 个钩子，实际用到几个？
  A：这个我没数。我只数了 `AgentLoopConfig` 上声明了多少个可选字段，没有去统计 `AgentSession` 实际实现了几个。这是我这次取证的一个缺口，如果要严谨应该补上。
- Q：钩子这么多，性能有影响吗？
  A：我没跑过 profile，答不了。直觉上每轮几十次同步函数调用相对一次 LLM 请求可以忽略，但这是直觉不是数据。
- Q：`stream.push` 换掉 `await emit` 这件事有什么影响？
  A：pi 的事件发射是 `await` 的，消费者天然被背压串行化；omp 改成同步 push，消费者就得自己排队。`AgentSession` 因此显式维护了一个 `#postPromptTasksPromise`，代码注释里写了原因。这是"少一层 async 间接"换来的账。
- Q：我自己写 agent，该照 8 个还是 40 个来？
  A：照 8 个甚至更少。这一页想说的恰恰是钩子数量是被需求逼出来的，不是设计出来的。你没有多模型 fallback 的需求，就不该有 `getModel` 这个钩子。

**过渡到下一页**：不过话说回来，这两千行只是量变。omp 真正做了一次质变的重构，不在这个文件里，在包的边界上——下一页。

## P11 · 切包才是真重构：把 harness 踢出内核包

**一句话主旨**：omp 最本质的架构动作是把 harness 从内核包踢出去，让 `packages/agent` 变成纯内核；代价是 harness 变成了一个 8,814 行的单文件类。

**提词**：
- 左 pi，右 omp，看红框
- pi：harness/ 8,108 行，住在 agent 包里 [重]
- omp：agent 包无 harness 目录，0 行
- 搬到 coding-agent，变成 AgentSession 8,814 行**单文件**
- 1,185 → 8,814
- 复杂度没消失，换了地方 [慢]
- 能抄的是动作，抄不了的是规模
- 未跟进 pi 的 SDK 化重构 —— 说"未见"不说"删了" [停]

**怎么讲**：
第 10 页讲的是同一个文件里多了两千行，那是量变。这一页讲的是包的边界变了，我认为**这才是 omp 唯一一次真正意义上的重构**。（停一拍）左右两栏，左边 pi，右边 omp，都是 `packages/agent/src` 这个包。

先看左边。pi 的 agent 包总共 10,368 行，里面这个玫红色的框——`harness/`，8,108 行。看清楚这个比例：**pi 的 agent 包里，八成是 harness**。`AgentHarness`、session store、tools、prompt，全在这个包里头。剩下那两千行才是循环本体：`agent-loop.ts` 792、`agent.ts` 577、`types.ts` 437、compaction 目录 1,287。

再看右边。omp 的 agent 包 14,873 行，比 pi 还多四千多行——但注意这个虚线的玫红框：**无 harness 目录，0 行**。这个包里现在只有循环和循环的配套设施：`agent-loop.ts` 2,869、`agent.ts` 1,650、`types.ts` 862、`pause.ts` 107、`telemetry.ts` 2,078、`run-collector.ts` 631、compaction 目录 5,667（13 个文件，pi 那边是 3 个文件 1,287 行）、还有 `append-only-context.ts` 348 行。**这个包现在是一个可以被别的宿主复用的纯内核。**

那 harness 去哪了？看下面这两个盒子。pi 的 `coding-agent` 是 56,431 行，harness 不在这儿；omp 的 `coding-agent` 是 398,480 行，七倍。harness 整体搬进来了，变成了 `session/agent-session.ts`。中间这个紫框是这次重构的一句话总结：**pi 的 `AgentHarness`，1,185 行 → omp 的 `AgentSession`，8,814 行**。

（停一拍）我要在这儿停一下，因为这个数字得念两遍：**8,814 行，一个文件，一个类。**右边那个玫红色的"代价"框写的就是这件事——**内核干净了，但 harness 的复杂度没有消失，它只是换了个地方待着**。这不是批评，这是一个必然的账：你把内核清干净，被清出去的东西总得落到某个地方。omp 选择让它落进一个巨型类，而不是继续拆成一个包。

底下这三条是我给这一页的三个结论。① 内核包只留循环与配套，好处是可以被别的宿主复用——这不是理论，`metaharness` 那边就是把它当 type-only import 用的。② 代价刚才说了，8,814 行单文件。③ 这条要小心讲：**omp 没有跟进 pi 后来在 `packages/agent/src/harness/session/` 做的 SDK 化重构**。pi 现在有一套 `SessionReader` / `SessionStore` / `SessionRepository` / `SessionSearch` 的抽象，omp 全仓 grep 那套的核心类型是零命中。但请注意底下这行灰字的措辞——**本次对比基准下未见对应实现，不等于 omp 删除**。为什么要这么绕？因为 omp 自己的 `docs/porting-from-pi-mono.md` 记的上游同步点是 2026-03-22，而我对比的 pi 是 08-01 的 HEAD。中间隔了四个多月，pi 这套 SDK 化抽象完全可能是三月之后才有的。代码能告诉我"omp 侧零命中"，但**代码告诉不了我这是主动删还是没跟上**，那是动机层面的东西。所以我只讲事实，不讲动机。

最后看右下角这两行，这是我认为这一页最该被带走的：**能抄的是这个动作——把"循环"和"产品"分成两个包；抄不了的是它的规模。**分包这个动作本身几乎零成本，你今天下午就能做。值钱的不是分包，是**"内核里什么都不许放"这条纪律**——每次有人想往内核里塞一个便利函数的时候，能不能顶住。omp 顶住了，代价是 8,814 行的 `AgentSession`。

**别漏了说**：
- "8,814 行单文件"要念两遍，这是本页的记忆点，也是本页的诚实度所在——不能只讲"内核纯化了"这个好听的一半。
- "复杂度没消失，只换了地方"是本页最该被带走的一句判断。
- 口径纪律必须现场讲清楚为什么这么措辞，不能只念灰字。这是整场诚实度的招牌动作，第 12 页还会再用一次。
- pi 的 harness 占它 agent 包八成，这个**比例**比绝对行数更有冲击力，别只念 8,108。
- "分包零成本，纪律才值钱"要说到——否则听众的行动项会变成"我也去分个包"，那没意义。

**可能被问**：
- Q：8,814 行的单文件类，这不是反模式吗？
  A：按常规工程标准是。我没法替他们辩护，也没法证伪——我没有读完那 8,814 行，只统计了行数、看了几个关键方法。但可以说的是：这是个单人主导的项目，单文件对一个人的心智模型可能反而是省事的，代价由后来者付。
- Q：pi 后来做的 SDK 化抽象更好吗？
  A：从类型上看更严格——比如它有个 `SessionForkSelection` 代数，把"全量 / 到某条 entry / 到某条 user 消息之前"三种分叉写成了类型，还会校验目标真的是 user 消息，不是就抛 `SessionError`。omp 那边这个语义是硬编码成一行 `.parentId`。我倾向于说 pi 那套在这一点上更有类型，但"更好"要看你是不是需要对外发 SDK。
- Q：omp 为什么不跟进上游？
  A：不知道。这正是我刚才说的动机层面，代码判定不了。
- Q：`packages/agent` 真的被别的东西复用了吗？还是只是理论上可复用？
  A：我确认到的是 `metaharness` 那边把它当 type-only import。真正把它当独立内核跑起来的第二个宿主，我这次没找到。所以"可复用"这个好处，目前更多是结构上的，不是已兑现的。

**过渡到下一页**：切完包，我们进内核最精细的一块。下一页只讲一件事：当用户在 agent 跑到一半的时候插了一句话，到底该杀谁、不该杀谁。

## P12 · abort 不是一个布尔，是四条信号

**一句话主旨**：abort 被拆成四条独立信号加一道暂停闸门，规则只有一句——排队的用户插话永不硬杀一个已经产生副作用的前台工具；错误恢复则分成协议层和策略层两层。

**提词**：
- 四个盒子从左到右，权限递减 [重]
- 外部 signal 杀一切；steering/IRC 只杀 interruptible
- 其余工具只收外部 signal —— 这是核心 [慢]
- 一句话规则：不硬杀已产生副作用的前台工具
- 第五条不叫 abort：PauseGate，冻结不中止
- 恢复两层：协议层 vs 策略层
- TurnRecovery 1,787 行；pi 侧「未见」不是「删了」
- 右栏 13 行是全场最能抄的一段 [停]
- 右栏是「照原码语义整理」，不是逐字原文

**怎么讲**：
这一页在我看来是 omp 内核里最精细的一块，也是最能看出"这些代码是被真实事故打磨过的"一页。（停一拍）先看最上面这四个盒子，从左到右权限递减。

第一个玫红的，**外部 signal**——调用方给的 abort，比如你按 Ctrl+C。这条**硬杀一切，谁都拦不住**。第二个青色的，**steering**——用户插话。第三个橙色的，**IRC**——别的 agent 发来的消息。这两条通过 `AbortSignal.any` 合成一条 `interruptibleSignal`。第四个绿色的，**协作式软信号**，通过 `ctx.toolCall.steeringSignal` 发给每一个工具，它**不中止任何东西**，只是通知："有人在等你，你要不要让个路。"比如 bash 收到这个信号可以自动把自己转到后台去跑。

那这四条怎么分派？看中间这个玫红框，规则就两行。**工具如果声明了 `interruptible: true`**——这类工具是纯等待型的，比如 `hub wait`、`vibe`，它们除了耗时间什么也不做——那它收 `interruptibleSignal`，可以被 steering 和 IRC 硬杀，因为杀了没有任何损失。**其余所有工具，比如 bash，只收外部 signal。**

这一句就是本页的心脏，我用大白话再说一遍：**你在 agent 跑到一半的时候插一句话，它不会去杀那个正在跑的 bash。**为什么？因为 bash 可能已经改了文件、已经发了网络请求、已经产生了副作用。杀掉它，副作用还在，但结果丢了——你的上下文里从此有一个谎：一条 "skipped"，实际上它跑了。代码注释里直接引用了 issue #4752，就是这么被打出来的。所以后面那半句也很重要：**工具跑完了就保留真实结果，不因为 abort 落地而伪造成 skipped**。

底下这个绿框是第五条，但它刻意不叫 abort，叫 `AgentPauseGate`——**冻结，不中止**。它只在两个动作边界上轮询：模型调用之前、每个工具启动之前。已经在飞的流、已经启动的工具，跑完再停。这个区分很重要：abort 是"别做了"，pause 是"做完这件别接下一件"。

（停一拍）下半页换话题，讲错误恢复，这里的看点是**分层**。左边绿框是第一层，在循环内，我叫它协议层，管的是"这一次 HTTP 流本身坏了"。四个例子：GPT-5 的 Harmony 协议泄漏，能救就截断续跑，上限两次，不能救就丢掉半截重新采样，还失败就抛；流中断时有半截 toolCall，只保留 `toolcall_end` 已经到达的那些；瞬时流错误但工具调用其实是完整的，那就把 `stopReason` 从 `error` **改写成 `toolUse`**，让这轮工具照跑；最后是批次尾扫，谁没产出结果就补一个 skipped，保证 tool_use 和 tool_result 严格配对——这个配对不严格，下一次请求就直接 400。对照 pi，pi 这一层只有一个函数，处理 `length` 截断。

右边紫框是第二层，在会话层，`TurnRecovery`，1,787 行，管的是"这个模型不行，换一个再来"。模型 fallback 链、空回复重试三次、非预期停止三次配四秒超时还带一个分类器、限流退避、"思考循环"重定向、重试成功之后还回头把历史里那条错误消息标成已恢复。注意底下这行灰字的措辞——**本次对比基准下，pi 侧未见对应实现**。跟上一页一样的谨慎，理由一样，不重复了。

分层的好处写在这行：**循环内不必知道有几个模型可切，会话层不必懂 Harmony 协议是什么。**这是个很干净的切法，我觉得比那 1,787 行本身更值钱。

还有一个小机关值得说：终结信号也复用了 abort。子代理调 `yield` 提交结果之后，会话层调 `agent.abort(TERMINAL_TOOL_RESULT_ABORT_REASON)`，主循环认出这个**特定的 reason** 就把 `hasMoreToolCalls` 置成 false。等于用一个 Symbol 当带内信令——既停住了循环，又不污染用户的 abort 语义。

（停一拍）好，现在看右半页，这是**全场我最建议你直接抄走的一段**。先说清楚一件事：这里显示的十三行，是我**照原码语义整理**过的，省掉了 telemetry 和错误包装，**不是逐字的原文**——原文在 `agent-loop.ts:2660-2686`，回头你自己去看。

它解决什么问题？我们先说 pi 是怎么做的：pi 有个全局配置 `toolExecution`，只有两个值，`sequential` 或者 `parallel`。而且更狠的是——**只要这一批里有任何一个工具声明了 sequential，整批全部串行**。你想想这个后果：模型一口气发了五个 read 和一个 write，read 之间完全可以并行，但因为 write 要串行，五个 read 也全被拖成串行。

omp 的做法是让**每个工具自己声明**，看上面这两行类型：`concurrency` 是 `"shared" | "exclusive"`，还可以是一个函数——**按调用参数动态决定**。比如同一个 bash 工具，跑 `ls` 是 shared，跑 `rm` 是 exclusive。`interruptible` 也一样能动态决定。

调度器就是这十三行，一条手写的**屏障链**。逻辑只有一句：**exclusive 的工具要等前面所有人跑完，shared 的工具只等上一个 exclusive。**我照着代码念一遍：来一个工具，先看它是不是 exclusive；是的话，`start` 等于 `Promise.all([lastExclusive, ...sharedTasks])`——等上一个 exclusive **加上**它之后所有的 shared；不是的话，`start` 只等 `lastExclusive`。然后 `start.then` 挂上真正的执行。如果是 exclusive，就把自己记成新的 `lastExclusive`，并且**把 sharedTasks 清空**——因为后面来的 shared 只需要等我，不需要等我之前那些。

翻译成一句人话：**写文件的工具声明 exclusive，只读的工具声明 shared，同一批工具调用就能既并发、又不互相打架。**exclusive 在这里的角色就是**批次内的写屏障**。十三行，零依赖，不需要任何调度框架，你今天写的那个小 agent 就能用上。这是我这次读整个 omp 最想推荐的一段代码——不是因为它复杂，恰恰因为它简单到你没有理由不抄。

**别漏了说**：
- 核心规则那一句必须用大白话再说一遍，并且要说清楚**为什么**——副作用已经发生，杀掉只会让上下文里留下一条谎。issue #4752 这个出处能加可信度。
- pause 和 abort 的区别要点破："别做了" vs "做完这件别接下一件"。
- 右栏那十三行必须明确说明是"照原码语义整理"，不是逐字原文。这是不能省的口径。
- 讲那十三行的时候，一定要**先讲 pi 的痛点**（一个 sequential 拖垮整批），再讲 omp 的解法。只讲解法听众感受不到价值。
- "按参数动态决定"这个点容易被略过，但它才是这段设计比"给工具打个静态标签"高一档的地方。举 `ls` vs `rm` 这个例子。

**可能被问**：
- Q：那我插话之后 bash 还在跑，我不是等很久？
  A：是。这就是这个设计的代价——它选择了"不丢副作用"而不是"响应快"。但协作式软信号就是给这种情况留的口子：bash 收到软信号可以自愿把自己转后台，让出前台。所以不是完全没辙，是让工具自己决定怎么让路。
- Q：`interruptible` 由谁来判断？会不会有人乱标？
  A：由工具的实现者标。会不会乱标——会，这就是把可变性外包给宿主的代价，跟第 10 页那四十个钩子是同一笔账。omp 内部标 interruptible 的都是纯等待类工具。
- Q：这十三行有 bug 吗？比如 exclusive 后面又来一个 exclusive？
  A：第二个 exclusive 会等 `Promise.all([第一个 exclusive, 空的 sharedTasks])`，也就是只等第一个，是对的。我没有做穷举的正确性验证，只是读了逻辑觉得成立。如果你要抄，自己写几个 case 测一下，别信我。
- Q：`TurnRecovery` 那 1,787 行值得抄吗？
  A：不值得整体抄，值得抄的是那条分界线。你自己的项目里，"HTTP 流坏了"和"模型不行要换"这两件事分不分开，这个决定是免费的；那 1,787 行是他们支持一堆 provider 才需要的。
- Q：为什么用 abort reason 当带内信令，不加个返回值？
  A：pi 那边确实是加返回值的——`AgentToolResult.terminate` 加 `shouldTerminateToolBatch`。omp 换成了 abort reason。我猜是因为终结 yield 是由会话层监听事件后触发的，那个位置手里只有 `agent.abort()` 这一个把手，没有工具返回值的通道。但这是我的猜测，不是代码告诉我的。

**一句话主旨**：`metaharness` 不是 harness 的 harness，是 benchmark 实验管理器；`swarm-extension` 是个没有并发上限、零重试、节点间零数据传递的 YAML DAG；真正有料的是没人提的 `AgentRegistry` 和 `IrcBus`。

**怎么讲**：
这一章最后一页，我换个方向。前三页都在讲 omp 哪里做得细，这一页我要拆两个包——**名字听起来最唬人，实际最朴素的两个**。（停一拍）

在开始之前，我必须先声明一件事，这很重要。看左边这一栏，标题叫"常见讲法"。**这不是我在引用谁、也不是在点名批评哪篇文章。**这一栏写的是**按包名望文生义的典型误读**——就是任何人第一次在包列表里看到 `metaharness` 和 `swarm-extension` 这两个名字，脑子里最可能自动补出来的那个东西。我把它写出来，是因为我自己第一次看到就是这么想的，而且我猜在座有一半人刚才看到标题也是这么想的。所以这一页打的不是别人的假，是**打名字的假**。

第一则，`metaharness`。左边这个虚线框是望文生义版本：harness 的 harness，一个能包住各种 agent harness 的抽象层，属于生产链路的上层。听起来很厉害对吧？（停一拍）右边是实情：它是一个**跨三种 benchmark 的统一实验管理器，外加一个 Harbor runner**。三种 benchmark 硬编码在 `store.ts:19` 一行里：`harbor | edit | snapcompact`。它自己**不定义任务、不写 verifier、不评分**——评分是各 benchmark 原生产物给的，它只做 adapter 归一化，那个归一化的分发口一共**三行 if**。所以"meta"的准确含义不是"元 harness"，是 **meta-over-harnesses**——跨多个 benchmark 的实验管理层。

怎么知道它不在生产路径上？看这行：`private: true`，版本停在 **0.0.1**，全仓库对它的反向依赖是**零**——除了它自己的 package.json 和根目录一条 dev 脚本，`coding-agent`、`agent`、`tui` 谁都不 import 它。而且它跑起来的前置条件是开发者机器专属的：宿主上要有 pm2 跑的 auth-gateway、要有 harbor CLI、要有 Docker、要有 uv。这是**一个人自己的实验台**，不是产品的一部分。

第二则，`swarm-extension`。左边望文生义版本：YAML 声明一张 DAG 就能编排多 agent，模型自己能触发，失败会重试，中断了还能续跑。（停一拍）右边逐条来。**DAG 是真的**——Kahn 算法环检测、wave 分层，`dag.ts` 里写得挺正经，整个包 1,795 行。但接下来四条：**并发上限——没有。**wave 内部是 `Promise.all` 全并行，无界；50 个节点就是 50 个并发子会话。而且宿主那个 `task.maxConcurrency`（默认 32）救不了它，因为那个信号量只在 `task` 工具的 spawn 路径上 acquire，swarm 是直接调 `runSubprocess`，绕过去了。**重试——零。**pipeline、executor、dag 三个文件里没有任何 retry 或 backoff。节点失败也不剪枝下游：per-agent 的 try/catch 把异常转成 `exitCode: 1` 的合成结果，wave 是启动前一次性算好的，之后不重算，所以依赖全挂的节点照样执行，只是磁盘上没有它要的输入。**节点间零数据传递**——没有变量插值、没有模板、没有结果回填。那个叫 `reports_to` 的字段，名字看起来像数据流，实际**只是一条排序边**。README 自己写得很直白："It does not pass data between them. Agents communicate through files in the shared workspace." 也就是说，**它们靠往同一个目录里写文件来通信**。**模型无自主入口**——整个包只注册了一个 slash command，`registerTool` 一次都没调用，尽管扩展 API 是支持的。最后，`dag.ts` 的拓扑排序、环检测、wave 构建，**零测试覆盖**——唯一那个测试 mock 掉了 `runSubprocess`，只断言了一个回归。

（停一拍）看中间这个紫框，这是本页的主张，我念一下：**要讲的不是"它们不行"，是"名字不是证据"。**这句话我要展开一下。metaharness 值得抄的不是代码，是它的**四层数据模型**——experiment → arm → run → trace，还有"跑分脚本也要有 schema"这个态度。它那个统计口径严谨到什么程度？代码注释里写着：所有观测统计只在**已判定**的 trial 上算，分子分母同一个总体；因为 `run.costUsd` 包含在飞 trial 的累计花费，早期拿它除以已判定数会**严重高估**每任务成本。这个意识比代码值钱。swarm 值得记的是**边界**：模型自主决策和声明式编排在这里被**硬切开**了——不是做得不够，是刻意不做。

底下这行是我给的一个通用手艺：**判断一个包重不重要，看两样——反向依赖有几个，测试覆盖到哪。**这两个指标不需要你读懂代码就能查，五分钟出结论。

最后看右半页，这才是我想让大家带走的：**真正有料的两个，反而不显山露水。**

第一个，`AgentRegistry`，217 行。进程内所有 agent——主会话加每一个子代理——登记成一张表，**带真正的状态机**：`running` 是有一个 turn 在飞；`idle` 是会话还活在内存里等活干，注意**干完活的 agent 是 idle，不是被移除**；`parked` 是会话已经销毁了，但 `AgentRef` 和 sessionFile 留着，**可以复活**；`aborted` 是硬杀，终态。配套的 `AgentLifecycleManager` 455 行，idle 超过 TTL 就 park，需要的时候 revive。park 和 revive 之间的并发被显式 gate 住并按 id 合并，而且每次操作绑定到**确切的那个 AgentRef**——防止一个旧的 revive 覆盖掉一个新的同 id ref。这种细节只有被并发 bug 咬过才写得出来。

第二个，`IrcBus`，agent 之间的邮箱，信箱容量 100。它的关键性质写在文件头注释里：**send 从不阻塞在"对方生成了什么"上**。收件人 parked 就经 lifecycle manager 复活它，idle 就用一个真实 turn 唤醒它，busy 就在下一个 step 边界给它一条**非中断的 aside**。

（停一拍）看到这儿，这一章就闭合了——**这个 aside，就是第 10 页右边那个橙色盒子**。第 10 页我说 aside 有三个生产者：IRC 消息、advisor 的评审意见、中途 todo 对账，它们一起注册在 `agent-session.ts:1140-1147`。现在你知道 IRC 那一条是从哪来的了。而且还记得我说 aside 是**惰性 thunk**吗——注入那一刻才求值，返回 null 就丢掉。放在这个语境下就更好理解了：一条 agent 间的消息在排队等待期间可能已经过时了，惰性求值让它有机会在最后一刻自己撤回。

最后一行：**上游 pi 完全没有子代理系统。**这次我 grep 了 `subagent`、`spawnAgent`、`Task tool`，在 pi 的 `coding-agent` 和 `agent` 两个包里**零文件命中**，也没有 `task/` 目录。所以这一整块大约 430 KB 是 omp 净新增，是"omp vs pi"面积最大的一块。这一条我用的是"零命中"这个事实，不是"omp 加了 pi 没加"这个判断——不过这次方向反了，是 omp 有 pi 无，所以那条口径纪律在这里不构成风险。
