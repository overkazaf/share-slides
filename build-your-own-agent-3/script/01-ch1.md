**怎么讲**：
刚才目录那页说了，七章，重心在 CH2 内核和 CH7 收口。我们从第一章开始——这一页我走得快，四十秒，因为它本身不承载论点，只告诉大家我们现在站在哪儿。（停一拍）左边这个大大的 01，下面「体量与血统」四个字，是本章的名字。再往下这行加粗的问题——「它到底大到什么程度，又是从哪儿长出来的？」——整章只回答这一句。底下这段小字我不念，我解释一下意图：这一章我**刻意不谈任何设计**，不讲主循环、不讲上下文压缩、不讲 Rust 热路径，那些全在后面六章。这里只做一件事，就是**把尺子摆出来**。为什么要先摆尺子？因为这一篇的主张是「omp 的价值不在它做了什么，而在它把每个决定的代价都摊开给你看」——可你要是不先相信这东西真的被做到了极致，后面我说「这个代价它付了、那个代价它付不起」，你会觉得我在夸张。所以第一章的唯一任务，是**建立可信度**，而且是用可核查的数字建立，不是用形容词。（停一拍）再看这排小圆点，一共七个，第一个是亮的——这是本场的进度条，每章扉页你都会看到它往前走一格，后面我就不再解释了。右边是本章的小目录，三页：06 讲三层血统，一句话剧透——**仓库层面它跟 pi 完全独立，血缘只剩 LICENSE 里的两行版权**；07 讲体量，153 万行，TS 是上游的六倍半；08 是本章的高潮，也是我个人觉得这次调研最有冲击力的一条——**这个仓库有两千多个 commit，署名给的是它自己**。底下这个绿框是我给这一章的承诺：读完三页，你不用同意我对 omp 的任何评价，但你会承认它确实站在了一个极端上。

## P6 · 血缘只剩两行版权：omp 与 pi 是两个独立仓库

**一句话主旨**：omp 是 pi 的代码级深度 fork，但在 GitHub 层面彻底 detach——「是 fork 又不是 fork」，这两件事必须分开说。

**提词**：
- 三层：pi → oh-my-pi → 本地 clone
- L1 Mario Zechner，11.2 万行；L2 Can Bölük，72 万行
- ①是代码级 fork，不是 Fork 按钮 [重]
- GitHub API `fork: false`
- LICENSE 两行版权并列，一个字没删 [慢]
- 本地这份是 clone，没有私有改动
- 顺带更正上一篇：FORK.md 全史零命中 [停]

**怎么讲**：
先看左边这张血统图，从上往下三层，一条直线，但**两次复制的性质完全不一样**，这是本页唯一要记住的事。（停一拍）最上面 L1，青色框，`earendil-works/pi`，作者是 Mario Zechner，原来叫 `badlogic/pi-mono`——第二篇整场讲的就是它，一个极简的 agent 工具包，右边那个数字，**11.2 万行 TS 源码**。往下这条箭头，旁边那行小字是①：**代码级深度 fork —— 仓库层面独立，不是 GitHub 的 Fork 按钮**。到了 L2，绿框，`can1357/oh-my-pi`，作者 Can Bölük，本篇的主角，右边 **72 万行 TS 再加 18.5 万行 Rust**。再往下 L3，虚线框，是我这次的取证现场——本地那份 clone，`git remote -v` 指向 can1357，`git branch -a` 只有 main 和 origin/main，**没有任何私有改动**，所以我等会儿引的每一个「文件:行号」，都是上游本体的原文，不是我这边改出来的。

现在讲这页最容易被讲错的地方，就是底下这个玫红框。**常见讲法**：oh-my-pi 是 pi 的一个 GitHub fork。**实情**：不是。我去查了 GitHub API，`oh-my-pi` 这个仓库的 `fork` 字段是 **false**，它没有 upstream 指针，你不能从它直接给 pi 提 PR，它有自己的 issue、自己的发布、自己的版本号——现在是 17.2.3，而 pi 那边根 package.json 还是 0.0.3。（停一拍）那为什么我还一直说它是 fork？看右边这一栏，最上面是 LICENSE 的前四行，我念一下：MIT License，空行，`Copyright (c) 2025 Mario Zechner`，`Copyright (c) 2025-2026 Can Bölük`。**两行并列，不是替换**，上游署名一个字都没删。这就是答案——**代码层面它是彻头彻尾的 fork，血缘硬得写在版权声明里；GitHub 层面它是彻底 detach 的独立仓库**。这两句话不矛盾，它描述的是两个不同的东西：一个是代码从哪儿来，一个是协作关系怎么维系。

那既然 detach 了，上游更新怎么办？看紫框最后一行——**靠人工**，仓库里有一篇 `docs/porting-from-pi-mono.md`，387 行，整篇就讲怎么从 pi-mono 往这边迁移。我提醒一句口径：那篇文档记录的上游同步点是 2026-03-22，而我对比用的 pi 基准是 08-01，所以后面某些「pi 有、omp 无」的东西，有可能是上游三月之后新加的，不是 omp 主动删的——这个不确定性我会在相关页面上标出来。（停一拍）最后是琥珀色那个框，顺带更正上一篇。上一篇我讲过一套 FORK.md 里的三层成本模型，讲得挺起劲——那份文件**根本不在 omp 上游仓库里**，它出自某个私有下游 fork 维护者自己写的手册。我这次把仓库 unshallow 了，**全史 16,613 个 commit，`git log --all -- FORK.md` 零命中**，从来没存在过。第 3 页我已经正式认过错了，这里只是把它挂在血统图旁边，因为搞混的根源就是血统没分清——我当时把 L3 私有 fork 的东西当成了 L2 上游的东西。

**别漏了说**：
- 「是 fork 又不是 fork」必须拆成两句话说清楚：**代码级深度重写 = 是 fork；GitHub 层面 `fork: false` = 不是 fork**。只说一半，听众一定会记岔。
- LICENSE 那两行要**念出来**，不要只指。这是全页唯一的一手硬证据，念出来的说服力比讲十句强。
- 「同步靠人工」这条要点到，它是后面所有「omp 为什么敢大改」的前提——没有 upstream 指针，就没有 merge 冲突的顾虑，重写的成本结构完全不同。
- 上游同步点 2026-03-22 vs 对比基准 08-01 的口径差要主动说，别等人问。
- 更正 FORK.md 时语气要平，别演。已经在第 3 页道过歉了，这里是补一个「为什么会错」的解释。

**可能被问**：
- Q：`fork: false` 是怎么查的？会不会是他 fork 完又 detach 了？
  A：我查的是 GitHub 仓库 API 的 `fork` 字段，当前值是 false。GitHub 确实支持申请把 fork 关系解绑，所以历史上有没有 fork 过、后来解绑了，我从 API 现状看不出来，这条我不知道。但对本场的结论没影响——现状就是两个独立仓库。
- Q：既然不是 GitHub fork，那还算「同一份基座」吗？6.45 倍这个对比公平吗？
  A：算，而且我认为公平。LICENSE 保留双版权、`docs/porting-from-pi-mono.md` 整篇讲从 pi-mono 迁移、包结构和主循环骨架还能一一对上——CH2 那页会给你看骨架的对照。它不是「参考了 pi」，是从 pi 的代码长出来的。
- Q：Mario 本人对这个 fork 什么态度？
  A：不知道，我没查到公开表态，也没去问。我能看到的只有 LICENSE 里保留的署名，和全史里 Mario 名下的 1,339 个 commit——那是 pi 时期的历史被完整带过来了，说明这不是复制粘贴，是带着 git 历史整体接手的。
- Q：本地这份 clone 会不会已经落后了？
  A：会。HEAD 是 09a7c865，2026-08-01。这个项目大概两天半发一个版本号，所以我上台这会儿它多半已经又往前走了几十个 commit。所有数字都以那天为准。

**过渡到下一页**：血统讲完了，那接下来就是最直白的问题——同一份基座，他到底堆了多少东西进去？下一页只有一张对比图，但那个长条会让你有点不适。

## P7 · 同一份基座，6.45 倍的体量

**一句话主旨**：TS 源码 72 万 vs 11 万，外加 pi 一行都没有的 18.5 万行 Rust 和 8.3 万行 Python——全仓约 153 万行。

**提词**：
- 上半区①：同口径 TS 对比，112,232 vs 723,921
- 6.45× 那个方块 [重]
- 下半区②：pi 完全没有的几块
- Rust 8.3 万自研 / 9 crate，pi 侧 **0 个 .rs 文件** [慢]
- vendor 10 万：内嵌 bash + 46 个 uu-*
- Python 8.3 万；测试 53.8 万，测试/源码 0.74
- 底部大字：≈ 152.9 万行
- 诚实补一刀：行数不等于价值 [停]

**怎么讲**：
这一页只有一张图，我讲慢一点，因为它是这一章的证据核心。（停一拍）先看上半区①，标题写着「同一口径下的正面对比」——我强调**同一口径**：两个仓库取的是同一天的 HEAD，用的是同一条 `find` 命令，都排除了测试文件、测试目录和 node_modules，omp 侧只数 `packages/*/src`。这条件我卡得比较死，因为体量对比最容易被人质疑口径。上面这根青色的短条是 pi，**112,232 行，495 个文件**。下面这根绿色的长条是 omp，**723,921 行，1,875 个文件**。你们看这两根条的长度差——右边那个方块写着 **6.45×**。

（停一拍）6.45 倍意味着什么？我给一个体感。11 万行 TS，是一个熟练的人认真读一两周能通读一遍的规模，pi 那边我第二篇就是这么干的。72 万行，**你通读不完**。72 万行大概是什么概念——比早期的 Linux 内核还大，跟一个中型商业 IDE 的核心层一个量级。而这不是一个团队十年堆出来的，是一个人在两年多里做的，最近这六十天还保持着**日均 155 个 commit**。所以当我说「一个人把 agent 做到极致」，6.45 这个数字就是「极致」两个字的定量版本。

再看下半区②，这几条是**上游 pi 完全没有的东西**，注意它们跟上面用的是同一个比例尺，所以长度可以直接比。第一条，**自研 Rust 8.3 万行，9 个 crate**，右边我特意标了一行玫红字——**pi 侧：0 行、0 个 `.rs` 文件**。这不是「omp 的 Rust 更多」，是**从无到有**。这 9 个 crate 里最大的是 `pi-shell`，四万多行，一个内嵌的 bash；CH5 一整章讲的就是这块。第二条虚线框，**vendored 的第三方 Rust 10 万行**，49 个 crate——一个 brush（就是那个 bash 实现的上游），加 **46 个 `uu-*`**，也就是 uutils 版的 coreutils，`cat`、`sed`、`sort`、`find`、`xargs`，一个命令一个 crate，全被搬进了进程里。第三条，**Python 8.3 万行**，其中三万二是 robomp——下一页的主角；两万九是 snapcompact 的离线研究脚本，CH3 会讲。第四条也是虚线框，**TS 测试 53.8 万行**，测试对源码的比例是 **0.74**。

（停一拍）最后看底下这条横带，把所有东西加起来——**约 152.9 万行**，我在标题里就叫它 153 万行。右边还有几个格子：16 个 workspace 包、docs 目录 122 篇 27,931 行、包里 243 个 prompt 的 `.md` 文件、模型目录 63 个 provider 4,106 个条目、版本号 17.2.3——注意这个版本号 TS 和 Rust 是**共用**的，一个 `Cargo.toml:6` 管到底。

现在我必须诚实地补一刀，不然这页就成了吹牛。**行数不等于价值。**（停一拍）我给你们三个减分项，都是我自己点算时发现的。第一，**测试占了 53.8 万行**，那 152.9 万里有三分之一是测试代码——这是好事，但你不能拿它去论证「功能有多复杂」。第二，**catalog 这个包 10.5 万行里，有 8.9 万行是 protoc 生成的 `*_pb.ts`**，Cursor 和 Devin 转售商协议的机器产物，手写的其实只有一万六。第三，那 10 万行 vendored Rust **不是他写的**，是搬进来的第三方。所以如果你只认「一个人亲手写的产品代码」，这个数会缩水不少。（停一拍）但我为什么还是敢把 6.45 倍这个数摆在标题上？因为**上半区①那个对比是干净的**——两边同口径、都排除测试、都只数 src，减分项减的是「153 万」这个总数，不是「6.45 倍」这个比值。

顺带补一条 slide 上没有的，因为我是点算完之后才想到该按同口径比一次的：**文档**。这页显示的 122 篇是 omp `docs/` 目录单独的数，跟 pi 不是同一个口径。我重新按全仓 Markdown 数了一遍：**omp 493 篇，pi 97 篇，5.08 倍**——跟代码的 6.45 倍几乎是同一个量级。而且更狠的是，**pi 根本没有 `docs/` 这个目录**。这条我留到 CH7 展开，那里有一整页讲文档。

**别漏了说**：
- 「同一口径」四个字要说出口，最好把排除条件念一遍。体量对比页最容易被质疑的就是口径，先自己堵住。
- Rust 那条必须说成**从无到有**，不是「更多」。指着那行「pi 侧 0 行、0 个 .rs 文件」念。
- 6.45 倍要给体感，不要只念数字。「11 万你能通读，72 万你通读不完」是这页最容易被记住的一句。
- **减分三条必须讲全**：测试占三分之一、catalog 8.9 万是生成的、vendor 10 万不是自研。这是本篇诚实度的第一次兑现，后面还有好几处，这里先立住人设。
- 立刻补上「减分减的是总数，不是比值」——不然听众会觉得你把自己的论点否掉了。
- README 自称 55k Rust、本地实测 83,443，这个口径差 slide 页脚有写，如果有人盯着看要主动解释。
- 文档 493 vs 97 那条是口头补充，slide 上没有，讲的时候要说明「这条是我事后按同口径补算的」。

**可能被问**：
- Q：72 万行里有多少是 AI 生成的？
  A：分不出来。git 元数据里没有这个信息，我也没有可靠的启发式去判。下一页会给一个相关但不等价的数——**署名给 bot 账号的 commit 有 2,564 个**，注意那是 commit 数不是行数，而且署名给 bot 不等于 AI 独立写成。这两个数不要混着用。
- Q：README 写「~55k lines of Rust core」，你说 8.3 万，谁对？
  A：都对，口径不同。我的 83,443 是 `crates/pi-*/src` 下全部 `.rs`；README 的 55k 大概率排除了 `pi-shell` 里的 minimizer 之类，但他没写口径，我没法确认。页脚标了这个差异，本页一律用本地实测值。
- Q：代码多是好事吗？会不会就是没管理好？
  A：这个问题很好，而且我不打算替他辩护。行数本身是中性的，但有两个旁证让我倾向于「不是失控」：一是 `AGENTS.md` 里明写「同一件事有两份实现就是 bug，哪怕两份都能跑」；二是 fix 类 commit 是 feat 类的将近 5 倍，说明项目已经进了稳定期高频修 bug 的阶段，不是在狂加功能。当然这只是旁证。
- Q：为什么要内嵌一整个 bash 和 46 个 coreutils？疯了吗？
  A：CH5 一整章讲这个，而且最后那页 benchmark 会给你看一个很诚实的结果——**小 payload 上 Rust 版反而慢 0.86 倍**，他们自己在文档里写了「若更慢，不要切换调用点」。先记住这块存在，理由等到 CH5。
- Q：Python 那 8.3 万行会随发布分发吗？
  A：不确定。snapcompact 那两万九是研究脚本，我没去核 `.npmignore` 和 package 的 `files` 字段，所以我在统计里把它单列，没并进「产品代码」。

**过渡到下一页**：153 万行，日均 155 个 commit，一个人——这个算术其实是对不上的。下一页告诉你缺的那一块从哪儿来。

## P8 · omp 的代码，有一部分是 omp 自己写的

**一句话主旨**：omp 在用 omp 开发 omp——全史 16,613 个 commit 里 2,564 个署名给它自己驱动的机器人，而贡献指南已经开始给这个机器人让路了。

**提词**：
- 上一页的算术对不上，缺的一块在这儿
- 左边五步回路：issue → omp 子进程 → 修 → PR → 合并
- 橙色虚线回到①：改好的 omp 下一轮接着用 [重]
- 右上署名条：8,807 / 2,564 / 1,339 / 其余 403 个身份
- CONTRIBUTING.md:28-32 念原文 [慢]
- 「别为自己要做的活开 issue，robomp 会当工单捡走」
- 玫红框：不能过度解读，同域同人分不出来 [停]
- 代价：机器人写的代码谁来 review

**怎么讲**：
上一页结尾我说算术对不上——72 万行 TS、18.5 万行 Rust、8.3 万行 Python、日均 155 个 commit，一个人。这一页给缺的那块。（停一拍）标题就是结论：**omp 的代码，有一部分是 omp 自己写的。**

左边这张图是完整的回路，五步，全部来自 `python/robomp/README.md` 的前 22 行，我照着走一遍。①有人在 GitHub 开一个 issue，robomp 先把它分类打标签——bug、documentation、question、enhancement、proposal、invalid、duplicate，七类。②它**起一个 omp 子进程**，注意这行小字：`omp --mode rpc`，也就是把 omp 当成一个可被程序驱动的服务跑起来，**每个 issue 开一个独立的 git worktree**。这里有个设计我很欣赏——下面那行：**PAT 不给 agent**，写回 GitHub 走一个单独的 sidecar 进程。也就是说 agent 有改代码的权限，但没有对外发言的凭证，这是很干净的一刀。③按标签分流：bug 和 documentation 会真的去复现、在新分支上修、跑验证；question 是发一条评论，四小时内没人反对就自动关掉；enhancement 只评论不动手。④开 PR，而且**格式是钉死的**——正文必须有 `## Repro`、`## Cause`、`## Fix`、`## Verification` 四段，加一句 `Fixes #N`。后续如果 issue 下面又有评论，它用 `--continue` **恢复同一个 omp session** 接着聊。⑤合并，代码进主干。

（停一拍）然后看这条橙色的虚线——从⑤绕回①，旁边写着「改好的 omp，下一轮接着用」。**这就是自举回路。** 这个词我想多说两句，因为它很容易被当成一句噱头。编译器的自举大家都熟：用 C 写第一版 C 编译器，然后用它编译自己。那个回路的意义在于——**你对自己的每一次改进，会立刻回到你自己身上**。omp 这里是同一个结构：他改进了 omp 的 bug 定位能力，下一个 issue 进来，robomp 用的就是改进后的版本，修得更准；修得更准，就有余力去改更难的地方。（停一拍）这就是上一页那个算术怎么对上的——**153 万行不是一个人手敲出来的，是一条回路跑出来的**。这也是我为什么把这页放在第一章的最后：前两页讲「多大」，这页讲「怎么可能这么大」。

再看右边这一栏。最上面这条堆叠柱是**全史 16,613 个 commit 的署名构成**，我把仓库 unshallow 之后重新数的。绿色最大那块，`me@can.ac`，Can Bölük 本人，**8,807 个，53%**。橙色这块，`omp@can.ac`，也就是 roboomp，**2,564 个，15.4%**。青色那块，Mario Zechner，**1,339 个，8.1%**——这就是我上一页说的，pi 时期的历史被完整带过来了。剩下灰色的是**另外 403 个提交身份**，全史一共 407 个。

（停一拍）中间这个玫红框是本页最有冲击力的一条，`CONTRIBUTING.md` 第 28 到 32 行，我念英文原文：**「Do not open an issue for work you are about to submit.」**——如果你打算自己实现某个改动，**不要先为它开 issue**。理由在下面：**robomp 会把「可行动的 issue」当成工单捡起来，可能并行做同一个修复，浪费算力和维护者时间。** （停一拍）我第一次读到这句是真的愣了一下。我们写了这么多年的贡献指南，「先开 issue 讨论再动手」几乎是所有开源项目的第一条规矩，理由是避免重复劳动。这里规矩被**反过来**了，理由**还是**避免重复劳动——只不过要避开的那个「重复劳动者」，不是另一个人类贡献者，**是项目自己的机器人**。协作规则第一次要为 AI 贡献者腾地方，这不是修辞，是白纸黑字的一条硬规矩。

（停一拍）但这条不能只讲光鲜面，代价必须一起讲，看下面琥珀色那个框——**同一份 CONTRIBUTING.md 的另一面**，第 38 到 51 行：**「AI agents are welcome as tools, not as unattended contributors.」** AI agent 欢迎作为工具，但**不欢迎作为无人看管的贡献者**。具体四条：把 agent 约束在议定范围内、**逐个文件审阅它改的东西**、亲自跑检查并验证行为、审完才准提 PR。还有更狠的两条——PR 正文**必须至少有一句你自己写的话**；以及「`bun check` 通过」**本身不算验证**。（停一拍）你把这两个框放在一起看，这个项目的立场其实非常清楚：**机器可以生产代码，但责任不能转移。**「你为这段代码负责，不管它是谁、是什么东西生成的。」

那问题就来了，也是我留给大家带走的问题：**机器人写的这 2,564 个 commit，谁 review 的？** 从公开信息看，答案是维护者本人——也就是那个已经写了 8,807 个 commit 的人。这就是自举回路真正的代价：**回路能把生产的吞吐放大，但没法把审阅的吞吐放大。** 你造得越快，瓶颈就越往 review 挤，最后压在同一个人的注意力上。这个项目的所有取舍——包括后面 CH6 那页 309 次「Stop.」的事故——某种程度上都是这个瓶颈的后果。

最后一句必须说，看底下这个玫红框——**这条不能过度解读**。`omp@can.ac` 和 `me@can.ac` 是同一个域名、同一个人，git 元数据**分不出来**哪些是「bot 自主提交并被合并」，哪些是「人用 omp 辅助写完之后署名给了 bot」。所以我能讲的是：**2,564 个 commit 署名给了项目自己的 bot 账号**；我**不能**讲：「这些代码是 AI 独立写成的」。这两句话差别很大，请大家引用的时候也用前一句。

**别漏了说**：
- 「自举」这个词要展开解释，用编译器自举打比方——不解释的话它听起来像噱头，解释了它就是本章最有分量的一句。
- 「PAT 不给 agent，写回走 sidecar」这个细节别跳，它是权限设计的一个漂亮范例，也呼应第一篇「护栏装在执行那一段」。
- `CONTRIBUTING.md:28-32` 要**念英文原文再翻译**，这是全场引用密度最高的一句，值得慢下来。
- **代价必须讲**：`:38-51` 那四条硬要求 + 「谁来 review」这个问题。只讲自举不讲代价，这页就变成布道了。
- 「回路放大生产，放大不了审阅」这句要说出口——它是本章接到全篇主张（把代价摊开）的接缝。
- 最后那个「不能过度解读」的免责一定要念完，别因为时间紧就砍掉。这是本篇诚实底线的一部分。
- 数字口径：16,613 是 **unshallow 之后的全史**，跟 research 笔记里 depth-200 窗口的 10,892 / 2,497 不是一回事，如果有人对着旧笔记问要能立刻分清。

**可能被问**：
- Q：15.4% 是不是就是说「15% 的代码是 AI 写的」？
  A：不是，两个偏差都有。一是 commit 数不等于代码行数，bot 的 commit 平均可能更小也可能更大，我没测；二是署名给 bot 不等于 AI 独立完成，同域同人分不出来。这个数只能读成「署名归属」。
- Q：robomp 修的都是些什么活？是不是格式化机器人？
  A：不是。我抽看了它的 commit 标题，长这样：`fix(mnemopi): anchored think stripping to leading blocks`、`fix(coding-agent): clear bash auto-background threshold timer`——是真的 bugfix，带具体子系统 scope 的。
- Q：这套东西我能抄吗？我们团队也想让 bot 自动修 issue。
  A：机制可以抄，`python/robomp` 是开源的，三万二千行，里面 issue 分流、worktree 隔离、sidecar 持凭证这几条都值得看。但**前提抄不了**：这个仓库的所有权和 review 权集中在一个人手上，他能承担「bot 提的 PR 全由我一个人过」这个成本。你们团队多半不能。CH7 那页「别抄的六条」里我会再提这一条。
- Q：那 403 个其他身份是真人吗？
  A：不全是。里面至少有五个 bot 账号（`oh-my-pi-bot`、`github-actions[bot]`、`robomp-bot` 之类），也存在同一个人多身份的情况——比如 `can1357` 和 `Can Bölük` 就是两条。所以我在 slide 上写的是「提交身份」不是「贡献者」，这个措辞是刻意的。
- Q：question 类 issue「四小时无人反对就自动关闭」，这会不会太粗暴？
  A：会，而且我觉得这是个明确的取舍——用一定的误关率换维护者的注意力。这是他自己的仓库、他自己承担后果，我不评价。但如果你抄，这个阈值一定要按你的社区规模重新定。
