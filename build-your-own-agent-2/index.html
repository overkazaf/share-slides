CH 2 · 循环

两层 while，四个判停点，没有迭代上限

真正的循环体 121 行，藏在 792 行文件里，而且是私有函数 —— 外面四个入口全是门面。

为什么要第二层

  • agent 在跑的时候用户又发了一条 —— 这条不能丢，也不能插队打断当前工具，只能排进 follow-up 队列，等这一轮收干净再转一圈

跑一半能插话

  • steering 队列让你在工具跑着的时候补一句「不对，先看 X」；已经发出去的工具调用照样跑完，不撤销

每轮重新取一次 key

  • 注释写得很直白：为了会过期的 token。一个长跑的工具阶段足够让 OAuth token 过期

最阴的一个 bug 被堵在这

  • 输出被截断时，工具参数是流式抢救解析出来的：schema 校验能过，内容是残的。所以整批直接不执行

CH 2 · 循环

中断和出错，都不靠抛异常

Ctrl-C 不是 throw，是把这一轮收成一条正常消息 —— 半截回复照样能渲染、能落盘。

回调的硬约束：不许抛

  • 几乎每个扩展点的注释都写着同一句 must not throw or reject；真抛了，上层伪造一条空的 assistant 消息把事件序列补齐，免得 UI 卡在半路

工具要抛，不要自己编错误

  • 工具接口文档反过来要求你抛异常，而不是在返回内容里写「失败了」—— 统一由内核转成模型能读懂的错误结果

迟到的进度回调会被丢弃

  • 长跑工具边跑边刷日志；一旦这次执行结算完，后到的进度更新直接忽略 —— 一个很容易漏掉的竞态

可以抄的一条

  • 把「取消」当成一种正常结局，而不是异常。 你的 UI、你的落盘、你的复盘全都会变简单

CH 2 · 循环

教科书 6 行，真实产品 121 + 517 行

多出来的代码，九成在解决同一件事：跑到一半，世界变了。

这一页就是本讲的中心论点

  • 教科书循环解决的是「怎么把工具结果喂回去」；真实循环九成代码在解决「跑到一半，世界变了」

自己造的时候照这个顺序补

  • 先有中断，再有插话，再有压缩，最后才轮到并行 —— 前两个不补，做出来只是个脚本

一条反向差异

  • 教科书爱加 max_steps，pi 刻意不加：停不停交给宿主判断和用户的 Ctrl-C —— 这是取舍，不是疏忽

留个把柄

  • 那个「宿主喊停」的钩子，全仓只有测试在用，产品路径没接 —— 设计留了口，产品还没用上

CH 3 · 会话

整棵树，只靠一个字段

文件里从不存「children」；分叉不是复制历史，是把叶子指针挪回去。

为什么值得做成树

  • 回到三步之前换个思路，旧那条不删；压缩、分支摘要都能当成普通条目挂上去 —— 复盘时整个决策过程都在

一个真实的缺口（可以当教训讲）

  • 产品路径的叶子指针不落盘：跳到旧节点后如果什么都不写就退出，下次打开会回到文件最后一条所在的分支
  • 只要之后写了任何一条，就自然落回正确分支 —— 所以日常用不出问题，但它确实是个洞

抄走这条

  • 「当前位置」是状态，不是日志。 想只用事件日志表达它，就得为它专门发明一种事件

CH 3 · 会话

全同步写 JSONL —— 这是故意的

用「慢一点」换一个强不变式：函数返回时，这一行已经在磁盘上了。

为什么 JSONL 值得抄

  • 人能读、能 grep、能 diff、能手改；出事故时不需要专用工具就能验尸。数据库是后来才需要的

  • 先落盘再渲染，别反过来
  • 空会话不建文件 —— 一个小到不值一提、但用起来天天有感的产品细节

CH 4 · 上下文

内核自带的上下文，只有 1,311 token

而它自己项目里那份 AGENTS.md 是 2,683 token —— 你写的比它带的多一倍。

先看这个数，再谈优化

  • 内核 1,311 token 是个基准线。你的 agent 如果开局就吃掉一万 token，多半不是模型的问题

环境信息只给一行

  • 没有日期、没有 OS、没有 git 分支 —— 需要就让它自己用 bash 去查，而不是每轮都塞给它

这一页要念出来的一句

  • system prompt 的成本不在长度，在「每一轮都要重付一遍」。所以它宁可少给，让模型按需去取

压缩的难点不在摘要，在切在哪

切错一刀，工具调用和它的结果就被劈散 —— 所以它有一张合法切点白名单。

CH 4 · 上下文

SKILL 的秘密：结构体里没有 content 字段

常驻上下文里只放名字、描述、文件路径三行；正文什么时候读？模型自己用 read 去拿。

这是最容易抄的一条

  • 不需要任何框架：一个目录 + 每个文件写好 description + 让模型自己 read。你今天下午就能给自己的 agent 加上

描述比正文重要

  • 模型只靠那一句 description 决定要不要展开 —— description 写砸了，正文写得再好也永远不会被读到

SDK 那套反而有 content

  • 但依然不进 prompt —— 字段有没有是实现细节，「常驻只放索引」这条语义两边一致

写了 7 个工具，默认只给 4 个

所谓「模糊匹配」，就是两次 indexOf

没有编辑距离、没有打分、没有模型兜底 —— 只有一次确定性的字符归一化，然后再找一次。

「不做权限弹窗」成立，而且比宣传更彻底

  • 抄那 162 行没意义，抄「agent 每干一次蠢事就往里加一条」这个机制

第 ⑫ 条的纪律很重要

  • 评测分数低只当观测，不算测试失败；硬断言只留给基础设施契约 —— 否则评测会退化成又一个红色的 CI

一句话收口

  • 这 12 条没有一条是关于模型的。这正是上一讲那句话的注脚：模型决定上限，harness 决定你能兑现多少
