## 2. Anthropic《Building Effective Agents》

**[A] 发布日期：2024-12-19**
- 出处：https://www.anthropic.com/engineering/building-effective-agents
- 作者：**Erik Schluntz（页面署名 "Erik S."）与 Barry Zhang**
- Hacker News 讨论：https://news.ycombinator.com/item?id=42470541

### 2.1 核心区分（原文引用）

> "**Workflows** are systems where LLMs and tools are orchestrated through **predefined code paths**."
>
> "**Agents** are systems where LLMs **dynamically direct their own processes and tool usage**, maintaining control over how they accomplish tasks."

### 2.2 基础构件

**Augmented LLM**（增强型 LLM）= LLM + retrieval + tools + memory，被定义为「the basic building block of agentic systems」。关键点是模型**主动**使用这些能力：自己生成检索 query、自己选工具、自己决定留什么。

### 2.3 五种 workflow 模式（**确切名称，务必逐字使用**）

1. **Prompt chaining**（提示链）
2. **Routing**（路由）
3. **Parallelization**（并行化）
4. **Orchestrator-workers**（编排器—工作者）
5. **Evaluator-optimizer**（评估器—优化器）

> ⚠️ 常见错误：网上很多中文/英文二手文章写成「六种模式」（把 Agent 本身算进去），或把 `Orchestrator-workers` 写成 `Orchestrator-worker`（少 s）。以官方页面为准是 **5 种 workflow + 1 种 autonomous agent**。

### 2.4 核心主张

> "When building applications with LLMs, we recommend finding the **simplest solution possible**, and only increasing complexity when needed."

**一句话贡献**：这篇文章第一次把「agent」从营销词还原成工程分类学——先问「这真的需要 agent 吗」，多数场景一个 workflow 就够；并给出了 5 个可直接落地的组合模式命名，成为后续两年的通用词汇表。

### 3.3 规范版本演进（**[A] 全部来自 GitHub Releases，可直接核对**）

```
2024-10-07   （最早的预发布 tag）
2024-11-05   初版规范
2025-03-26   OAuth 2.1 授权 + Streamable HTTP 传输（HTTP+SSE 开始弃用）
2025-06-18   elicitation、结构化工具输出、MCP-Protocol-Version 头
2025-11-25   OIDC Discovery、icons、增量授权、URL elicitation、实验性 tasks
2026-07-28   ★ 最大规模改版：MCP 彻底无状态化
```
出处：`gh api repos/modelcontextprotocol/modelcontextprotocol/releases`

**2026-07-28 版本的重大变更**（[A] 官方 changelog：https://modelcontextprotocol.io/specification/2026-07-28/changelog）：
1. **移除协议级 session 和 `Mcp-Session-Id` 头**（SEP-2567）
2. **移除 `initialize` / `notifications/initialized` 握手**，每个请求在 `_meta` 里自带协议版本与 client capabilities（SEP-2575）—— 这是 MCP 从「有状态连接」转向「无状态 HTTP 语义」的分水岭
3. 新增 `server/discover` RPC 用于版本/能力协商
4. 用 `subscriptions/listen` 单一长连接替代 HTTP GET + `resources/subscribe`
5. 引入 **MRTR（Multi Round-Trip Requests）**，用 `InputRequiredResult` 替代服务端主动发起的 `roots/list` / `sampling/createMessage` / `elicitation/create`
6. **弃用 Roots、Sampling、Logging 三大特性**（SEP-2577，12 个月弃用窗口）
7. 弃用 OAuth 2.0 动态客户端注册（RFC 7591），改推 Client ID Metadata Documents
8. 建立正式的特性生命周期与弃用政策（Active / Deprecated / Removed）

**一句话贡献**：MCP 把「AI 接工具」从 N×M 的定制集成变成 1×N 的协议问题；一年内被最直接的竞争对手（OpenAI、Google）先后采纳，两年内交给中立基金会治理——这是这一轮 agent 浪潮里唯一真正做成的「事实标准」。

## 5. Agent Skills / SKILL.md

### 5.1 首次发布

**[A] 2025-10-16** — 两篇同日发布：
- 产品公告：https://claude.com/blog/skills （原 `anthropic.com/news/skills`，308 跳转）
- 工程博客：https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills
- 交叉验证：Claude Code `2.0.20` 于 **2025-10-16T16:01:05Z** 发布，changelog 写 "Added support for Claude Skills"
- 仓库 `anthropics/skills` 创建于 **2025-09-22**（[A] GitHub API），即公开前约三周开始准备

**定义**：Skill 就是**一个文件夹**，里面有一个 `SKILL.md`（YAML frontmatter 指定 `name` + `description`，正文是 Markdown 指令），可以再附带脚本和资源文件。

**发布时的可用范围**：Claude apps（Pro / Max / Team / Enterprise）、Claude Developer Platform（Messages API + `/v1/skills` 端点）、Claude Code（通过 plugin 或手动放到 `~/.claude/skills`）。

### 5.2 核心机制：Progressive Disclosure（渐进式披露）

工程博客原文表述（**这是最适合上 PPT 的机制描述**）：

> "**Progressive disclosure** is the core design principle that makes Agent Skills flexible and scalable. Like a well-organized manual that starts with a table of contents, then specific chapters, and finally a detailed appendix, skills let Claude load information **only as needed**."
>
> "Agents with a filesystem and code execution tools don't need to read the entirety of a skill into their context window... This means that the amount of context that can be bundled into a skill is **effectively unbounded**."

三层加载：
1. **启动时**：只加载所有 skill 的 `name` + `description`（几十 token 量级）
2. **任务匹配时**：加载完整 `SKILL.md` 正文
3. **需要时**：agent 自己去读附带的脚本、参考文档、数据文件

**为什么这是范式级的**：它把「知识」从 context window 里搬到了**文件系统**上，用 agent 自己的读文件能力做惰性加载。等于承认 context window 不是知识容器，而是**注意力预算**。

### 5.3 开放标准化

**[A/B] 2025-12-18** — Anthropic 把 Agent Skills 作为**开放标准**发布，规范与 SDK 放在 **agentskills.io**。

## 9. Anthropic 官方 context engineering 博客

**[A] 2025-09-29** — 《**Effective context engineering for AI agents**》
- 出处：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- 作者：Anthropic Applied AI 团队 —— **Prithvi Rajasekaran、Ethan Dixon、Carly Ryan、Jeremy Hadfield**；贡献者 Rafi Ayub、Hannah Moran、Cal Rueb、Connor Jennings
- **发布日与 Claude Code 2.0 / Agent SDK 更名同一天（2025-09-29）**——这三件事同日发生，本身就是「harness 工程化」的宣言

### 9.1 核心论点

**定义切换**：
- **Prompt engineering** = 「怎么写、怎么组织给 LLM 的指令」——一次性的、离散的任务
- **Context engineering** = 「策划并维护那组最优 token 集合」——覆盖 system instructions、tools、外部数据、消息历史的**全部**内容，是**迭代的、持续的**

**关键概念（PPT 用词表）**：

| 概念 | 含义 |
|---|---|
| **Attention budget（注意力预算）** | LLM 的 token 处理能力是有限资源，超过阈值性能就退化。context 不是仓库，是**预算** |
| **Context rot（上下文腐化）** | 随着 context window 变大，信息检索准确率**下降** |
| **Compaction（压缩）** | 总结对话历史以重置 context window，同时保留关键细节 |
| **Structured note-taking（结构化记笔记）** | agent 把持久记忆写到 context window **之外**（文件） |
| **Sub-agent architectures（子代理架构）** | 专门的子 agent 处理聚焦任务，只把**浓缩后的摘要**返回主 agent |
| **Just-in-time retrieval（即时检索）** | 运行时动态加载数据，而不是预先全量塞进去 |

**为什么重要**：这篇文章把「context window 变大就够了」这个幻觉打掉，明确说 —— **更大的窗口不等于更多的可用信息**。整个 Skills（progressive disclosure）、Explore subagent、code execution with MCP、compaction，都是这一论点的工程化落地。

### 10.3 长任务 harness 的工程化（**这是「范式转移」最直接的证据**）

**[A] 2025-11-26 — 《Effective harnesses for long-running agents》**
https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

「harness」定义：让 agent 跨**多个 context window**持续工作的框架——特化 prompt + 环境管理 + 工具访问的组合。

推荐结构：
1. **Initializer agent**：第一个会话负责搭地基（feature list、进度追踪文件、git 仓库）
2. **Coding agent**：后续每个会话只做**一个 feature**，做完保持代码干净可交接
3. **Feature list**：结构化 JSON，**200+ 条**明确的 feature 规格，标记 passing/failing，防止 agent 过早宣布完成
4. **Progress documentation**：每个会话结束写 commit + 更新进度文件
5. **Testing tools**：用 Puppeteer 做端到端浏览器验证，而不是只靠单测

**[A] 2026-03-24 — 《Harness design for long-running application development》**
https://www.anthropic.com/engineering/harness-design-long-running-apps
作者：**Prithvi Rajasekaran**（Anthropic Labs，也是 context engineering 那篇的第一作者）

核心：**受 GAN 启发的三 agent 架构** —— **Planner / Generator / Evaluator**
- Planner：把一句话需求扩成详细产品规格（含 AI 特性与视觉设计指引）
- Generator：按与 evaluator 协商出的 "sprint contract" 增量实现
- Evaluator：用浏览器自动化**测跑起来的应用**，按标准打分并给出反馈；**evaluator 从未见过生成过程，因此没有沉没成本偏见**

问题陈述（很适合上 PPT）：让 LLM 生成代码再自己评自己的输出，它会自信地夸自己，哪怕质量明显平庸。**解法是结构性分离：一个 agent 建，另一个 agent 判。**

**成本/质量对照表（[A] 原文数据，极适合上 PPT）**：

| 任务 | harness 类型 | 耗时 | 成本 |
|---|---|---|---|
| Retro Game Maker | 单 agent（solo） | 20 分钟 | **$9** |
| Retro Game Maker | 完整 harness | 6 小时 | **$200** |
| DAW 音频应用 | 升级版 harness（v2） | 3 小时 50 分 | $124.70 |

原文结论：完整 harness **贵 20 倍以上**，但产出的应用核心功能可用，而 solo 跑出来的是坏的。

**[A] 2026-03-25 — 《How we built Claude Code auto mode》**
https://www.anthropic.com/engineering/claude-code-auto-mode

在「每次都问」（审批疲劳）与「完全关闭安全阀」之间引入第三条路：**把审批委托给基于模型的分类器**。

两层防御：
- **输入层**：服务端 prompt-injection 探针在 agent 处理工具输出前扫描，发现敌意内容就加警告
- **输出层**：transcript classifier 在执行前评估每个动作。两阶段：先一个快速单 token 过滤器，被标记才走 chain-of-thought。**分类器故意「对 reasoning 失明」**——只看用户消息和工具命令，防止 agent 用推理把分类器说服

三级 allowlist：安全工具直接执行 → 项目内编辑跳过分类 → 只有风险动作（shell 命令、外部操作）才进分类器。被拦截时 **deny-and-continue**（换个安全做法重试，而不是停下来）。

**[A] 真实流量指标（10,000 次调用）**：
- **假阳性率 0.4%**（被错误拦截的安全动作）
- **假阴性率 17%**（被放行的危险动作）

Anthropic 自己的评价：17% 的漏检率诚实但可接受——远好于「完全没护栏」，但**不如认真的人类 review**。

## 11. 范式转移：从「让模型自己想办法」到「工程化 harness」

这是整条时间线最该讲清楚的一件事。可以分成五幕：

### 第一幕（2023 — 2024 上半年）：把智能塞进 prompt
- **代表事件**：Devin 发布（2024-03-12），SWE-bench 13.86%
- **信念**：只要模型够强 + prompt 够好，agent 就能自主完成任务
- **实际情况**：SOTA 只能解决 **1.96%** 的真实 GitHub issue（SWE-bench 论文，2023-10-10 预印本）。Devin 的 13.86% 是在 **25% 随机子集**上的 unassisted 成绩
- **暴露的问题**：demo 惊艳、复现困难；评测口径不透明；没人能说清楚「为什么这次成了、下次没成」

### 第二幕（2024 年末）：承认「agent」不是万能锤
- **代表事件**：《Building Effective Agents》（2024-12-19）
- **关键动作**：把 **workflow**（预定义代码路径）和 **agent**（模型自主决定流程）**明确分开**，并给出 5 个可组合的 workflow 模式命名
- **核心主张**："finding the simplest solution possible, and only increasing complexity when needed"
- **意义**：这是行业第一次公开说「大多数场景你不需要 agent」。**从追求自主性，转向追求可控性**

### 第三幕（2024-11 — 2025 上半年）：把「接工具」变成协议问题
- **代表事件**：MCP 发布（2024-11-25）→ OpenAI 采纳（2025-03-26）→ Google 采纳（2025-04-09）
- **关键动作**：把 N×M 的定制集成变成 1×N 的协议。同期 Google 推 A2A（2025-04-09）补上「agent↔agent」这一层
- **意义**：agent 能力的边界从「模型知道什么」变成「模型能连上什么」。**基础设施开始与模型解耦**

### 第四幕（2025 下半年）：harness 成为一等公民 —— **真正的转折点**

**2025-09-29 这一天，Anthropic 同时做了三件事**：
1. 发布《Effective context engineering for AI agents》
2. 把 **Claude Code SDK 改名为 Claude Agent SDK**（"给你的 agent 一台电脑"）
3. 发布 Claude Code 2.0（checkpoints、subagents、hooks、后台任务）

这三件事合起来是一个宣言：**agent 的能力上限不再主要由模型决定，而是由包裹模型的那层工程（harness）决定。**

具体的信念替换：

| 旧信念 | 新工程实践 | 落地时间 |
|---|---|---|
| context window 越大越好 | **attention budget** + context rot；compaction、just-in-time retrieval | 2025-09-29 |
| 把所有知识写进 system prompt | **Skills + progressive disclosure**：知识放文件系统，按需加载，容量「effectively unbounded」 | 2025-10-16 |
| 把所有工具定义前置塞进 context | **Tool Search Tool**（省 85%）、**code execution with MCP**（150k → 2k tokens，省 98.7%） | 2025-11-04 / 2025-11-24 |
| 一个 agent 从头干到尾 | **subagents**（独立 context，只回摘要）→ **Explore subagent** → **agent teams** → **dynamic workflows**（数百并行） | 2025-07-24 → 2026-05-28 |
| agent 行为靠 prompt 约束 | **hooks**（确定性代码在生命周期节点强制介入） | 2025-06-30 |
| 每次操作都问用户 | **auto mode**：分类器代替人类审批（FP 0.4% / FN 17%） | 2026-03-25 |
| 扩展能力靠改 prompt / 改代码 | **plugins**：把 commands + agents + hooks + MCP servers 打包分发 | 2025-10-09 |

**用一句话概括这一幕**：以前是「怎么跟模型说话」（prompt engineering），现在是「怎么给模型搭工位」（harness engineering）——文件系统、沙箱、工具目录、检查点、权限分类器、子代理调度、验证回路。

### 第五幕（2025 末 — 2026）：harness 自身被拆解和产品化

- **结构化**：长任务 harness 从「一堆技巧」变成**明确架构**——Initializer/Coding（2025-11-26）→ **Planner / Generator / Evaluator**（2026-03-24）。核心洞察是「让模型自评会自我吹捧」，所以要**结构性分离生成与评判**
- **分层化**：**brain（模型）/ hands（沙箱与工具）/ memory（会话与检查点）解耦**，每层独立演进、独立替换（2026-04-08）
- **托管化**：Managed Agents 把 agent loop、工具执行、沙箱、状态持久化打包成 REST API——**harness 本身变成了云服务**（2026-04）
- **规模化**：dynamic workflows 让单会话编排「数十到数百个并行 agent」（2026-05-28）；Cursor 3.0 的 Agents Window 做跨仓库、跨环境的 agent 舰队管理（2026-04-02）
- **协议成熟化**：MCP 交给中立基金会（2025-12-09），并在 2026-07-28 做无状态化重构、弃用 Roots/Sampling/Logging——**协议开始为「大规模、多实例、无状态的 agent 集群」而设计**，而不是为「一个桌面 App 连一个本地 server」

### 反向张力（**最有意思的收尾，但需要核实**）

2026 年出现了一个耐人寻味的反向信号：**harness 开始给模型让路**。

- **[C]** Boris Cherny 称，为 Opus 5 **删掉了 Claude Code 80% 以上的系统提示，模型反而表现更好**
  - 二手来源：https://finance.biggo.com/news/7df48019614f68c0
  - **务必回溯一手播客/访谈后再用**
- **[A] 佐证**：Claude Code `2.0.30`（2025-10-30）**主动弃用了 output styles**，理由是改用 `--system-prompt-file` / CLAUDE.md / plugins——即**收缩内建 scaffolding，把控制权交回给用户和模型**

这暗示第六幕可能是：**harness 从「补模型的短板」转向「给模型让路」**——脚手架不是越多越好，而是要随模型能力上升而**主动瘦身**，只保留模型确实做不好的部分（权限、沙箱、状态持久化、验证回路、并行调度）。
