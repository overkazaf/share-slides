## P13 · 技术全景：Agent 技术栈七层

**一句话主旨**：模型是主项、harness 是次项，但次项才是你能攥在手里的那部分。

**怎么讲**：
这是全场的地图，后面十一页都会回到这张图上来。[手指中间那一摞]

中间这一摞是七层，从下往上看。最底下 L1 是模型本身，我特意画成了虚线灰框——因为它是你租来的，不是你造的。L2 模型接入层，管 provider 抽象、流式、缓存、重试、token 计数。L3 工具层，工具集设计和权限沙箱。L4 上下文层，塞什么进去、塞不下怎么办。L5 编排层，主循环、判停、并发、会话树、DAG。L6 可扩展层，SKILL、Hook、MCP、子代理。最上面 L7 交互层，TUI、IDE 插件、审批和打断。

左边这一列小字，是每层要回答的一个问题；右边这一列，是每层最常见的翻车姿势。比如 L4 那一行右边写着"上下文腐化：越长越蠢，中间的内容被无视"，这个第 18 页会展开。再看左边这个粉色的大括号，从 L2 一直括到 L6，竖着写着 HARNESS——这五层合起来就是今天的主角。底下那行小字也说了：这一章自下而上把 L2 到 L6 走一遍；L1 不碰，那是另一个行业；L7 决定体验，但不决定能力。

下面这段 takeaway 我要慢慢念，两个方向的证据我都摆出来了。[放慢]

证据一：十六个模型、一百八十个修 bug 任务，只换一个变量——编辑工具的格式。Grok Code Fast 1 从 百分之六点七，涨到 百分之六十八点三。全体平均加十五个百分点。但请注意后面这半句：越弱的模型收益越大。这是第三方博客的控制变量实验，Can Bölük 的《The Harness Problem》。

证据二：Terminal-Bench 官方榜，我们从榜上筛出二十二个模型，看它们各自换 harness 前后的分差——中位数只挪动 五点三九 分，二十二个里有七个挪动超过十分，最大的挪了 二十点九 分。而同一个 harness 换模型，极差是 七十点七 个百分点。[停一下] 还有个更扎心的例子：Gemini 3 Pro 套一个通用 harness 拿到 七十三点九三，套 Google 自己家的 Gemini CLI，只有 六十五点八四——自家工具输给通用工具八分。

所以诚实的结论是这句：模型是主项，harness 是不可忽略的次项，大约是模型效应的四分之一量级。我不想把它吹成"harness 万能"——中位数只有五点几分，这个数我也照样念出来了。但下一句才是我真正想说的：主项买不到差异化，因为大家用的是同几个模型；次项才是你能自己攥在手里的那部分。

**别漏了说**：
- "越弱的模型收益越大"必须念，不然 6.7→68.3 会被听成 harness 神话。
- 中位数 5.39 必须念，别只念最大值 20.90 —— 只念极值就是标题党。
- 两个数字口径不同：①是第三方控制变量实验，②是官方榜横向对比。

**可能被问**：

  A：不是。榜上是不同提交方各自的 harness，框架、工具集、运行预算都不一样。所以我只敢说"约四分之一量级"，不敢说精确倍数。这一点我讲的时候就承认了。

## P14 · Harness：包在模型外面的那台机器

**一句话主旨**：内核做成无状态纯函数，有状态的事全靠外层挂上去。

**怎么讲**：
上一页我们说中间五层统称 harness，这一页我们把这个词落到实处。

harness 这个词原意是马具、也是试验台，在这儿指的是：除了模型权重之外，让模型能真正干活的全部工程。pi 干脆把它写进了项目定位——"Pi Agent Harness"，而且真有一个类就叫 AgentHarness。

看左边这张图，是三层套娃，从外往里看。最外面这个青色虚线框是产品层 pi-coding-agent：七个内置工具、TUI、扩展、CLI、session 命令。往里一层紫色实框，就是 AgentHarness 编排层，右上角标着 1185 行——这是 agent-harness.ts 这一个文件的行数，不是整个 harness 的代码量。

再往里，最中间这个绿色粗框，是内核 agent-loop.ts 里的 runAgentLoop。请重点看它下面这两行小字：无状态纯函数、事件驱动、双层 while；以及——它只管"转圈"，不管存盘、不管压缩、不管权限。[停一下] 这就是整页的核心。

那些它不管的事，都在它上下四条带子里。上面这条是 Session 树持久化：JSONL v3 格式、十一种条目、只追加，从不原地改写。下面这两条，左边 Compaction，上下文满了自动瘦身；右边 Turn Snapshot，每轮冻结配置、做存档点。最底下这条橙色的是 Hook 总线：二十一种事件，其中十种的返回值能直接改变流程。

右边四张卡是四个细节。快照那张：每轮开始冻结 messages、tools、model、systemPrompt——你跑到一半改设置，本轮不受影响，下一轮才生效。Hook 那张列了十个切点能干什么，最狠的是最后一条，能完全接管压缩，不用它自带的。持久化那张有个我很喜欢的设计：扩展在忙的时候发起的写，要排队等存档点，这样记录才可重放。最后一张，相位状态机挡并发——idle、turn、compaction、branch_summary、retry 五个相位，不在 idle 就拒收并抛 busy。注意它专门强调了：不是一个布尔忙标志位。

下面这句可借鉴我就不念了，就是刚才那条分界线：你自己造 agent 时，最值得先想清楚的，就是这条线画在哪。

**别漏了说**：
- 1185 行是 agent-harness.ts 单文件的行数，说清口径，别被听成整个项目。
- "内核只管转圈，不管存盘/压缩/权限"是本页的骨头，必须单独停顿强调。
- 21 种事件里只有 10 种能改流程，其余是纯通知，这个区分不能省。
- 相位状态机 vs 布尔标志位的对比，是这页最容易被当废话跳过、但最实用的一条。

**可能被问**：
- Q：五个相位比一个 busy 布尔好在哪？
  A：能区分"在跑一轮"和"在做压缩"，拒绝的时候能告诉调用方为什么忙；而且相位迁移是可枚举的，能测。布尔位只能告诉你"现在不行"。
- Q：21 个 hook 事件是不是太多了？
  A：多是有代价的，每个事件都是一份要长期维护的公开契约，改一次就可能破坏别人的扩展。这个取舍我不替 pi 辩护——它选了扩展性优先。
- Q：Hook 能接管压缩，会不会让行为不可预期？
  A：会。能力越强的切点，出问题越难查。这是扩展性的固有代价。

## P15 · Loop Engineering：一圈里到底发生了什么

**一句话主旨**：主循环真正难的不是循环，是中断、插队、判停和截断。

**怎么讲**：
上一页那个绿框我说它"只管转圈"，现在我们把它剖开。

教科书里的 agent loop 就一行：while true，调模型，跑工具。真实实现里，难的全在中断、插队、判停、截断、并发和错误恢复。pi 的主循环是双层 while，我觉得这个设计值得抄。

顺着中间这条主链往下走。①取插队消息 steering——用户在 agent 干活途中补的话，下一轮开头就注入，不用打断重来。②流式请求 LLM，注意这行小字：每轮重新解析 API key，因为 OAuth 会过期；边流边渲染；全程可 abort。③出错或被中断？是的话立刻收尾，不做任何补救性猜测。④这一步是我最想让大家记住的：有 tool_call 吗，输出被截断了吗——如果被截断，参数就可能不完整，那就全批判失败让模型重发，而不是拿半个参数去跑。⑤执行工具，并行还是串行：参数校验和权限钩子始终串行，只有 execute 并发；结果按源顺序写历史。⑥prepareNextTurn 重建快照，此刻才允许换模型、换上下文、改思考档位。⑦判停，还有后续任务吗。

再看两条回边。绿色这条是内层，处理"回答→调工具→再回答"这条链路，还有插队。黄色这条是外层，管的是"agent 已经收工了，用户又追加了活"。右边两个出口盒：红的是立即终止，error 或 aborted；绿的是 agent_end，交付结果。右下角这句小字我要念一下——三种排队语义做进内核，这个挺罕见的。

右边三张卡。判停有四种收敛条件，其中第三条有个细节：工具返回 terminate 信号时，pi 要求这一批里每一个结果都 terminate 才停。三个坑：一，没有超时，pi 把超时交给工具自己管，bash 工具的 timeout 默认不设，这个你得自己想清楚；二，并行写同一个文件，按真实路径串行化，软链接同锁；三，报错就是养料，把字段路径带回去喂模型，比一句"执行失败"有用一百倍。

**别漏了说**：
- ④截断整批判失败——这是最容易被听众当成"太保守"的设计，要解释半个参数的危害。
- ⑤"校验和权限串行、只有 execute 并发"，一句话说清并发边界在哪。
- 内层/外层分工要点明：内层是工具链，外层是"收工后又来活"。
- bash 默认不设超时是 pi 的选择，不是最佳实践，要按坑讲、不要按亮点讲。

**可能被问**：
- Q：三种排队语义具体是哪三种？
  A：页面上只有这一句话，我没在图里列全。这个我会后补。
- Q：默认不设超时不是很危险吗？
  A：危险，我就是把它当坑列的。两边都说一下：内核统一超时会误杀长任务，交给工具管则容易漏——pi 选了后者，你可以选前者，但要显式地选。
- Q：截断就整批失败，会不会浪费一次调用？
  A：会浪费。但拿一个被截掉一半的 JSON 参数去执行写文件或跑命令，代价大得多。
- Q：UI 按完成顺序、历史按源顺序，会不会让人看着乱？
  A：这就是取舍——体验要实时，记录要可重放。两个顺序服务两个目的。

## P16 · Graph Engineering：向后是一棵树，向前是一张图

**一句话主旨**：会话树不是历史记录，是可以回退和重跑的可执行状态。

**怎么讲**：
上一页的循环只有一个方向——往前。这一页补两件循环解决不了的事：走错了怎么退回去，多条路怎么同时走。

先看左边这棵树。它是 append-only 的 JSONL，每条都带 parentId，从不原地改写。从上往下：session 头，记着版本 v3、cwd、父会话；然后 user 消息、assistant 带 tool_call、tool_result，这是一个标准回合。再往下这个紫色菱形是 compaction 条目——注意它旁边这行小字：读上下文的时候回溯到这里就停，前面的历史被摘要顶替了。这是第 19 页的伏笔。

再往下这个青色节点写着"在这里改主意了"，于是树分了叉。左边那条灰的是旧分支，没删，只是不在当前路径上；右边这个带实心点的是当前叶子，而且叶子指针本身也是一条持久条目。右边这段橙字很重要：切分支的时候，被放弃的那一条会被压成一段摘要注入进来，不至于"白干一场"。最底下一行说明有三种分叉语义：整棵复制、只保留到某一条、回到某条 user 消息之前。

右边这张是往前的图。入口拆解任务，散成三个并行子任务，各自独立上下文；汇聚去重这一步——注意括号里写着"普通代码即可"，不是什么都得让模型干；然后进对抗式验证，不过就打回重来，就是这条红色虚线回边。旁边这句是关键：回边由代码控制，不是模型说了算，所以循环次数、退出条件都可测。

下面这两个框是取舍对比。左边自主循环：路径模型现场决定，适合没法预先枚举的探索，代价是贵、难复现、会跑飞——就是那句"我不知道要查哪几个文件，你自己找"。右边 DAG 编排：路径你写死、模型只填节点，适合形状已知的批量工作，红利是并发、可重试、可断点续——"这 40 个文件，每个都按同一套流程走一遍"。我不打算替你们选，现实里几乎总是混合：先用 agent 探索出清单，再用 DAG 把清单批量做掉。oh-my-pi 干脆把它做成了一个扩展，用 YAML 描述 DAG，跑多 agent 流水线。

**别漏了说**：
- "只追加、从不原地改写"是所有回退能力的前提，不能一带而过。
- 旧分支没删、只是不在路径上——这是"可执行状态"而非"历史记录"的关键证据。
- 汇聚去重"普通代码即可"，提醒大家别什么都塞给模型。
- 自主循环 vs DAG 两边都摆出来，不要暗示 DAG 更高级。

**可能被问**：
- Q：只追加不删，磁盘会不会撑爆？
  A：确实只增不减。具体的体积数据页面上没有，我也没实测过，这个会后补。
- Q：被放弃的分支压成摘要注入，会不会把新分支又带偏？
  A：有这个风险。页面上只说了它的好处——不至于白干一场。坏处是你刚否掉的思路，又以摘要的形式回到上下文里了。要不要注入，我觉得应该可配。
- Q：DAG 编排和多智能体是一回事吗？
  A：不是，但相关。第22、23 页专门讲 workflow 模式和多智能体。
- Q：三种分叉语义分别用在什么场景？
  A：图上只列了名字。我能确定的是"回到某条 user 消息之前"对应最常见的"重问一次"，另外两种的具体触发场景我会后补。

## P17 · Loop 派 vs Graph 派：争的不是数据结构，是「可停可续的最小单位」

**一句话主旨**：这场争论的题面不是「循环 vs DAG」，是「运行的权威状态是 transcript 还是显式 state」——落到实处就是「这一轮结束了，谁说了算」。

**怎么讲**：
先把伪题面挡掉。[慢] 很多人把这件事说成「循环 vs DAG」，这个说法本身就是错的：**LangGraph 从来就不是 DAG**，它是 Pregel 消息传递模型，支持环。所以别拿数据结构说事。

真正的分歧在最上面这行：**运行的「权威状态」到底是什么**。左边循环派认的是 transcript——一条对话轨迹就是全部真相；右边图派认的是一份显式的 state schema。

这个分歧一落地，「一轮什么时候结束」就有了两个互不兼容的答案。[指左] 循环派：模型这一轮不再要 tool_call 就算完，原文是 "until it produces a response with no tool calls"。[指右] 图派：所有 node 都 inactive、没有消息在途才算完——**判停从模型的判断变成了图算法的不动点判定**。这句是这一页的题眼。

接着往下就都是推论了。最小单位不一样：循环是一个 turn，图是一个 node / super-step。图派把 checkpointer 做成强制项——原文就一句 "A checkpointer is mandatory."——换来的是 replay 和 fork。循环派的判停也不是玄学，是五种可枚举的 subtype。

两边我都摆了自承的弱点，这是我最想让你们看的：[指玫红条] 循环派自己说 "non-deterministic between runs, even with identical prompts"；图派自己说 resume 的时候 node 从头重跑、副作用必须幂等，而且 replay 会重新调 LLM、结果可能不同。**所以在「结果可复现」这件事上没有赢家，我不替任何一方吹。**

下面五张卡是五个真分歧。第三张我特意标红了：**loop 和 graph 的成本对照，公开数据不存在**。你可能听过 agent 是 chat 的 4 倍、multi-agent 是 15 倍——那是 agent vs chat、多 vs 单的口径，拿来说 loop vs graph 就是偷换。这条我判不了，我就说判不了。

最后这条橙色的是最大的伪分歧：**两边都是图，区别只在于图画在未来的执行上，还是画在过去的历史上。** pi 的 /rewind + /branch、LangGraph 的 replay + fork、Cursor 的代码快照，是同一族能力的三种落点。

**别漏了说**：
- 「LangGraph 不是 DAG」必须说，否则和上一页矛盾——**上一页那个「Orchestration DAG」指的是狭义的确定性编排（比如 oh-my-pi swarm 的 YAML DAG），那确实是 DAG；LangGraph 是更一般的显式状态图。两个不是一个东西。**
- 「token 的账判不了」要主动说，别等人问。
- 第五张卡（人插在哪一刀）是唯一真正不可互相替代的差别：图能卡在一个动作**中段**，循环只能卡在动作**之间**。
- 这是全场第二场对撞，第一场在后面（多智能体之争）。可以提一句「等会儿还有一场」。

**可能被问**：
- Q：那我到底该选哪个？
  A：底下那句就是我的判据——有便宜的 verifier 就用循环；verifier 只能是人或合规，就用图。图的作用不是让 agent 更聪明，是让人能在正确的位置插进去。
- Q：你这个判据站不住吧，verifier 是可以造出来的啊？
  A：**这是对我这句话最强的反驳，我自己先说了**。官方建议原文就是 "encode verification as skills"。我的回应是：造不出 verifier 的那一类，卡的不是「对不对」，是「准不准」——Claude Code 那句话很说明问题，它说外部副作用 "can't be checkpointed, which is why Claude asks before running"，**注意它没说「所以我们写个 verifier」，它说的是「所以我们问人」**。
- Q：你说图更适合审计，可 LangGraph 自己说 replay 结果可能不同？
  A：对，所以我说的是**控制流可审计**，不是**结果可复现**。这两个我分得很清楚。
- Q：现实里是不是都混着用？
  A：是。OpenAI 自己就说多智能体可以建模成图、agent 就是 node。这条分歧正在消解，但恢复粒度和卡点位置那两条不会消。

**过渡到下一页**：树也好图也好，管的都是"走哪条路"。但每一步能带多少东西上路——那是上下文的事。

## P18 · Context Engineering I：上下文是预算，不是仓库

**一句话主旨**：上下文是有限的注意力预算，塞满是反模式。

**怎么讲**：
这一页和下一页，是我自己踩坑最多的两页。

先分清两个词。prompt engineering 关心的是"这一句怎么写"；context engineering 关心的是"在有限的窗口里，每一轮到底该放哪些东西进去"。后者才是 agent 的主战场，原因很简单——agent 会自己往窗口里疯狂塞东西，你写得再好的那一句，第五轮之后就被淹了。

看中间这根横条，它代表一次请求的窗口被谁占了。先声明口径：右上角写着"比例为示意，随任务差异极大"——这不是我实测的数据，宽度只是示意，别记数字。[停一下]

从左往右：第一段黄的是 system prompt，角色、规则、环境信息，常驻，每一轮都要付一遍钱。第二段绿的是工具定义，每个工具的 JSON schema 都得常驻——所以工具越多，开局越贵。第三段紫的是项目上下文，AGENTS.md、CLAUDE.md 这类长期约定。第四段这一小条亮紫色的，是 SKILL 索引，特别窄——因为它只放名字加一句描述，几十个 token，正文用到才展开。这是本页第一个关键技巧，第 20 页会专门讲。

中间这一大段青的是对话历史，随轮次线性增长，而且不可逆。紧接着这段橙的最宽，是工具结果——旁边那行字：一次 grep 就能吃掉几万 token。这是最会爆炸的一块。最右边这段灰的是预留输出，不留够，模型话说一半就被截断，而截断的工具参数尤其危险——这就接上了上一页第④步。

最下面这段机制解释是 Anthropic 官方的表述，我念慢一点：transformer 里每个 token 都要与其余所有 token 建立关系，n 个 token 就是 n 平方对关系。所以模型有一份有限的"注意力预算"，塞得越满，单位注意力越稀。它是一份边际收益递减的有限资源，不是仓库。所以那句红字——窗口大不等于能用好。

下面三张卡是三条对策：按需加载、卸载到外部、压缩。第三条怎么压才不丢关键信息，下一页专门讲。

最后这条红框是我后来补上去的，也是最有说服力的一条：这不是我说的，是厂商自己的数据。同一个 Gemini 3.6 Flash，做长上下文召回测试，在 十二万八千 的窗口下拿 九十一点八 分；把上下文拉到 一百万，掉到 五十四点零。[停] 窗口"能装下"，不等于模型"找得到"。这就是为什么我说上下文是预算不是仓库。

**别漏了说**：
- "比例为示意"这个口径必须在讲条形图之前先说，否则整页都会被当成实测数据。
- SKILL 索引那一小条为什么窄——只放索引不放正文，这是全场复用率最高的技巧。
- 预留输出不够会截断工具参数，和 P15 的④串起来讲。
- n² 那段是官方表述，标明出处，不要说成自己的推导。

**可能被问**：
- Q：这个比例是哪来的？
  A：是示意图，图上自己写了。真实占比随任务差异极大，我没有一份可以拿出来的实测分布。
- Q：n² 那个说法严谨吗？
  A：这是 Anthropic 官方博客里的直觉解释，我引用的时候标了"官方表述"。它不是一个严格的注意力衰减证明，别当定理用。
- Q：那我上百万窗口的模型是不是就没意义了？
  A：有意义，能装下的东西多了。但"能装"和"能用好"是两件事，页面上这句红字就是这个意思。中间部分被无视的现象，窗口越大越明显。
- Q：工具定义常驻很贵，能不能动态加载？
  A：可以，卡片里就写了——工具也可以分级，先给一个"找工具"的工具。代价是多一次往返。

**过渡到下一页**：那么，窗口真的满了，到底该怎么压？

## P19 · Context Engineering II：压缩，以及一种反直觉的压法

**一句话主旨**：压缩必须是"可解释的有损"——你要知道自己丢的是哪一类信息。

**怎么讲**：
"让 LLM 写个摘要"只是起点。真正的工程量在三件事：切在哪、保留什么、摘要本身怎么迭代。还有第四件——窗口已经爆了、连摘要请求都发不出去的时候，怎么办。

先看左边做法一，摘要式压缩。上面这排小方块是原始历史，颜色对应不同类型的条目。中间这条红色虚线打了个叉，写着"不能切在这里"——因为会把"调用工具"和"工具结果"切散。想象一下：模型看到自己调了工具，却看不到结果，它只能瞎猜。右边这条绿实线才是合法切点：回退到一轮的开头。

切完之后，左边这段压成摘要，右边保留原文。看下面这两个盒子：左边"历史摘要"，注意小字——是在上一版摘要上迭代，不是每次重新总结全量；右边"最近的原文，一字不动"，按 token 数从尾部反向累加，够了才停。

底下这四条是 pi 的实现细节，每一条都是踩过坑的。①触发用绝对阈值不用百分比，剩余空间少于预留额度就压，预留默认约 16K token。②切点明确排除工具结果，切到轮中间就回退到轮首——这时候要做两次摘要。③摘要迭代更新。④摘要请求用独立缓存和独立会话，不污染主线的 prompt 缓存——这条很容易漏，漏了你会发现压缩一次，主线缓存全废。最后这行小字接上了第 16 页：压缩本身就是一条会话树条目。

右边是做法二，oh-my-pi 的做法，我第一次看到时是不信的：把要丢弃的历史在本地光栅化成点阵 PNG，让视觉模型"读图"回忆。不调 LLM，也就不产生摘要幻觉。

为什么反直觉却有效，三个理由。一，计费不对称——某些模型按每图固定预算计价，与像素无关，那图放大到 2048 像素就是纯赚。二，存在 OCR 悬崖，这两个数字我要标一下来源：同一份内容，密排版的 f1 掉到 零点三五一，模型基本摆烂不读；把字间距拉开，回到 零点八零六。这组数据是引自 oh-my-pi snapcompact 源码顶部的注释，是项目自测，我没有独立复现，只有这一个来源。三，零依赖——窗口已经爆了、摘要式压缩恰好失效的时候，它还能跑。

还借了个生物学比喻：归档用中央凹布局，头尾高清、中段低清，超预算先丢最老的中段，模仿"最老的细节先褪色"。还有个顺序细节：先脱敏，再光栅化，不然密钥就被烙进图片里了。

**别漏了说**：
- 0.351 和 0.806 的口径——项目自测、二手来源、未独立复现，必须当场说明。
- ④独立缓存独立会话，是最容易漏、漏了最疼的一条。
- 切点为什么不能切散 tool_call 和 tool_result，要给出"模型只能瞎猜"的画面感。
- 先脱敏再光栅化这个顺序，是安全细节，别当花絮跳过。

**可能被问**：
- Q：0.351 那组数是谁在什么条件下测的？
  A：引自 oh-my-pi snapcompact 源码顶部注释，属于项目自测。测试集、模型、评测脚本我没有逐项核对，也没有独立复现。就当一个方向性信号，不要当基准。
- Q：哪些模型是按每图固定预算计价？
  A：页面上写的是"某些模型"，我没有逐家核对当前的计价规则。这个我会后补。
- Q：把历史变成图，代码细节不会丢吗？
  A：会丢。所以中央凹布局把最近的头尾留高清，先褪色的是最老的中段。它本来就是有损压缩，只是丢的方式换了一种。
- Q：16K 预留是硬编码吗？
  A：页面写的是"默认约 16K"，是默认值。用绝对阈值而不用百分比的原因是：窗口越大，百分比留出来的空间越离谱。
- Q：两种压法该选哪个？
  A：不是二选一。摘要式是主力；图像式是摘要式失效那一刻的兜底。

**过渡到下一页**：压缩是在窗口满了之后补救。更好的办法是一开始就别塞——这就是 SKILL 的渐进式披露。
