## P19 · SKILL：把说明书挂在墙上，而不是背在身上

**一句话主旨**：常驻的只有目录，正文用到才翻开。

**怎么讲**：

上一页我们在解决"窗口已经满了怎么办"。这一页往前挪一步——能不能一开始就别让它那么快满。

看左边这个三层的图，从上往下走。最上面这条紫色的框，叫第 0 级，常驻在 system prompt 里。它里面装的是什么？就框里这两行 XML：一个 name，一个 description，一个 location。**注意这里没有正文**。右上角标着"大约几十个 token 一个"——这是个量级估计，不是实测，你可以理解为"一句话的价钱"。

往下走一个箭头，箭头旁边写着"模型读到描述，判断这次用得上"。注意这个判断的主语是模型。它判断用得上了，才进第 1 级——绿色这层。这层是把完整正文拉进来：操作步骤、检查清单、坑位说明、命令模板，几百到几千 token。这层下面我特意留了一行小字，请大家看一眼：**读它用的就是那个再普通不过的 read 工具**。没有"技能加载器"，没有专门的运行时。这件事听起来平淡，但它是整个设计能站住的原因。

再往下,第 2 级，黄色的：references、scripts、大段样例。这层可能永远不会被读到，所以它免费。这里有一句我自己踩过坑才想明白的话——**脚本尤其划算，因为你可以让 agent 去执行它，而不是把它读进上下文再复述一遍**。

最后看底下这行红字：这不是检索。RAG 是按相似度切碎了塞给你；SKILL 是模型自己决定翻开哪一本，读到的是完整的、有作者意图的整篇。

右边三张卡里最硬的是第一张：pi 的 Skill 结构体里压根没有 content 字段。正文从来没被读进内存过——这不是我推测的，是翻代码看到的。

**别漏了说**：
- "只有 read 工具在场时才注入 skills 段"——这个细节要点一下，逻辑很干净：没有 read 就翻不开，那列出来纯属浪费 token。
- description 是唯一入口。这是最反直觉的一条：**大家花力气写正文，但决定正文会不会被看见的是那一句描述**。
- 底下那行小字要念："决策权在模型、成本可预估、内容可版本管理可 code review"——这三点才是它比"再调调 prompt"强的根本原因，不是因为它更聪明。
- 右下角那张卡：渐进式披露本来是 HCI 的老概念，界面先给最常用的。省的从"用户注意力"变成了"模型注意力"，是同一个问题换了个对象。

**可能被问**：
- Q：那 SKILL 和 RAG 到底能不能一起用？
  A：能，而且不冲突。它们回答的是不同问题：RAG 解决"我不知道答案在哪本书里"，SKILL 解决"我知道该翻哪本，但不想一直背着"。真正的区别在决策权归谁。
- Q：几十 token、几百 token 这些数是怎么来的？
  A：是按 name + description 的长度估的量级，**不是我实测的**。如果你要做容量规划，得按自己的 skill 描述实际数一遍。
- Q：skill 一多，模型会不会选错、或者干脆不选？
  A：会。这正是下一页 oh-my-pi 要解决的同一类问题，只不过它是对工具做的。

**过渡到下一页**：说明书可以这么省着放，那"工具"呢——工具定义也是常驻成本，这件事有两个完全相反的答案。

## P20 · 工具集是接口设计，不是功能清单

**一句话主旨**：给多少工具没有标准答案，但两派的取舍逻辑都值得学。

**怎么讲**：

刚才 SKILL 那套逻辑，本质是"常驻的东西越少越好"。那把这个逻辑推到工具上，就出现了这一页——同一个问题，两个方向完全相反、但各自都自洽的答案。中间这条虚线把屏幕分成两半。

先看左边，绿色的，极简派，pi。标题右上角写着：**内置 7 个，默认只给模型 4 个**。上面这四个实心框就是那四个——read 看、bash 干任何事、edit 改、write 写。下面这三个虚线框：grep、find、ls，注意它们是**已经实现了的**，只是默认不注入给模型。

理由在下面这个绿框里：模型已经会用命令行了。与其教它用"我的 grep"，不如让它用它早就会的 rg 和 fd。这句话我很喜欢——**bash 的文档是整个 Unix 世界**，你一分钱没花就白嫖了这份文档。但请大家一定读最后那行灰字，那是代价：每次都要付 shell 启动的开销，输出格式不受控，出了事更难归因。

再看右边，黄色的，全能派，oh-my-pi。**30 多个工具，但分两级发放**。常驻 system prompt 的只有这上面五个：四个 essential，加一个 search_tool，走 BM25 检索。顺着这条虚线箭头往下——其余 25 个以上躺在池子里，模型需要的时候先"搜工具"，命中了才把定义加载进来。

理由是：工具定义本身就是常驻成本。30 个 schema 全塞进 prompt，一是烧 token，二是**让模型选错的概率上升**。于是它把"工具发现"这件事本身也变成一次工具调用——请注意这里我标了紫色一行：**和 SKILL 是同一个思路**。代价也写在下面：多一跳延迟；描述写不好就搜不到，等于白做。

下面四张卡是不管你站哪一派都成立的四条。我只强调第三张：**报错必须带上"下一步怎么办"**。pi 的参数校验失败会生成一个带字段路径的多行错误回喂给模型——这是让 agent 能自己爬起来的关键。

**别漏了说**：
- 两边都是对的，我不替大家下结论。选哪边取决于你的环境：能不能信任 shell、要不要审计每一次调用、延迟敏不敏感。
- "少而正交"这条最容易被忽略：两个功能重叠的工具 = 每次调用都强迫模型做一次**无谓的选择**，还多一次选错的机会。
- 第四张卡"结果必须裁剪"——工具结果是**最会爆窗口**的一块，比 prompt 危险得多。分页、截断、大结果落盘只回路径。
- pi 那三个虚线框不是"没做"，是"做了但不给"——这个区别要说清楚，否则听众会以为是功能缺失。

**可能被问**：
- Q：那到底该选哪个？
  A：我的经验是看你有没有可信的沙箱。有 bash 且能兜住风险，极简派更省心；不能给 shell、或者要逐工具审批的环境，只能走全能派那条路。
- Q：BM25 检索工具，命中率怎么样？
  A：**这个我没有实测数据，只有设计意图**。页面上写的"描述写不好就搜不到"是它公开承认的失败模式，会后我可以补一下实际表现。
- Q：MCP 算哪一派？
  A：MCP 天然偏全能派——它一挂就是一堆工具定义。这也是 pi 刻意不做 MCP 的原因之一，P23 会再提。

**过渡到下一页**：工具讲完了，但在你决定要给多少工具之前，其实还有个更前置的问题——你确定你需要的是一个 agent 吗？

## P21 · 先学会不用 agent：五种 workflow 模式

**一句话主旨**：绝大多数"我需要一个 agent"，其实是这五种之一。

**怎么讲**：

这一页我讲得快一点，因为它是一张**词汇表**，不是一个论证。出处在最下面：Anthropic 的《Building Effective AI Agents》，2024 年 12 月 19 号。这套词现在基本成了行业黑话，你不认识它就没法参与讨论。

表格四列，从左到右念：模式、形状、机制、**最右边这列是原文说的"什么时候用"**——这列才是重点，别只看形状。

第一行，Prompt chaining，提示链。看形状：一串圆圈依次往右。中间这个红色的菱形，下面标着"校验闸门"——它是**代码写的**，不是模型判断的。原文说：任务能被干净地拆成固定子任务时用它。

第二行，Routing，路由分流。黄菱形是分类器，往后分出三条路。这里有句话值得记：分类器可以是小模型，甚至可以是正则。适用条件：存在明显不同、且分开处理更好的类别。

第三行，Parallelization，两个变体。绿字 Sectioning 是拆成互不相干的子任务同时跑；紫字 Voting 是同一个任务跑多遍取不同视角。形状上都是散开再收拢，但语义完全不同。

第四行，Orchestrator-workers。看这三条**虚线**箭头——虚线的意思是子任务数量由模型现场决定。但请注意中间这行字：**它仍然被归为 workflow**，因为编排骨架还是写死的，只有"分几份"交给了模型。这一条最容易被误认成多智能体，下一页就要用到。

第五行，Evaluator-optimizer，生成-评审循环。左边生成，右边评审，反复到通过。下面这行小字先记着：**评审方不共享生成方的上下文，效果反而更好**——这条我下一页和再下一页还会各提一次，它是有出处的。

最下面那行边界，我念一遍：真正的 agent 留给"开放式问题、步数无法预先估计"的场景。

底下的金句就一句话：agentic 系统是**拿延迟和成本去换任务表现**。workflow 给你可预测性和一致性，agent 给你灵活性。先问清楚你要的是哪一个。

**别漏了说**：
- ④ 被归为 workflow 而不是 agent，这个分类点必须讲，它是下一页争论的前提。
- ⑤ 那行"2026 年的实践发现"是我加的注，**不是 2024 年原文里的**，念的时候要区分开。
- 最右列是原文的适用条件，不是我编的判断标准——这点要说明,增加可信度。
- 这五种可以嵌套组合，不是互斥的五选一。

**可能被问**：
- Q：这套分类到现在还成立吗？
  A：形状层面成立得很好。但边界在往下滑——2024 年划给 agent 的一些场景，现在用 workflow + 好的上下文工程也能做。
- Q：Orchestrator-workers 和多智能体的界线到底在哪？
  A：看写操作和编排骨架归谁。骨架写死、子任务只是被分派，就是 workflow；如果连"要不要拆、拆给谁、谁先谁后"都由模型自由协商，那才是多智能体——下一页正好讲它翻车。

**过渡到下一页**：说到"多个模型协作"，2025 年 6 月有两篇文章前后只差 24 小时，结论看起来完全相反。这是全场我最想讲的一段。

## P22 · 多智能体：相隔 24 小时的两篇对撞，与 10 个月后的收敛

**一句话主旨**：两边都不是错的，他们在说不同的事。

**怎么讲**：

这一页我要慢慢讲。中间这条横线是时间轴，左下角标了一句**"非等距时间轴"**——因为前三个点挤在四天里，最后一个点在十个月后。

从最左边这个红框开始。2025 年 6 月 12 号，Cognition，就是做 Devin 那个团队，发了一篇《Don't Build Multi-Agents》。两条论点：第一，要共享上下文，而且要共享**完整轨迹**，不是几条消息；第二，行动本身隐含着决策，**决策一冲突，结果就烂**。底下这个反例特别形象，我念一下：他们拆给子 agent 去做一个 Flappy Bird，结果一个 agent 做出了超级马里奥风格的背景，另一个做的鸟根本不像游戏素材。两个都完成了任务，拼起来是个怪物。

然后看这条橙色虚线，上面写着**"相隔 24 小时"**。第二天，6 月 13 号，Anthropic 发了《多智能体研究系统是这么建的》——绿框在时间轴下面。主 agent 协调，子 agent 并行干活。它认的主要收益不是"人多力量大"，而是**上下文隔离**：子 agent 是"智能过滤器"，各自独立探索，不互相带偏。

框里这两个数字，我要说清口径。**高 90.2%**——这是 **Anthropic 自家的内部研究评测**，测的是他们自己的系统，不是第三方 benchmark，请大家按"一方自报"来听。下面这行同样重要，是他们自己披露的代价：普通 agent 大约 4 倍 token，多智能体大约 15 倍。**15 倍**。这个数比那个 90.2% 更值得记。

第三个点，6 月 16 号，第三天，LangChain 下场当裁判：多 agent 之所以失败，根因是 **context engineering 没做好**，而不是"多 agent"这件事本身有问题。这句话把一场立场之争拉回到了工程层面。

最后往右看，中间这段虚线写着"十个月过去"。2026 年 4 月 22 号，**Cognition，同一位作者**，发了《现在哪些是真能跑的》。三条：第一，代码评审循环——评审方**不共享**上下文反而更能抓到 bug，作者自己都说这反直觉；第二，"聪明朋友"，弱模型在难点上找强模型求助;第三，管理者派发，可行，但要大量上下文工程。最下面那行红字是他仍然认为不行的：**一群 agent 无结构地自由协商**。

所以这不是谁打脸谁，是边界被磨清楚了。

**别漏了说**：
- "同一位作者"这四个字必须点出来，这是整个故事的戏剧性所在——**他没有全盘推翻自己，他把条件补上了**。
- 90.2% 和 15× 是同一篇文章给的，一个是收益一个是代价，**只念收益不念代价是不诚实的**。
- takeaway 那句英文一定要翻译着讲：writes stay single-threaded——**写操作保持单线程**；additional agents contribute intelligence rather than actions——多出来的 agent 贡献**判断力**，不是**动作**。
- 收一句：这就解释了为什么现在主流产品里的子代理，大多数是**只读的调研员**。这个观察比前面所有数字都实用。

**可能被问**：
- Q：90.2% 可信吗？
  A：**我不完全信**。它是内部评测、自己测自己、任务集也没公开。我引它是因为它是这场争论里唯一有数的一方，不是因为它是定论。
- Q：15 倍 token，那还有什么用？
  A：看你的任务值不值这个价。深度调研类的任务，一次多花十几倍 token 换一份能用的报告，很划算；日常改代码，绝对不划算。
- Q：LangChain 是不是有立场？
  A：有。他们做编排框架，"是工程问题不是架构问题"这个结论对他们有利。我把它放进来是因为这个视角有价值，不是因为它中立。
- Q：Flappy Bird 那个例子是不是太老了、模型早就变强了？
  A：例子会过时，机制不会。只要两个 agent 各自做隐含决策又不共享轨迹，风格漂移就还会发生——只是现在漂得更精致一点。

**过渡到下一页**：既然"多加一个 agent"只是众多扩展手段中的一种，那我们把所有扩展点摊开看一遍——这是我认为整场最实用的一页。

## P23 · 六种扩展点，各管一段

**一句话主旨**：六种扩展点不是同义词，挂错位置会很痛苦。

**怎么讲**：

上一页说 subagent 是一种手段。这一页把所有手段都摊在同一条流水线上——请大家先看上面这条横线。

从左到右六个格子，就是 agent 跑一轮的全过程：**用户输入 → 提示组装 → LLM 请求 → 工具执行 → 结果回灌 → 落盘/存档点**。每个格子上面挂着能插在这个位置的扩展点。

用户输入这格上面挂的是 **Slash command**，青色。提示组装这格挂三样：context files、SKILL 索引、自定义 system prompt。LLM 请求这格是 **Hook——改写送 LLM 的上下文**。工具执行这格挂了两层：上面绿色的是内置工具、MCP、自定义工具，下面红色的是 **Hook 拦截和权限审批**。结果回灌那格是 Hook 改写工具结果，最右边落盘那格是 Hook 埋点和归档。**Subagent 挂在结果回灌下面**——派生一份独立上下文，只回一份摘要。

现在请大家看横线下面这一行小字，我认为这是整页最关键的一行：**"谁能触发它"**。人写、常驻；代码强制；模型决定;代码强制。同一条流水线上，触发者是三种完全不同的角色。选扩展点，本质上就是在选**谁来按这个按钮**。

下面这张表把六种展开，第三列"谁触发"就是刚才那条线。我挑三个最容易踩的坑说：

Context file 那行的代价——**每轮都付一次 token，写太长会稀释注意力，反而没人听**。这个坑我踩过，CLAUDE.md 越写越长，最后模型什么都不遵守。

Hook 那行——它是**唯一能"强制"的机制**，也因此写错会直接卡死主流程。它的力量和危险是同一件事。

Subagent 那行——token 放大明显，**让它并行写文件基本等于灾难**。这句话就是上一页 Flappy Bird 那个故事的结论。

最下面这条决策线，我建议大家拍照。两个问题就够了：**第一，这事必须发生，还是模型可以自行判断？** 必须发生就 Hook，模型判断就 SKILL 或 Tool。**第二，它是知识，还是动作？** 知识用 SKILL，还能享受渐进式披露；动作用 Tool。剩下两个——slash command 是给人的快捷键，subagent 是给上下文减负的隔离舱。

**别漏了说**：
- 那条"谁能触发"的横线是全页的骨架，别让听众只看表格。
- 最下面的出处要念：pi **刻意没有 MCP 和 subagent**。这不是能力缺失，是取舍——和 P20 那个极简派是同一套价值观。
- Slash command 那行的陷阱：**模型不会主动用它**。很多人把重要约定写成 slash command，然后奇怪为什么 agent 不遵守。
- 两个决策问题只需要 5 秒钟就能问完，但能挡掉 80% 的选型纠结——这句话可以直接送给听众。

**可能被问**：
- Q：SKILL 和 slash command 到底怎么分？
  A：看触发者。你希望自己敲一下才发生，用 slash command；你希望模型自己意识到该用，用 SKILL。**同一段内容做成两份也没问题**，成本很低。
- Q：Hook 会不会太重？
  A：会。我的建议是只把"违反了就必须回滚"的规则放进 Hook——格式校验、权限审批、审计埋点。剩下的都用 SKILL 表述，让模型判断。
- Q：MCP 和自定义工具选哪个？
  A：跨进程、要复用给别的客户端，用 MCP；只服务自己这一个 agent，直接写内置工具更省事、也少一层协议开销。
- Q：pi 不做 subagent，那要并行探索怎么办？
  A：**这个我没查到它的官方替代方案，会后补**。从设计取向推测，它更倾向于让人开多个会话，而不是让模型自己派生。

## P24 · 记忆分三个尺度，纠偏分两个时机

**一句话主旨**：记忆要按尺度分开设计，纠偏要把生成和评判分开。

**怎么讲**：

这一页是 CH3 的收尾，专门还债。第一幕留下两个病：**记不住**、**停不下来**。左半屏治第一个，右半屏治第二个。副标题里有句话我要强调：**它们的解法都不在模型里**，全在 harness 里。

先看左边，记忆的三个尺度，从上往下。

最上面青色这层，**尺度一 · 轮内**，右上角标着"秒到分钟"，它就是上下文窗口。请注意下面这行定义：**它不是仓库，是注意力预算——越满越钝**。这句话是整个左半屏的地基。

顺着箭头往下，箭头旁边写着"跨轮：靠只追加活下来"。紫色这层是**尺度二 · 会话内**，小时级，会话树加压缩。**只追加、不改写**，所以能回溯、能分叉、能重放。这里有个细节：**压缩本身也是树上的一个节点**——也就是说你事后能看到"当时压掉了什么"。

再往下，箭头写着"跨会话：只有被显式巩固的才活下来"。绿色这层是**尺度三 · 跨会话**，天到永久。最朴素也最有效的形态是什么？**文件**。写下来的东西天然可 review、可版本管理。更工程化的做法是工作记忆到情节记忆的巩固机制，加全文和向量的混合召回。

最下面这个黄框是我最想让大家记住的：**最容易犯的错，是把三个尺度混成一个"记忆系统"**。它们的读写频率、可靠性要求、成本量级差好几个数量级，必须分开设计。

再看右边，纠偏两个时机。共同前提写在最上面：**让模型自己评自己，它会自我吹捧**。

红框，事中拦截。看这条线：绿色是正在流式生成，走到中间这个红点——违规 token 出现了。后面这段灰色虚线全部丢弃，然后顺着这条回勾的虚线：**立即打断、回滚、带着规则重跑这一轮**。好处在下面：违规**从来没有进入过历史**，模型不会看到自己犯过的错再学一遍。代价也写了：要在流式层做，实现复杂。

紫框，事后评审。三个盒子从左到右：主 agent 跑完这一轮 → **第二个模型只读这一轮的增量** → 给出异议或放行，插回主线。关键设计在下面这两行：评审方**不共享**主 agent 的完整上下文。为什么干净的上下文反而更容易看出问题？因为**它没被主线的叙事说服过**。

最下面这条黄字，把两边收在一起：**结构性地分离"生成"和"评判"**。

**别漏了说**：
- 这一条"评审方不共享上下文"在这一整章出现了三次——P21 的 evaluator-optimizer、P22 Cognition 的转向、这一页。**三次都要串起来提一句**，这是全章唯一被反复交叉验证的结论。
- 页面上有个不一致要注意：图里写的是 **mnemosyne**，页脚证据栏写的是 **mnemopi**。念的时候统一说一个名字（建议按页脚的 mnemopi 念，或者干脆说"oh-my-pi 的那套双层记忆"），别在台上被听众抓到。
- TTSR 只出现了缩写没展开——如果听众不熟，说一句"就是流式回滚"即可，别装懂。
- "上下文窗口不是仓库，是注意力预算"这句是全场最好用的一句金句，值得停半拍。

**可能被问**：
- Q：跨会话记忆到底该用文件还是数据库？
  A：先用文件。文件的 review 和版本管理是白送的，你写向量库要自己造这两样。等文件多到检索不动了再上召回。
- Q：mnemopi/mnemosyne 这套双层记忆，效果有数据吗？
  A：**我没有看到公开的评测数字，这是设计描述不是效果验证**。会后我去确认一下有没有 benchmark。
- Q：事中拦截会不会误杀？
  A：会，这是它最大的风险。所以它只适合**规则明确、判定确定**的违规（比如禁止的 API、禁止的路径），不适合"质量不够好"这种模糊判断——那类只能走事后评审。
- Q：两个时机能不能同时上？
  A：能，而且互补。事中拦硬规则，事后评软判断。但两套都上意味着两份成本，小项目先上事后评审就够了。
