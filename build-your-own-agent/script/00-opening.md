先看左上角这个小标签，一个跳动的点，写着 AGENT ENGINEERING · 2026。这个年份不是装饰——agent 这个词大概每半年就要变一次意思，我把时间戳打在这儿，是想说：这份材料是站在 2026 年这个时间点看的，再往后可能又不一样了。

页脚这行是这套图表设计系统的出处，不用管。

## P2 · 核心观点：结论先行

**一句话主旨**：五句结论摆在最前面，后面三十几页都是在给它们找证据。

**怎么讲**：

刚才说了结论先行，那就真的先行。这页是全场唯一一页"你可以拍照走人"的页面。

从上往下五条，每条右下角都有个灰色的页码，那是这句话的证据在第几页——你可以只听你在意的那一章。

第一条，青色的：**模型决定能力上限，harness 决定你能兑现多少**。下面这行是它的实验口径，我念慢一点：十六个模型，乘以一百八十个真实的修 bug 任务，只改动"编辑工具格式"这一个变量——其他全部不变。结果是，其中一个模型的通过率从百分之六点七变成了百分之六十八点三。（停）全体平均提升十五个百分点。这里我要先打个补丁：六点七到六十八点三是最极端的那一个样本，具体是哪个模型、以及"越弱的模型收益越大"这个更重要的发现，第 13 页会完整给。别现在就得出"换个工具就能十倍"的结论。

第二条，紫色的：**上下文是预算，不是仓库**。原因就一句——窗口里每个 token 都要和其余所有 token 建立关系，注意力是被摊薄的。后面所有 context engineering 的花招，都是这一句的推论。

第三条，绿色的：**能写死的就别让模型猜**。绝大多数"我需要一个 agent"的需求，其实是五种 workflow 模式之一，更便宜、更可控、更好排查。

第四条，琥珀色的：**你能给自己的领域造出验证器，agent 才真的能进来**。coding 先落地不是因为程序员多，是因为编译器和测试天然就是验证器。没有验证器的领域，agent 只会自信地胡说。

第五条，玫红色的：模型是租来的，工具是现成的，但那层壳只能自己焊。下面这句英文是 pi 官网的原话，逐字是这样的——"There are many agent harnesses but this one is yours"。

**别漏了说**：
- 这五条不是并列关系：1 说 harness 值得投入 → 2、3 说具体怎么做 → 4 划边界 → 5 回答"为什么要自己造"。串一句因果，听众才记得住
- 数字口径必须说全：单变量受控实验、修 bug 任务、页面上写的是"同一个模型"，别让人误以为是某个大厂旗舰模型
- 主动说明"6.7→68.3 是极端样本"，你自己先承认，比被人在 Q&A 里挑出来强
- 页脚那句"每一句后面都挂着可核查的出处"要念，它是这五条能立住的前提

**可能被问**：
- Q：这个实验是谁做的？可复现吗？
  A：Can Bölük 的《The Harness Problem》，2026 年 2 月 12 日。原文我核过，但我没有自己复跑。原博客地址已经跳转到 stencil.so 那边了，引用请用新址。
- Q：那有没有反方向的证据？
  A：有，第 13 页我会给 Terminal-Bench 官方榜的数据：同一个模型套四种 harness 极差是 18.4 个百分点，而同一个 harness 换模型极差是 70.7 个百分点。所以诚实的说法是——模型是主项，harness 是不可忽略的次项。
- Q：pi 是什么？
  A：一个开源的 agent harness，第 30 页专门讲。现在只需要记住这是本场的主要代码样本之一。

**过渡到下一页**：这五句话听起来都挺硬，那我得先交代一下——我凭什么这么说，以及你听完能带走什么。

## P3 · 关于这次分享：目的 · 收获 · 交流

**一句话主旨**：这是一份工程读书笔记加一手代码取证，不是产品宣讲。

**怎么讲**：

标题这句我想说得直白一点：这不是产品宣讲，是一份工程读书笔记，加一手代码取证。背景很简单——我自己在造一个 agent，造之前把这两年的公开工程实践系统啃了一遍，与其让笔记烂在硬盘里，不如整理出来。

四张卡，我按顺时针走。

左上角青色这张，"为什么讲这个"。我的观察是：市面上关于 agent 的内容，要么是概念科普，要么是产品广告，中间那层"到底怎么工程化"很少有人讲。而这层恰恰是唯一你能自己掌控的部分——模型你造不了，界面别人已经替你做了，只有中间那层得自己写。所以第三条是我给自己定的规矩：所有断言尽量挂出处，官方博客、arXiv、以及直接打开源码看行号；凡是只在二手转述里见过的数字，一律不上页。这条规矩会贯穿全场。

右上角绿色这张，"你能带走什么"，右边小字写着"按投入产出排"。第一是一套共同词汇，以后跟人讨论 agent 不再各说各话。第二是一张决策表——什么时候写 workflow、什么时候才轮到 agent、什么时候干脆别用。第三是选型依据。第四是几个能直接抄的工程模式：会话树、渐进式披露、fork 的 tier 成本模型、生成与评判分离。

右下角紫色这张，交流方式：全部开源，slides 源码、逐页讲稿、十六份带出处的研究笔记都在仓库里。发现错了请直接提 Issue。仓库地址在最底下。

最后回到左下角琥珀这张，我认为最值钱的三个点：第 13 页那场受控实验，第 22 页相隔二十四小时的两篇对撞——两家顶尖团队公开打架，十个月后一方改口，第 31 页的 FORK.md tier 成本模型。
