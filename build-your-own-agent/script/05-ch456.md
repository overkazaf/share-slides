这一章我写得很短，短到只有一页。你们看右边"本章内容"，就孤零零一条——第 26 页，适用场景矩阵。但我要提前打个招呼：**如果今天你只记住一页，我希望是下一页。**

我个人的偏见先说在前面：这个行业现在最缺的不是"怎么用 agent"的教程，是"什么时候别用"的判断力。

## P26 · 适用场景：反馈可得性 × 任务确定性

**一句话主旨**：能不能用 agent，取决于路径能不能枚举、对错能不能机器判。

**怎么讲**：

好，这就是那唯一的一页。标题已经把结论放出来了：**agent 的甜点区只有一格，其余三格都别硬上。**

先看副标题，这是整页的判据来源：决定该不该用 agent 的，**不是任务难不难**，而是两件事——路径能不能预先枚举，以及对错能不能不靠人来判断。这两句话，就是图上的两个轴。

看左边这张图。横轴：最左边是"路径无法预先枚举"，最右边是"路径能预先枚举"。纵轴：上面是"反馈可得性高，机器能判对错"，下面是"反馈可得性低，只有人能判，而且慢"。四个格子。

**左上角，绿框，画了颗星，这是唯一的甜点区。**写代码、调试、修 CI、数据清洗，大规模检索、逆向分析、渗透测试。它们的共同点写在下面——每一步都有个**不靠人的信号**：测试过了、跑起来了、hash 对上了。但要走哪条路，事先谁也说不准。最下面那行绿字是关键：失败很便宜，沙箱里重来一次就是了。

**右上角**：路径你已经知道了。批量格式转换、固定流程审批、分类打标、模板化生成。这里该写 workflow，不该上 agent。青色那句"硬上 agent 等于花十倍的钱买一个更不稳定的结果"——我得诚实说一句，**"十倍"是个修辞，不是我实测出来的数字**，你们听个意思。

**右下角**：定时任务、ETL、表单校验、RPA。这里连 LLM 都不需要。灰字那句我很喜欢——"能用 if-else 解决的事情，不要请一个会做梦的东西来做"。

现在，**左下角。**[停]

这一格我画成了红色，标题是"红线区：别交给 agent"。战略判断、创意方向、人事决定、需要承担法律或伦理责任的结论。为什么它是红的？因为它同时踩了两个轴的最坏值——你**既枚举不出路径，又验证不了对错**。[停]

于是唯一确定的结果是——下面这两行红字，请允许我一字一句念完：[慢]"它会非常自信地给你一个说法，而你没有任何办法证伪它。"[停]

这是这一整页我最想让你们带走的一句。不是它会出错——出错不可怕，出错能改。可怕的是**它出错的时候看起来跟对的时候一模一样**，而你手里没有任何工具能分辨。

右边三张卡片，第一张是可操作版本：上线前问三个问题。① 失败便宜吗——能沙箱、能回滚、能重来。② 成功可验证吗——有没有一个**不靠人肉判断**的信号。③ 路径能预先枚举吗——能就写 workflow，不能才轮到 agent。最后那行小字是决策规则：三个都是"是"就放手干；**只要第②个是"否"，无论多想用都先别用。**

第二张卡，四条硬红线，我念一遍：不可逆加难验证的操作——删生产数据、对外发布、转账；需要有人为结果负责的判断；反馈只有人能给而且很慢的——品味、关系、政治；最后一条，**输入不可信又没做隔离**。提示注入不是理论风险，第七章我会给一个实例。

第三张卡是我自己的一个观察，也是我觉得最有迁移价值的：coding 之所以成为 agent 第一个大规模落地的场景，**不是因为程序员多，而是因为编译器和测试天然就是验证器**。反过来说——你能给自己的领域造出一个验证器，agent 才真的能进来。这句话我建议做垂直 agent 的同学抄走。

底下的出处说明一下：**四个象限是我自己归纳的，不是谁的官方分类**；判据参考了 Anthropic 那篇《Building Effective AI Agents》里的一句话——"先找最简单的方案，只在必要时增加复杂度"。

**别漏了说**：
- 红线区要停顿、要重念，尤其最后那两行"自信地给你一个说法 / 你没办法证伪它"。这是全页的情绪高点。
- "十倍的钱"必须主动声明是修辞不是实测，否则会被追问。
- 三个问题里的第②条是**否决项**，不是加权项——这个逻辑差别一定要讲出来。
- 象限是自己归纳的，主动说明，别让人以为是权威分类。

**可能被问**：
- Q：那 agent 写代码就一定安全吗？它也会写出能编译但逻辑错的代码。
  A：对，验证器只保证"这一步没崩"，不保证"这一步是对的"。它降低的是搜索成本，不是替你做代码评审。甜点区的意思是"值得试"，不是"可以不看"。
- Q：红线区里"创意方向"是不是太绝对了？很多人用 AI 做创意辅助挺好的。
  A：这个我同意有争议。我的区分是：**拿它当发散工具没问题，拿它当拍板的人有问题。**因为你没法证伪它给的方向。两边我都摆在这儿，你们自己判断。
- Q：有没有量化数据支持"甜点区"这个划分？
  A：没有。这就是一个基于判据推出来的归纳框架，不是实验结论。我不想假装它有数据。
- Q：那"能造验证器就能进来"，具体怎么造？
  A：这个我没有通用答案。我自己在逆向这个领域的尝试是第七章的内容，能不能推广到别的领域，我不敢说。

**过渡到下一页**：边界讲完了。接下来我们看看，在这条边界之内，别人已经把车造成什么样了。

## P27 · 第 05 章 · 全景

**一句话主旨**：把主流 coding agent 摆进一张图，看分野，不看排名。

**怎么讲**：

刚才那一页我们划完了边界——什么该交给 agent，什么打死也别交。现在假设你已经确定"这事该用 agent"了，下一个问题很自然：**用谁的？**

进度条第五格，第五章，「全景」。

这个大问句就是很多人真正想问的："别人都怎么做的？我该选谁？"[停] 我知道大家最期待的是一个排行榜。但我得先泼一盆冷水——看副标题：**重点不是排名，是看清分野在哪。**

原因很实在：排名这个东西,你今天记住了，三个月就过期了。这个赛道变得太快。但"分野"不会——分野是结构性的，它反映的是不同产品在架构上做了什么不可逆的选择。选择比分数更耐放。

右边"本章内容"，这一章也是只有一页，第 28 页。副标里三个词组：**内核大小 × 开源程度**、**三种交互面**、**选型血泪**。前两个是分析框架，第三个是我踩过的坑。

然后请注意副标题最后半句——"以及那个空着的象限说明了什么"。[停] 我在这儿先埋一个扣子：下一页那张图上，有一格是空的。**空得很规律，空得有道理。**待会儿我会问你们能不能找出来是哪一格。

底下这块灰边的框是这一章的承诺，也是本场我最想推的一个选型观念：选型时真正该看的维度**不是「谁更强」，而是「这层壳能不能改」**。因为"谁更强"过三个月就换人了，"能不能改"是你能长期握在手里的东西。

**别漏了说**：
- 一定要明确说"重点不是排名"，先把听众的期待值调过来，否则下一页他们只顾着找自家用的产品在哪。
- 空象限的扣子一定要埋，而且要说"我等下会问你们"，制造参与感。
- "能不能改"这个选型观念在这里先说一次，下一页和第六章会各回响一次。

**可能被问**：
- Q：为什么不直接给个推荐？
  A：因为我的推荐只对我的场景成立。我第七章会讲我自己怎么选的，包括为什么这么选，你们可以拿我的推理过程，别直接拿我的结论。

**过渡到下一页**：好，图放出来，你们先别听我说，先自己看十秒，找一找哪一格是空的。

## P28 · 主流 Coding Agent 全景：内核大小 × 开源程度

**一句话主旨**：2026 年真正的分水岭，是这层壳你能不能改、能不能拥有。

**怎么讲**：

先给大家十秒，自己看这张图。[停][停]

好，先说两个轴。纵轴是**开源程度**：上面是宽松开源，MIT 或者 Apache 这一类；下面是闭源专有。横轴是**内核大小**：最左边"内核最小，一切靠你自己长"，最右边"电池全包，开箱即用"。

**左上角，青色**，最大的那个圈是 pi，**八万一千五百个 star**——这个数字得说清口径：**GitHub API 采集于 2026 年 8 月 1 日，是个快照，不是实时的**。它是本场的主角。旁边两个小圈是 Aider 和 Goose，Goose 底下有行小字"能力全走 MCP"，它跟 pi 是同一个思路的两种极端做法。

**右上角，绿色**，opencode，**十九万一千七百个 star**，同一天同一个口径。它是这张图上的热度天花板。我要说句公道话：**star 数不等于质量，更不等于装机量**，opencode 比 pi 高一倍多，只能说明它更出圈。旁边还有 Cline、OpenHands、Qwen Code。

**右下角，琥珀色**，闭源加大而全。Claude Code 那个大圈下面我列了它的扩展体系——Skills、Subagent、Plugin、Hook、MCP。然后是 Amp、Codex、Cursor、Devin、Copilot 和 Jules。这一格是今天商业上最热闹的一格。

现在——**左下角。**[停] 刚才有没有人找出来？

这一格是空的。虚线红框圈着，里面写着：**没有"极简 + 闭源"的产品。**

为什么？下面那两行给了答案：**因为闭源产品没有做极简的商业动机——功能就是卖点。**[停]

我觉得这个空格比图上任何一个点都值钱。它不是我漏画了，是这个位置在商业上根本站不住：你收钱，就得给功能;你给功能，内核就往右滑。所以**"极简"这件事，几乎只可能长在开源那一侧。**如果你想要一个自己能完全掌控的最小内核，你不用挑了——你只能往左上角看。

右边三张卡。第一张是另一个切法：按**交互面**分。终端优先，心智模型是"结对"，人在场随时打断——Claude Code、Codex CLI、pi、opencode、Aider。编辑器优先，是"陪审"，看 diff 逐个批准——Cursor、Zed agent、Cline、Copilot agent mode。云端异步，是"外包"，人不在场，回来收 PR——Jules、Copilot coding agent、Codex Cloud。**这三种不是优劣，是你愿意在场多久。**

第二张卡是我认为 2026 年最重要的架构趋势：**agent 和前端正在解耦。**编辑器侧出现了通用协议，仓库侧出现了统一的 agent 调度台。换句话说，"用哪个 agent"和"在哪用"正在变成两个独立选择。**这正是自己造 harness 变得可行的前提**——第六、第七章的所有内容都建立在这个前提上。

第三张卡，血泪。这个赛道死亡率很高：我这次核实的时候就发现，**有产品已经停运了，有免费档已经停服了，有产品已经改名换东家了**。我没在图上标出来是哪几个，因为我不想在台上点名。结论就一句：**把赌注押在"你能改的那部分"上，别押在别人的路线图上。**

底下再重复一次口径：象限归属是我自己归纳的，不是官方分类。

**别漏了说**：
- 空象限的包袱一定要留时间让听众自己找，找完再抖。抖完要马上给"为什么空"的商业解释，否则只是个段子。
- 两个 star 数必须带口径：GitHub API、2026-08-01、快照。并且主动说明 star 不等于质量、不等于装机量。
- "解耦"那张卡是承上启下的枢纽——它是第六第七章成立的前提，一定要点破，别当普通趋势念过去。
- 血泪卡不要点名具体产品，但要说明"我确实核实到了"，保持可信度。

**可能被问**：
- Q：每个产品在象限里的具体坐标是怎么定的？有量化标准吗？
  A：没有。位置是我按照阅读它们文档和源码的主观印象放的，**相对位置有意义，绝对坐标没有意义**。这一点我在页脚写明了。
- Q：opencode star 比 pi 多这么多，是不是应该选它？
  A：star 衡量的是关注度。如果你的目标是开箱即用，右上角确实更合适;如果你的目标是拥有一个自己能改的最小内核，那 star 数在这个问题上给不了你任何信息。
- Q：那几个停运/改名的产品是哪几个？
  A：我不在台上点名，会后可以私下说，也可以自己搜一下就知道。
- Q：Claude Code 也有 Skills、Plugin、Hook，扩展性也很强，为什么算"不能改"？
  A：问得好，这是我这张图的一个粗糙之处。**扩展性和可修改性是两件事**——它给了你很多插孔，但内核不给你。这张图的横轴测的是插孔多少，纵轴测的才是内核归谁。两者不能混。

## P29 · 第 06 章 · 样本

**一句话主旨**：接下来看两个具体样本——同源，但走向了两个反方向。

**怎么讲**：

刚才那张全景图我们停在了左上角。前面五章讲的都是通则——什么是 agent、怎么演进的、原理是什么、什么场景能用、市面上都有谁。**通则听多了会飘。**所以第六章我只做一件事：**落到两个具体样本上，把它们拆开给你们看。**

进度条第六格。这一章叫「样本」。

大问句：极客圈为什么偏爱 pi？oh my pi 又是什么？

看副标题，这是这一章的结构：**一个把「最小」做到极致，一个把「最全」做到极致。它们出自同一条血脉，却走向了两个反方向。**[停] 这里我想强调的是"同一条血脉"——oh my pi 是 pi 的 fork。同一份代码作为起点，一个删到不能再删，一个加到六十多万行。**这是一个天然的对照实验**，比拿两个不相干的产品比要干净得多。

右边两条内容。第 30 页，pi 的「刻意不做」清单，副标里我直接把几条抄出来了——No MCP、No sub-agents、No permission popups。你没看错，**一个产品的卖点是一串"不"。**

第 31 页，oh my pi 和它的 FORK.md。这里有两个数字：**63 万行 TypeScript，7 万行 Rust。**还有那套 tier 成本模型——先剧透一句，**那套模型是我认为这整场分享里最可迁移的一个工程方法**，跟 AI 一点关系都没有，但你只要维护过 fork 就会想抄。

底下绿边框的承诺：读完这一章你会知道，为什么 pi 的卖点是一份"刻意不做"的清单，以及**维护一个深度 fork 的成本该怎么量化**。注意"量化"这个词——不是"怎么熬过去"，是"怎么算出来"。

**别漏了说**：
- "同一条血脉、两个反方向"是这一章的骨架，务必点明 oh my pi 是 pi 的 fork，否则听众会以为是两个不相干的产品。
- 提前预告 FORK.md 的 tier 模型"是全场最可迁移的方法"，给 P31 蓄势。
- "刻意不做"这个说法本身要停一拍——一个产品的卖点是一串"不"，这个反常识点值得让听众咂摸一下。

**可能被问**：
- Q：为什么挑这两个样本，而不是市占率更高的？
  A：因为它们的设计意图写得最清楚——一个把哲学写进 README，一个把 fork 成本写成一份文档。**可讲的不是它们多强，是它们把"为什么"留下来了。**

**过渡到下一页**：先看小的那个。它的 README 里有一节叫 Philosophy，我们一条一条看。

## P30 · 为什么极客圈喜欢 pi：一份"刻意不做"的清单

**一句话主旨**：pi 用"不做什么"定义自己，把决定权还给使用者。

**怎么讲**：

刚才说这一章看两个样本，先看小的这个。

标题：**pi 的卖点，是一份"刻意不做"的清单。**副标题解释了这有多反常——别人的 README 写"我们支持什么"，pi 的 README 有一节叫 Philosophy，逐条写"**我们不做什么，以及你该怎么自己做**"。

看左边这张表。左边红色的一列是"不做"，右边绿色的一列是"官方给的替代方案"，我做了意译。我一条一条念，你们感受一下节奏。[慢]

**第一条，No MCP。**替代方案：写个带 README 的 CLI 工具就够了；真要 MCP，自己写个扩展加上去。

**第二条，No sub-agents。**用 tmux 多开几个 pi，或者自己写扩展。下面那行灰字是作者原话的意译——**子代理是"黑箱里的黑箱"，你对它在干什么零可见度。**

**第三条，No permission popups。**跑在容器里，或者自己写确认流程。下面这个箭头是我加的注解：**把安全边界交给操作系统，而不是假装在应用层解决。**

**第四条，No plan mode。**把计划写进文件；想要就自己做一个。

**第五条，No built-in to-dos。**用一个 TODO.md 就行。琥珀色那行是原文理由——"**它们让模型更糊涂**"，多出来的状态模型还得自己维护。

**第六条，No background bash。**用 tmux，全程可观测，还能直接手动介入。

六条念完，你们应该听出来一个共同的模式了：**每一条"不做"，后面都跟着一个"你可以这样自己做"。**它不是砍功能，是把决定权推回给你。

底下那条分割线下面是贯穿始终的一句话——"Pi is **aggressively extensible** so it doesn't have to dictate your workflow"，激进地可扩展，所以它不必规定你的工作流。官网还有一句同样精准：**"primitives, not features"，给你零件，不给你成品。**

右边三张卡。第一张，"自扩展"是个真闭环，这是我最服的一点：扩展文档**随 npm 包一起发布**，system prompt 里**直接写死"你自己的文档在哪"**；每份扩展文档的第一行就是"让 pi 自己写"；写完**热加载**，agent 还能自己触发重载。所以"想要个功能就让它自己长出来"这句话在这儿是真的成立，不是宣传。

第二张，可读、可改、可拥有：会话是**人能读的 JSONL 树**，可以 fork、resume、回到任意一步换条路;MIT 协议、依赖极少、版本锁死，甚至**在配置上拒绝当天新发布的依赖**——这是防供应链投毒的土办法，但很有效;作者还把自己的真实工作会话公开成了数据集。

第三张，它不只是小圈子自嗨：**OpenClaw 的底层就是 pi**，官方口径是"Pi is the minimal agent within OpenClaw";OpenAI 的开源社区文档里也直接点名了 pi，跟 Codex、OpenCode、Cline 并列。

最底下这句是 pi.dev 首页的 slogan，也是我今天整场的题眼：**"There are many agent harnesses but this one is yours."** 有很多 agent harness，但这一个是你的。极客喜欢它，不是因为功能多，而是因为**它留了足够的空位给你自己填，并且它相信你填得比它好**。

**别漏了说**：
- 六条"不做"要有节奏地一条条念，中间不要插评论，念完再总结"每条后面都跟着一个替代方案"。这个节奏本身就是内容。
- No permission popups 是全场最有争议的一条，必须两边都讲（见下方 Q&A），不要替听众下结论。
- "primitives, not features" 和 "this one is yours" 是两句题眼，念的时候要慢，值得重复一遍中文。
- 证据出处要报一下：README 的 Philosophy 节、docs/usage.md 的 Design Principles、pi.dev 抓取于 2026-08-01、作者博客 2025-11-30。

**可能被问**：
- Q：No permission popups 不就是不安全吗？这在企业里根本没法用。
  A：**这条我认为争议最大，两种说法我都摆一下。**支持方的逻辑是：应用层的确认弹窗是"安全剧场"——用户点十次之后就无脑点同意了，真正的边界应该在操作系统和容器上。反对方的逻辑是：现实中大量用户就是裸跑在自己的开发机上，没有容器，那这条就等于把风险全推给用户。我个人偏向前者，但我承认它对使用者的要求高得多，**企业环境里我不会推荐这么用**。
- Q：No sub-agents，可是多 agent 明明有用啊？
  A：作者的理由是可见度，不是效果。而且他给的替代是 tmux 多开——本质上还是多 agent，只是把编排权交给你，而不是藏在框架里。有意思的是，下一页那个 fork 就把 sub-agent 加回来了，还加成了 DAG。**同一份代码，两个作者，两种答案。**
- Q：那这些都要自己写，上手成本不是很高吗？
  A：是。**pi 明确不是给所有人用的。**如果你想开箱即用，上一页右上角和右下角有的是选择。它的目标用户就是那些"宁可自己搭也不愿被规定工作流"的人。
- Q：pi 的 star 是不是虚高？
  A：这我判断不了，也没有数据。我只能说 OpenClaw 用它做底层、OpenAI 文档点名它，这两条是可核查的外部信号。

**过渡到下一页**：那么，如果有人不满足于"自己填空位"，而是直接把整个内核推倒重写呢？

## P31 · oh my pi：一次重写级深度 fork，以及它最该被抄的那一页

**一句话主旨**：真正值钱的不是那 63 万行，是 FORK.md 那套 tier 成本模型。

**怎么讲**：

上一页我们看的是"最小"，这一页看"最全"——而且是从同一份代码长出来的。

先介绍作者：**他是写 VMProtect 去虚拟化器的逆向工程师。**这个背景很重要，你待会儿会在他的技术选择里到处看到逆向工程师的痕迹。他没有"用" pi，他**重写**了 pi。

看左上角这四个数字，我念慢一点，口径先说：**这些行数是我在本地 v16.3.12 上实测点算的，不是官方公布的。**[慢] **六十三万零七百五十三行 TypeScript**;**六万九千九百零一行自研 Rust，七个 crate**;**一百二十一篇设计文档**;**三十八万八千四百八十六行测试，一千五百六十八个测试文件。**[停]

对比一下：上一页那个 pi，卖点是"我什么都不做"。这个 fork，六十三万行。**同源，反方向。**

中间这十二个方块是相对 pi 的十二项增量，我不逐个念，挑几个有代表性的指一下。**snapcompact**：把要丢掉的历史画成点阵图，让视觉模型"读图"回忆——这是我见过最野的压缩思路。**hashline**：带内容指纹的行锚定补丁语言。**Rust 热路径**：grep、glob、PTY、shell 不是"加速"，是**唯一实现**，注意这个措辞的差别。**TTSR**：在违规的那一刻打断并回滚重跑，而不是事后骂一顿。**advisor / watchdog**：主 agent 会自我说服，所以挂第二个模型，只看增量做同行评审。**swarm**：YAML 声明 DAG 跑多 agent 流水线——**你们注意到没有，上一页 pi 说 No sub-agents，这里加回来了，还加成了 DAG。**

底下这两行请务必跟我一起看。第一行：**LICENSE 里署名两行**——Mario Zechner 2025，Can Bölük 2025 到 2026。**fork 的礼节写进了 LICENSE 里。**第二行是我自己加的免责声明，也是我的真心话：**以上大部分是"你可能不需要"的工程。它们的价值在于示范"能做到什么程度"，不在于照抄。**

好，现在看右边。**这才是我今天最想推销给你们的一页。**

它叫 FORK.md。它干的事情是：把"维护一个高速上游的深度 fork"这个问题，**从英雄主义问题变成一个可度量的成本函数。**中间这句黄字是整套模型的口号：**"pick the lowest tier that works"——挑能干成事的最低那一档。**

看这三个框，**注意它们的宽度是不一样的，这是故意的。**

最上面最窄的，**Tier 2，真冲突**：深改核心、打 Rust 补丁。代价写在下面——要缝隙标记、要台账、要漂移测试。三样都得有。

中间，**Tier 1，冲突极轻微**：只在核心的某个列表或者联合类型里加一行。注意这行小字——**全仓只允许四个这样的坐标。**他给自己定了个硬配额。

最下面最宽、绿色加粗的，**Tier 0，零冲突，优先用它做一切**：不碰上游任何文件，所以**上游同步在物理上无法与之冲突**。包括 hooks、extensions、能力提供者、skills、rules，以及磁盘上的工具和命令。

框越往下越宽，就是在说：**你应该把绝大部分东西塞进 Tier 0。**

最后，右边这条绿色虚线箭头，加上底下那个框——**这是我认为最漂亮的一招：Tier 2 → Tier 1 → 0 的降级路径。**做法是：在核心里加**一行缝隙**，就是一个 hook 调用;真逻辑放到缝隙后面的扩展里，这部分就变成 Tier 0 了;然后——**把这行缝隙提 PR 给上游**。合了，你的核心补丁就**永远消失**了。

那句话我念完就过：「**最便宜的分歧，是被消除掉的分歧。**」[停]

这套东西跟 AI 一点关系都没有。你维护任何一个上游跑得很快的 fork，都能直接抄。

**别漏了说**：
- 四个规模数字必须带口径："本地 v16.3.12 实测点算"，不是官方数字。
- **图上那个 hashline 方块里写着"就是 P8 那场实验里的胜出格式"——这个页码引用在当前 37 页的版本里对不上（P8 现在是第二章的章节页）。上台别念页码，改说"就是前面讲工具那部分提到的补丁格式"，或者干脆跳过这半句。**
- 三个 tier 的框宽是递增的，这是视觉语言，一定要用手指一下并说破，否则听众看不出来。
- Tier 1 "全仓只允许 4 个坐标"这个硬配额是整套模型可执行性的关键，别漏。
- swarm 与上一页 No sub-agents 的对照，是本章"同源反方向"的最好证据，要点出来。
- 结尾必须强调 FORK.md 与 AI 无关、可直接迁移，这是本页的落点。

**可能被问**：
- Q：63 万行里有多少是 AI 生成的？
  A：**这个我没查到，会后补。**从 121 篇设计文档加 38 万行测试的比例看，人工设计的密度不低，但具体比例我不敢猜。
- Q：这个 fork 现在还跟得上上游吗？
  A：FORK.md 这套模型的目的就是让它跟得上。但我没有实测过它的同步频率和冲突率，**这个数字我只有它自己文档里的说法，属于一手文档、二手结论。**
- Q：Tier 1 为什么是"4 个"，这个数是怎么来的？
  A：文档里就是这么定的，没给推导过程。我理解它是个自律配额——**关键不在于是 4 还是 5，在于你给自己设了个上限并且写下来。**
- Q：普通团队真的用得上这套吗？我们又不 fork agent。
  A：只要你 fork 过任何上游活跃的开源项目就用得上。它的三个 tier 本质上是"改不改上游文件"和"改多少"，跟项目是什么完全无关。
- Q：这十二项增量里哪个最值得抄？
  A：我个人偏向工具两级加载和 advisor/watchdog，因为它们解的问题最通用。但这是我的偏好，不是评测结论。
