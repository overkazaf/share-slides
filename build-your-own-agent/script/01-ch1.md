## P5 · 第 01 章 · 定义

**一句话主旨**：这一章不讲技术，只划一条边界：什么算 agent，什么不算。

**怎么讲**：
刚才目录那页我说了，七章，重心在 CH3 和 CH7。那我们从第一章开始——这一页我走得很快，三十秒，因为它本身不承载信息，只是告诉大家我们现在站在哪儿。（停一拍）左边这个大大的 01，还有下面"定义"两个字，就是本章的名字。再往下这行加粗的问题——"Agent 到底是什么？"——整章只回答它。底下这段小字我不念，我解释一下我的意图：这一章我刻意不谈任何技术细节，不讲上下文、不讲工具、不讲多智能体，那些全在 CH3。这里只解决一件事，就是**什么算 agent、什么不算**，以及为什么这条边界值得认真划。为什么值得？因为现在这个词被用得太松了，套壳对话框叫 agent，写死的脚本也叫 agent，大家嘴上说的是同一个词，脑子里想的是完全不同的两个东西，后面所有讨论都会跑偏。再看这排小圆点，一共七个，第一个是亮的——这是本场的进度条，每章扉页你都会看到它往前走一格。右边是本章的小目录，只有两页：第 6 页讲什么是 agent，第 7 页讲决策权谱系。底下这个青色边框的框，是我给这一章的承诺：读完这两页，判断一个系统是不是 agent，你只需要看一条——**下一步做什么，是代码写死的，还是模型现场决定的**。这句话我等会儿还会说两遍，因为它是整章的钥匙。

**别漏了说**：
- 强调"这一章不谈技术细节"是**刻意的**，不是没准备——防止有人以为你在跳过硬货。
- 七个进度点要指一下，第一次出现要交代这个视觉约定，后面六个章扉页就不用再解释了。
- 那句"判据只有一条"要预告，让听众带着这条判据去看下一页。

**可能被问**：
- Q：定义有必要花两页吗？直接讲实现不行吗？
  A：如果全场只有工程同学，可以跳。但只要有人把 chatbot 也叫 agent，后面"为什么要 harness"这一大段就没有立足点。我宁可花两页。
- Q：这是谁的定义？业界统一吗？
  A：不统一。我采用的是 Anthropic 那套划分，下一页页脚会标出处。别家（比如学术界的 agent 定义）范围更宽，我会在 P7 说清楚我的口径。

**过渡到下一页**：那我们就把这条边界直接摊开——下一页是全场的地基，一张图。

## P6 · 什么是 Agent：一个会自己决定下一步的循环

**一句话主旨**：Agent 是"模型决策 → 工具 → 环境 → 回灌"的闭环，三者缺一都不算。

**怎么讲**：
刚才说本章只有一条判据，答案就是这张图。这是全场的地基，后面十几页的技术点全挂在它上面，所以我讲慢一点。（停一拍）从最左边看，青色这个盒子是输入，"目标 / 任务"，请注意底下那行小字——**一句自然语言**，比如"把这个 crash 修了"。人只给到这儿，不给步骤。往右进入那个黄色虚线框，框上标着 AGENT LOOP，框里的东西由模型驱动，框外不是，这条虚线就是边界。第一格 ① 模型决策：读完当前上下文，只回答一个问题——"下一步做什么"。这句话是整张图的心脏。第二格 ② 发出工具调用，输出的不是文字，是结构化的 tool_calls，read、edit、bash、search 这些。第三格 ③ 环境真实执行——文件、进程、网络，甚至人。看这行小字：**副作用发生在这里**。前两格都还在"想"，只有这一格真的动了外面的世界。所以红色那行注解指的就是这一段回程线：护栏装在这里，权限、沙箱、审批——装在别处都晚了。往下拐是 ④ 结果回灌，observation 追加进上下文。我特意写了一句"报错也是信息，甚至是最好的信息"，因为对模型来说，一条真实的编译错误比十句"你再想想"有用得多。然后箭头拐回 ①，转下一圈。什么时候停？看上面这条青色虚线：模型这轮不再要工具了，循环就收敛，直接走到最右边的"交付"。底下这条紫色横条是上下文，append-only，每一步都写进来、每一次决策都从这里读出去，它是这台机器唯一的内存。左下角那行灰字是代价提醒：每转一圈，上下文更长、更贵，也更接近答案。最后看右下角图例，判据收成三条——能动手、能循环、能看见；每条底下都写了缺了会退化成什么：退成 chatbot、退成提示链、退成开环生成。**三者缺一，就不算 agent。**

**别漏了说**：
- 三个必要条件要一条一条点名，别整块带过——这是本页唯一必须被记住的东西，后面 CH3 每一节都在补其中某一条。
- "护栏装在 ③ 这一段"必须说出口。很多人以为安全是在提示词里写"请不要删库"，这页告诉他们不是。
- 上下文是 append-only、是唯一的内存——这句是 P18/P19 讲压缩的伏笔，这里先埋。
- 口径要交代：这张图的定义边界来自 Anthropic 的《Building Effective Agents》，页脚有标；循环骨架可以在 pi-mono 的 packages/agent 里对照到实现。这不是某家官方架构图，是我为讲清楚而做的抽象。

**可能被问**：
- Q：那 RAG 算不算 agent？
  A：按这三条看，标准 RAG 是检索一次、生成一次，没有"自己判停的循环"，也没有把执行结果回灌再决策，所以按我这套口径不算。但如果它能自己决定检索几轮、检索完不满意再检索，那就滑到 agent 那边去了——这正是下一页要讲的连续谱系。
- Q：循环不收敛怎么办？会一直转吗？
  A：会。这就是为什么真实实现里除了"模型不再要工具"这个自然退出条件，还必须有硬性的轮数上限、token 上限、超时。这一页的图是理想形态，工程上必须加闸——P15 讲主循环状态机时会展开。
- Q：④ 回灌之后上下文一直涨，怎么控？
  A：CH3 有两页专门讲压缩（P18–P19）。这里先记住"它一定会涨"就够了。
- Q：pi-mono 里这个循环具体在哪个文件？
  A：我标的是 packages/agent 这个包。具体到函数级别的对照我这次没有整理成页，会后可以一起翻代码。

**过渡到下一页**：不过现实里很少有系统是纯粹的这张图——大部分东西卡在中间，所以下一页我们把"是不是 agent"这个是非题，改成一把尺子。

## P7 · 决策权谱系：Chatbot → Workflow → Agent → Multi-Agent

**一句话主旨**：Agent 不是是非题，是"决策权交出去多少"的连续刻度。

**怎么讲**：
上一页给了三条硬判据，但真拿去套现实系统，你会发现很多东西卡在中间——所以这页我把是非题换成一把尺子。（停一拍）先看标题下面这句，这是 Anthropic 的原话口径：**workflow 是用预定义的代码路径去编排模型和工具，agent 是模型自己动态决定流程和工具用法**。分界就在"路径由谁定"。中间这五个盒子从左到右是刻度。01 对话式，单轮问答、无工具、无状态，模型只输出文字，动手的永远是人。02 提示链，多步，但顺序是写死的——抽取、翻译、校对，走几步是代码说了算，模型只负责填空。03 工作流，代码定路径、模型定内容，下面列了路由、并行、编排者-执行者、评估-优化这几类经典模式，准确定义在 CH3。04 是黄色加粗那格，标着"本场主角"——智能体：**模型定路径，代码只给护栏**，自己选工具、自己决定跑几轮、自己判断做完没有。05 多智能体，agent 再派生 agent；这里我要说清楚一件有争议的事——它的主要收益是**上下文隔离**，不是"人多力量大"，代价和争议我放在 CH3 那页展开，那页我两边都会讲。（停一拍）再看下面这条渐变条，左端写着"人 / 代码"，右端写着"模型"，中间那行字是"谁决定下一步"——这才是这页真正的坐标轴，五个盒子只是刻度上的几个采样点，它们之间是**连续的**，你完全可以做出一个卡在 03 和 04 之间的东西。两端的注解是代价表：左边确定性高，可预测、可测试、可复现、便宜、出事好定位，代价是遇到没写过的分支就抓瞎；右边灵活性高，能吃长尾、能自我纠错、能处理没预设过的情况，代价是贵、慢、难复现、出事难归因。这两列你得同时看，不能只看一边。

**别漏了说**：
- 一定要说出"是连续的"这三个字，并明确五个盒子只是采样点——这页最容易被误读成五个分类。
- 两端代价必须对称地念完，不能只夸右边。这页的诚实度全在这两列小字上。
- takeaway 要念到位并解释：不要问"我该不该上 agent"，要问"**这一段决策我能不能写死**"；能写死的写死，写不死的才交给模型。绝大多数生产系统的正解是 **workflow 骨架 + 局部 agent**，不是全盘自主。这是本章唯一一条可以直接带走的工程准则。
- 出处口径：这个分类来自 Anthropic《Building Effective Agents》，2024 年 12 月。是一篇工程博客，不是标准，也不是论文——用它是因为它够干脆，不是因为它是权威。

**可能被问**：
- Q：盒子里写"四类经典模式"，页脚又写"五种 workflow 模式"，到底几种？
  A：我这里做了个拆分，原文把提示链也算作 workflow 模式之一，一共五种；我把提示链单独拎出来当 02 号刻度了，所以 03 这格里只剩四类。CH3 那页会按原文的五种完整列。这个不一致是我的排版取舍，先说明一下。
- Q：多智能体是不是就是比单 agent 强？
  A：不一定，我不替大家下结论。收益端确实存在——主要是上下文隔离，子 agent 把脏活的中间过程消化掉，只把结论回传给主 agent。代价端是 token 成倍涨、延迟涨、出问题更难归因。CH3 有一页专门对撞两边观点。
- Q：怎么判断"这一段决策能不能写死"？有量化方法吗？
  A：我没有一个能量化的判据，这是经验活。我自己的粗糙做法是：如果这个分支我能穷举出来并且写得完测试，就写死。更严谨的方法我没查到，会后有想法欢迎聊。
- Q：那 Claude Code、Cursor 这些落在哪一格？
  A：主体在 04，但内部有大量写死的 workflow 段落。这正是"workflow 骨架 + 局部 agent"的现实样子。具体全景对比在 CH5。
