## 1. 本章一句话

**这半章讲的全是同一件事的六个切面：上下文是有限预算，所以每一个工程决策——技能怎么放、工具给几个、要不要拆 agent、扩展点挂哪儿、记忆存哪层、谁来评判——本质上都是在回答「什么东西有资格常驻，什么东西用到才付费，以及这个决定由谁来做」。**

## 2. 论点链

### 论点 1 · SKILL 不是「写提示词」，是「分级加载的文件系统协议」；它真正改变的是**决策权归属**

**断言**：SKILL 相对 system prompt / RAG 的差异，不在内容质量，而在「谁、在什么时刻、决定这段内容进不进上下文」。RAG 是**检索器在推理前**按 embedding 相似度决定；system prompt 是**永远在**；SKILL 是**模型在运行时**按 description 自己决定。

**凭什么（一手）**：
- pi 的 `Skill` 结构体里**根本没有 `content` 字段**——只有 `name / description / filePath / baseDir / sourceInfo / disableModelInvocation`（`packages/coding-agent/src/core/skills.ts:74-81`）。正文从未被读进内存。
- 注入 system prompt 的只有三个 XML 字段 `<name>/<description>/<location>`，且提示语明写 *"Use the read tool to load a skill's file when the task matches its description."*（`core/skills.ts:335-357`，注释里标了标准出处 agentskills.io/integrate-skills）。
- 整个 skills 段的注入条件是 **`hasRead`**：`if (hasRead && skills.length > 0) prompt += formatSkillsForPrompt(skills)`（`core/system-prompt.ts:154-157`）。没有 read 工具就不列——因为列了也翻不开。
- 官方三级表（platform.claude.com/docs/…/agent-skills/overview，逐字）：Level 1 metadata **~100 tokens/skill，always**；Level 2 正文 **<5k tokens，triggered 时**；Level 3+ **None until accessed**，且 *"Scripts run through bash, and only their output enters context."*
- `description` 在 pi 里是**硬性必填**：缺失直接 `return { skill: null }`（`core/skills.ts:304-307`）。

**反方 / 边界**：
- **它不是免费，只是延迟计费**。Claude Code 官方原话：*"Once a skill loads, its content stays in context across turns, so every line is a recurring token cost."* 一旦加载，整个 session 都在。
- **压缩会吃掉 skill**：auto-compaction 后每个 skill 只重挂**前 5,000 tokens**，所有重挂 skill **共享 25,000 tokens 总预算**，旧的会被整个丢弃（官方 Claude Code 文档）。
- 幻灯片上的「≈ 几十 token / 个」与官方 **~100 tokens/skill** 是同量级但不同数；讲稿自己承认这是**按长度估的量级，不是实测**。建议口径统一到「约一百 token 量级」。

### 论点 2 · 「给模型多少工具」没有正确答案，两派各自自洽；真正的变量不是数量而是**重叠度**与**信任边界**

**断言**：极简派（pi：内置 7、默认给 4）与全能派（oh-my-pi：30+、两级发放 + BM25 发现）不是对错之分，而是对「shell 可不可信 / 要不要逐调用审计 / 延迟敏不敏感」三个前置条件的不同回答。

**凭什么（一手）**：
- pi：`export type ToolName = "read" | "bash" | "edit" | "write" | "grep" | "find" | "ls"`（`core/tools/index.ts:83-84`），默认激活 `["read","bash","edit","write"]`（`agent-session.ts:2592-2594`）。**grep/find/ls 是「做了但不给」，不是「没做」**——模型走 bash 调 `rg`/`fd`。SDK harness 路径更狠，只导出 4 个。
- oh-my-pi：`DEFAULT_ESSENTIAL_TOOL_NAMES = ["read","bash","edit","write","glob","eval"]`（**6 个**，`src/tools/index.ts`），其余靠 `search_tool_bm25` 检索激活；`BUILTIN_TOOLS` 本地点算 **30 个 + 5 个 HIDDEN**（v16.3.12；上游 README v17.2.2 自称 32，版本差非矛盾）。MCP 侧同款：`mcp.discoveryMode` 开启后 MCP 工具默认隐藏。
- 「工具定义也是常驻成本」有官方硬数字支撑（不是推测）：把 MCP 工具定义改成文件系统上的 TS 文件按需读取，同一工作流 **150,000 → 2,000 tokens，-98.7%**（Anthropic《Code execution with MCP》2025-11-04）。
- 错误可自愈：pi 参数校验失败生成带字段路径的多行错误回喂模型（讲稿；对应 R10 的工具定义结构）。

**反方 / 边界**：
- **「工具一多就选错」这个流行说法，OpenAI 的一手材料明确反对**：*"The issue is **not solely the number of tools, but their similarity or overlap**. Some implementations successfully manage **more than 15 well-defined, distinct tools** while others struggle with **fewer than 10 overlapping tools**."*（OpenAI《A practical guide to building agents》p.16–17）。所以「少而正交」这条里，**正交比少重要**。
- BM25 工具发现的**命中率没有任何公开数据**——「描述写不好就搜不到」是它自己承认的失败模式，但没有量化。「待核实」。
- 幻灯片写「四个 essential + search_tool」= 5 个常驻，与 R08 代码点算的 **6 个 essential** 不一致（见 §4）。

### 论点 3 · 五种 workflow 模式是词汇表而非论证；它唯一 load-bearing 的信息在**最右列的适用条件**和**orchestrator-workers 被归为 workflow** 这个分类学动作

**断言**：这一页的价值不在五个形状，而在两点：(a) Anthropic 原文给出的 "when to use" 是**判据**不是描述；(b) 把 orchestrator-workers 划进 workflow，等于宣布「模型决定拆几份」≠「多智能体」，这为下一页的争论划了前提。

**凭什么（一手，Anthropic《Building Effective AI Agents》2024-12-19）**：
- 定义边界逐字：Workflows = *"systems where LLMs and tools are orchestrated through **predefined code paths**"*；Agents = *"systems where LLMs **dynamically direct their own processes and tool usage**"*。
- Orchestrator-workers 原文：*"a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results"*，适用于 *"complex tasks where you can't predict the subtasks needed"*——**编排骨架仍写在代码里**。
- Agent 的边界：*"open-ended problems where it's difficult or impossible to predict the required number of steps"*。
- 金句：*"Agentic systems often **trade latency and cost for better task performance**."*

**反方 / 边界**：
- ⑤ Evaluator-optimizer 下面那行「2026 年的实践发现：评审方不共享生成方的上下文，效果反而更好」**不是 2024 年原文**，是讲者加的注（讲稿自己标了）。台上必须区分，否则是把 2026 年的观察塞进 2024 年的嘴里。
- 分类边界在往下滑：2024 年划给 agent 的场景，2026 年用 workflow + 好的上下文工程也能做。形状层面成立，阈值层面不成立。
- 五种可嵌套组合，不是五选一。

### 论点 4 · 多智能体之争不是对错之争，是**任务形态之争**：隔离的收益 ∝ 子任务之间的解耦程度

**断言**：Anthropic 测的是**并行只读研究**（子任务之间几乎无隐式耦合），Cognition 说的是**协作写代码**（子任务之间充满隐式设计决策）。两边的结论在各自的任务形态下都成立。

**凭什么（一手，三方 + 时间戳）**：
- **2025-06-12 Cognition《Don't Build Multi-Agents》**（Walden Yan）两条原则逐字：*"Share context, and share full agent traces, not just individual messages"* / *"Actions carry implicit decisions, and conflicting decisions carry bad results"*。Flappy Bird 反例逐字：*"Subagent 1 … started building a background that looks like Super Mario Bros. Subagent 2 built you a bird, but it doesn't look like a game asset."*
- **2025-06-13 Anthropic《How we built our multi-agent research system》**：orchestrator-worker；*"outperformed single-agent Claude Opus 4 by **90.2%** on our internal research eval"*；*"agents typically use about **4× more tokens** than chat interactions, and multi-agent systems use about **15× more tokens** as chats"*；BrowseComp 上 *"token usage by itself explains **80% of the variance**"*。
- **Anthropic 自己写的不适用条件**（这是最少被引用、却最重要的一段）：*"domains that require **all agents to share the same context** or involve **many dependencies between agents** are not a good fit"*；*"most **coding tasks** involve **fewer truly parallelizable tasks** than research."* ——**Anthropic 和 Cognition 在「写代码不适合多 agent」这一点上其实是同意的。**
- **2025-06-16 LangChain**（Harrison Chase）一刀切判据：*"**read actions are inherently more parallelizable than write actions**."*
- **2026-04-22 Cognition《Multi-Agents: What's Actually Working》同一位作者**：三种能跑的模式（Code-Review Loop / Smart Friend / Manager-Child Delegation）；仍不行的是 *"the **unstructured-swarm** approach, arbitrary networks of agents negotiating with each other, is mostly a distraction"*；统一原则 *"Multi-agent systems work best today when **writes stay single-threaded** and the additional agents **contribute intelligence rather than actions**."*

**反方 / 边界（口径必须念清楚）**：
- **90.2% 是内部研究评测，自己测自己，任务集未公开**。不是第三方 benchmark。
- **4×/15× 是相对 chat，不是 multi-agent 相对 single-agent**。后者 15/4 ≈ 3.75× 属**二次推导，原文没有这个数**。
- LangChain 有立场：它做编排框架，「是工程问题不是架构问题」的结论对它有利。
- Flappy Bird 例子会过时，但机制不会：只要两个 agent 各自做隐含决策又不共享轨迹，风格漂移就还会发生。

### 论点 5 · 六种扩展点的骨架不是「功能表」，是**触发权表**——选扩展点等于在选「谁来按这个按钮」

**断言**：Context file / SKILL / Slash command / Tool·MCP / Hook / Subagent 六者的真正区分维度是触发者：人写常驻、模型判断、代码强制、模型派生。两个问题（「必须发生还是模型可判断」「是知识还是动作」）能挡掉绝大多数选型纠结。

**凭什么（一手）**：
- pi 的钩子面：`ExtensionAPI` 上 **33 个 `on()` 重载**（`core/extensions/types.ts:1193 起`，`grep -c "^\ton(" = 33`），其中**只有 8 个有 Result 类型、能改变流程**：`context`（改写送 LLM 的整个消息数组）、`before_provider_request`、`tool_call`（阻断执行）、`user_bash`（整体接管）、`tool_result`（改写结果）、`message_end`（替换定稿消息，注释要求保持原 role）、`session_before_compact`、`session_before_tree`。**「能观测的很多，能强制的很少」——Hook 的力量与危险是同一件事，这在代码里就能看出来。**
- pi 官方「刻意不做」清单（`docs/usage.md:301`）：*"It intentionally does not include built-in MCP, sub-agents, permission popups, plan mode, to-dos, or background bash."* 且 README:495/497 给了理由和替代路径。
- 但生态补上了：`examples/extensions/` 下 **79 个**示例，恰好覆盖 pi 不做的每一项（`permission-gate.ts` / `plan-mode/` / `sandbox/` / `subagent/` / `todo.ts` / `custom-compaction.ts`）。
- 扩展点的**评价标准**（omp `FORK.md` tier 成本模型，可直接迁移）：*"Every change has a **tier** = how much it costs to carry across an upstream sync… **Push everything you can down to Tier 0.**"* → **扩展点的价值 = 它把多少 Tier-2 需求降级为 Tier-0**。反过来，「加了很多 hook 但没人能只靠 hook 做完一件真事」= 扩展点失败。

**反方 / 边界**：
- Context file 的代价是**每轮复付**，写太长稀释注意力（讲稿：CLAUDE.md 越写越长，最后模型什么都不遵守）。
- Slash command 的陷阱：**模型不会主动用**。把重要约定写成 slash command 然后抱怨 agent 不遵守，是常见误用。
- 「pi 刻意不做 subagent」这句要说全：**内核不做，生态做**——`examples/extensions/subagent/index.ts` 有 **1015 行**参考实现。

### 论点 6 · 记忆必须按**尺度**分开设计；把三个尺度混成一个「记忆系统」是最常见的架构错误

**断言**：轮内（上下文窗口，秒~分）、会话内（会话树 + 压缩，小时）、跨会话（外部记忆，天~永久）三层的读写频率、可靠性要求、成本量级差好几个数量级，共用一套抽象必然在某一层上过设计、在另一层上失效。

**凭什么（一手）**：
- 轮内不是仓库是预算：Anthropic *"LLMs have an 'attention budget'… **Every new token introduced depletes this budget**"*；腐化机制是 n² 注意力被摊薄 + 长序列训练样本稀缺 → *"performance gradient rather than a hard cliff"*（2025-09-29）。实证锚点：Liu et al. 2023，相关文档放中间时 GPT-3.5-Turbo 表现**低于一篇文档都不给（closed-book 56.1%）**；Chroma Context Rot（18 模型），**只加 1 个干扰项**就低于 baseline。
- 会话内：pi 的 session 是真正的**树**，append-only 事件日志，**压缩本身也是树上的一个节点**（R10 §5–§6：路径回溯、压缩感知读取、fork/clone/resume/tree）。omp 同构：append-only session 树 + 可变 leaf 指针，*"压缩不再『视觉重启对话』；branch 只移 leaf 不写 entry"*，13 种 entry 类型 + 4 个 schema 版本迁移。
- 跨会话：最朴素形态是**文件**（可 review、可版本管理，白送）。工程化形态 = omp 的 mnemosyne/mnemopi：SQLite `working_memory → episodic_memory` 巩固，FTS5 三索引 + 触发器，向量存 `memory_embeddings.embedding_json`，混合打分 `dense*w + fts*w + importance*w` × 72h 半衰期时间衰减 × MMR 去冗余。
- 一个值得抄的细节（比架构更实用）：**embedding 输入截断用「头尾各半 + 中缝」**，因为 naive `slice(0, max)` 会让所有后期 episode 拿到相同前缀向量，**召回全废**。

**反方 / 边界**：
- **mnemosyne 这套双层记忆没有任何公开评测数字**——是设计描述，不是效果验证。「待核实」。
- 页面自身不一致：图里写 `mnemosyne`，页脚证据栏写 `mnemopi`。台上统一一个说法。
- 「先用文件，等文件多到检索不动了再上召回」是讲者经验判断，无一手数据支撑。

### 论点 7 · 纠偏的共同原则是**结构性地分离「生成」与「评判」**，而且这个分离必须由**代码**来保证，不能指望模型自觉

**断言**：事中拦截（流式层规则）与事后评审（第二个模型只读增量）解决的是同一个问题的两个时机——前者拦硬规则，后者判软质量；共同前提是「让模型自己评自己，它会自我吹捧」。

**凭什么（一手，omp 代码级）**：
- **TTSR（Time Traveling Stream Rules）** 的出发点写得极清楚：规则（「不许 `git push --force`」）写在 system prompt 里**模型照样违反，而你只能事后发现**。做法：`turn_start` 重置 buffer → 流式期间实时匹配 `text_delta`/`thinking_delta`/`toolcall_delta`（regex 或 **ast-grep 结构匹配**）→ 命中即 `agent.abort()`（不等扩展回调）→ `contextMode: "discard"` 时 `agent.replaceMessages(...)` **丢弃被打断的半截输出**，注入中断消息后 `agent.continue()` 重跑本轮。**违规从未进入历史**。
  - 最精妙的一点：对 `edit`/`write` 用**重建的源码快照**做 `checkAstSnapshot`——匹配的是「这次编辑之后代码会长成什么样」，不是「模型此刻写了什么字符」。
- **advisor / watchdog**：独立 `Agent` 实例 + 独立 `ToolSession`（id 后缀 `-advisor`），**不共享**主 agent 的文件快照 / seen-lines / 冲突状态 / 摘要缓存；默认工具池只读 `read`/`grep`/`glob` + `advise`；三档 severity（`nit` 非打断 / `concern` / `blocker` 打断式 steering）；`advisor.immuneTurns` 默认 3 限制打断频率。
- **`AdvisorEmissionGuard`（最值得抄的一段）**：在 `enqueueAdvice` 边界**用代码强制**「每次更新最多一条、绝不重复」——归一化（NFKC + 折叠空白，`"Stop."`/`"*Stop*"`/`"  stop  "` 都归到 `stop`）→ 空洞短语静默丢弃（`stop`/`done`/`lgtm`/`nothing to add`）→ 全 session 精确去重（FIFO 环 4096）→ 每周期最多一条。**且抑制对模型不可见**（`AdviseTool` 仍返回 `Recorded.`），以免模型换个说法绕过去重。
- 这条与 Cognition 2026 的 Code-Review Loop 对上：*"clean context leads to a notable improvement in capabilities when using a generator-verifier loop"*（作者自称反直觉）。

**反方 / 边界**：
- **事中拦截会误杀**——只适合规则明确、判定确定的违规（禁用 API、禁止路径），不适合「质量不够好」这类模糊判断。
- **advisor 是双倍成本**，适合无人值守长跑，不适合交互式（R08 自己的判断）。
- **已知刀口**（omp 文档自己记录的信任边界）：advisor 的工具池**不经过 approval wrapper**——`WATCHDOG.yml` 授予 mutating 工具时直接可用。讲这条比讲优点更能建立可信度。

## 3. 被低估的点

### (a) subagent 的真收益是**上下文隔离**，不是并行——用 token 成本数字反证

流行叙事是「多开几个 agent 一起干活更快」。但把三条一手证据摆在一起，并行这个解释站不住：

**第一，成本结构不支持「为了快」**。Anthropic 自报：agent ≈ **4× chat**，multi-agent ≈ **15× chat**。若只为并行提速，你付的是 3.75 倍于单 agent 的 token（此为推导，原文无此数）去买墙钟时间——这个交易在绝大多数任务上是亏的。讲稿的判断是对的：深度调研值，日常改代码绝对不值。

**第二，Anthropic 自己的归因指向 token 而非并发**。BrowseComp 上 *"token usage by itself explains **80% of the variance**"*。也就是说，多智能体的收益主要来自**多花了 token 去探索**。而这里有个关键推论：**同样多花 15 倍 token，塞进一个窗口和分进 N 个窗口，结果完全不同**——因为 context rot 是实证的（Chroma：只加 1 个干扰项就低于 baseline；Liu et al.：最坏情况 20/30 篇文档不如一篇不给）。**能把 15× token 花出去而不劣化，唯一的办法就是分窗口花。并行只是「分窗口」的一种交付方式，隔离才是那个起作用的机制。**

**第三，也是最决定性的一条：把并行完全拿掉，收益仍在。** Cognition 在反对多智能体的那篇文章里顺手记录了对 Claude Code 的观察：*"It **never does work in parallel** with the subtask agent, and the subtask agent is usually **only tasked with answering a question, not writing any code**."* 一个**从不并行、只读、只回答问题**的子代理，依然是 Anthropic 和 Cognition 双方都认可的有效形态。Anthropic 官方文档给出的理由完全是隔离而非速度：子代理 *"get their own fresh context, completely separate… Their work doesn't bloat your context. When done, they return a summary. **This isolation is why subagents help with long sessions.**"* 返回量级是 **1,000–2,000 tokens** 的凝练摘要。

**第四，实现层面也印证**。pi 的 subagent 参考实现里，隔离是**四重 CLI flag**：`--no-session`（不写会话）、`-p`（一次性 prompt，零上下文起步）、`--tools <list>`（裁剪工具集）、`--append-system-prompt`（换角色），进程由 `spawn()` 独立起。**上下文隔离由操作系统保证，不需要任何框架抽象**；并行只是 `parallel` 三种模式之一（另两种是 `single` / `chain`）。

**所以真正的评估公式是**：子代理值不值，看的不是「能不能并行」，而是「它的探索过程会往主窗口里倒多少垃圾」。Anthropic cookbook 实测里，未做管理的 research agent 末态上下文 **96.3% 是文件读取结果**（~322,946 tokens），推理文本只有 1.7%。子代理真正买到的，是把那 96.3% 关在别人的窗口里，只让 1,000–2,000 tokens 的结论过来。**它是一台上下文层面的压缩机，恰好长得像一个并发原语。**

### (b) Anthropic vs Cognition：两边都对，决定谁对的是三个可判定的条件

**Anthropic 的立场（公允复述）**：在**广度优先、只读、子任务彼此独立**的研究型任务上，orchestrator-worker 显著更好。子代理是 *"intelligent filters"*，靠 *"separation of concerns—distinct tools, prompts, and exploration trajectories—which reduces path dependency"*。数字：内部研究评测 +90.2%（自报口径）。适用信号：信息量超出单窗口、需要对接大量复杂工具、任务价值付得起账单。

**Cognition 的立场（公允复述）**：在**协作写代码**的任务上，拆多 agent 会烂，因为「行动隐含决策，决策冲突结果就烂」；且上下文共享必须是**完整轨迹**而非几条消息，而多 agent 架构天然做不到。替代方案不是「别拆」而是「单线程 + 专门训练一个压缩模型把历史蒸馏成关键决策与事件」。

**2026 年 Cognition 的更新（关键在于它不是打脸，是补条件）**：同一位作者（Walden Yan）在 2026-04-22 说 *"A lot has changed since then"*，承认三种模式实际可用——① **Code-Review Loop**，且评审方**不共享**编码方上下文反而更能抓 bug（作者自称反直觉，与他 2025 年的 Principle 1「共享完整轨迹」表面矛盾）；② **Smart Friend**，弱模型在难点上向强模型求助；③ **Manager-Child Delegation**，可行但需要大量 context engineering。仍然否定的是 **unstructured swarm**：*"arbitrary networks of agents negotiating with each other, is mostly a distraction"*，以及并行**写**。统一表述：*"writes stay single-threaded and the additional agents contribute intelligence rather than actions."*

**决定谁对的三个条件（可当场判定）**：
1. **读 or 写**。LangChain 的一刀切：*"read actions are inherently more parallelizable than write actions."* 子任务只读 → 站 Anthropic；要并行写 → 站 Cognition。
2. **子任务之间有没有隐式设计决策的耦合**。Flappy Bird 的背景风格和鸟的画风之间存在一个从未被写下来的共同决策——这类耦合越多，拆得越碎越烂。反之，「查 2021 年芯片危机」和「查 2025 年供应链」之间没有隐式共识需要维护。（注意 LangChain 也引了 Anthropic 自己的失败案例：3 个子 agent 里 2 个重复查同一件事，缺乏有效分工。）
3. **单窗口装不装得下**。Anthropic 的正向信号里有一条是 *"information that exceeds single context windows"*；如果装得下，隔离的收益直接归零，只剩 15× 的成本。

**最容易被忽略的和解点**：Anthropic 自己在同一篇文章里写了 *"most coding tasks involve fewer truly parallelizable tasks than research"* 和 *"domains that require all agents to share the same context… are not a good fit"*。**两家在「写代码不适合多 agent」上从来没有分歧**——分歧只存在于旁观者对两篇标题的对读中。这也是为什么这场「对撞」在 10 个月后能收敛得这么干净：它本来就不是一场关于事实的争论。

### (c) 渐进式披露到底在优化什么：常驻 token 与检索准确率**同向**，但代价是失败模式变得**不可见**

多数人把 progressive disclosure 理解成省钱。省钱只是副产品，而且这里有个不常见的好事：**成本和准确率在这个设计里是同向的，不是权衡关系**。

**同向的证据链**：
- 成本侧（官方算术）：单个 skill「常驻 : 满载」≈ **100 : 5,000 = 1 : 50**。按官方 per-skill 数值推算（**标注为推算，非 Anthropic 实测**），100 个 skill 走渐进式披露常驻 ≈ 10k tokens；同等内容全塞 system prompt ≈ 500k tokens，**超过 200K 窗口 2.5 倍，根本装不下**。
- 准确率侧（三条实证）：Anthropic 的 n² 摊薄机制；Chroma——**只加 1 个干扰项**，NIAH 表现就低于 baseline；Liu et al.——最坏情况下给 20/30 篇文档**不如一篇都不给**。
- → **即使窗口装得下，把 100 份 SOP 全塞进去也会因为 99 份不相关内容抬高噪声底而变差。** 省 token 和提信噪比是同一个动作的两面。

**但被优化掉的东西也被换了个位置——这是最被低估的部分**：
- RAG 的失败模式是**可见的**：检索器召回了错误的 chunk，你能在 trace 里看到那段无关文本。
- SKILL 的失败模式是**沉默的**：description 写成 "Helps with documents"，模型永远不会翻开它，**没有任何错误、没有任何日志、什么都不会发生**。你写了 800 行完美正文，它一次都没被读过，而系统表现得完全正常。
- 所以三级加载真正的设计取舍是：**用「入口 recall 的可见性」换「常驻 token + 信噪比」**。第一级只有 ~100 tokens，全部赌注押在那一句 description 上。官方把它定位为 *"critical for skill selection"*，pi 干脆把它设成硬性必填。**「大家花力气写正文，但决定正文会不会被看见的是那一句描述」——这句讲稿里的话，是全章最实用的一条。**

**顺带一个 40 年跨度的反差（可当包袱）**：Nielsen 2006 的硬约束是 *"designs that go beyond 2 disclosure levels typically have low usability because users often get lost."* 而 Agent Skills 明确用 3 级甚至 3+。为什么可以？因为读者从人换成了**会 `ls`/`grep`/`cat` 的模型**——导航成本从「跨屏迷路」变成「一次 bash 调用」。但**约束没有消失，只是换了形式**：官方要求「引用文件只保持一层深度」，因为嵌套引用会触发 `head -100` 式部分读取拿到不完整信息。**同一条 HCI 原则，换了用户之后，约束从「层级数 ≤ 2」重新参数化成「引用图深度 ≤ 1」。**

### (d)（附赠）「不共享上下文的评审方更强」这条洞见，在本章出现了三次——但它们不是三份独立证据

讲稿建议把三处串起来讲（P22 evaluator-optimizer、P23 Cognition 2026、P25 advisor），并称之为「全章唯一被反复交叉验证的结论」。**这个说法需要打个折**：
- P22 的 evaluator-optimizer 是 2024 年原文，**原文并没有说「不共享上下文」**——那行字是讲者加的 2026 年注解。
- P23 的 Cognition Code-Review Loop 和 P25 的 advisor/watchdog 是**同一条洞见的两个实例**，且都没有公开的量化对照。
- 唯一的一手表述是 Cognition 的 *"clean context leads to a notable improvement"*，作者自己标为反直觉，**没有给数字**。

所以正确的讲法是：**这是一条被多个独立实现不约而同采纳的工程直觉（pi 生态、omp advisor、Cognition、Claude Code 的只读子代理都指向它），但它至今缺少一份公开的量化验证。** 这样说比「三次交叉验证」更站得住，也更容易赢得懂行听众的信任。
