## 一、本章一句话

**给定模型之后你还能做的，全在 L2–L6 这五层；这五层的工程主题只有三个 —— 转圈（loop）、退回去（graph/session tree）、和只带得动多少东西上路（context budget）—— 而且每一个都有可取证的实现细节和明确的代价。**

## 二、论点链（7 条）

### 论点 1 · 一个 agent 拆开是七层，你真正要写的是中间五层

- **断言**：L1 模型是租的、L7 交互决定体验但不决定能力；被统称为 harness 的 L2（模型接入）/ L3（工具与护栏）/ L4（上下文）/ L5（编排）/ L6（可扩展）才是「造 agent」的实际工作面。
- **凭什么**：
  - 分层不是拍脑袋，是从 `pi-mono` 的包结构反推：`ai / agent / coding-agent / tui` 恰好对应 L2 / L5 / L3·L4·L6 / L7（P13 页脚自陈）。
  - 「harness = 模型之外的一切」有一手定义：Böckeler（martinfowler.com, 2026-04-02）；更窄的执行层定义见 HF 术语表（2026-05-25）「Agent = Model + Harness」（R04 §1.2）。
  - pi 自己的默认 system prompt 第一句就写着 `"...operating inside pi, a coding agent harness."`（`core/system-prompt.ts:121`，R10 §9）。
- **反方 / 边界**：
  - 七层**不是行业公认分法**，讲稿 P13 的 Q&A 里已自认。别人按 inner/outer harness 或 guides/sensors 切（Böckeler），切法完全不同。
  - **UI 算不算 harness 本身有分歧**：HF 的执行层定义**不含** UI，R04 §1.2 已把这一条标为「待核实」。P13 图把 L7 划在括号外，恰好是安全的做法 —— 讲的时候要说「这是范围声明」，不要说「这是定义」。
  - harness 这个词本身是 2025 H2 才完成语义迁移的，2023–2024 主流用词是 **scaffold**（R04 §1.1）。别把它讲成一个有明确源头的老概念。

### 论点 2 · 模型是主项，harness 是约 1/4 量级的次项 —— 但次项才是你能攥住的

- **断言**：换 harness 的收益真实存在但被严重夸大；它的价值不在幅度，在**它是你唯一能自己动的变量**。
- **凭什么（必须双向报）**：
  - 正向极值：Can Bölük《The Harness Problem》(2026-02-12) — 180 个 React 修 bug 任务 × 3 次 × 16 个模型，只换编辑格式（引入 Hashline），Grok Code Fast 1 **6.7% → 68.3%**，16 模型平均 **+15pp**，Grok 4 Fast 输出 token **-61%**。原作者自己写了「**越弱的模型收益越大**」（R03 §《The Harness Problem》）。
  - 冷水：Terminal-Bench 2.0 官方榜，22 个模型两端条目**均经官方 verified**，同模型换 harness 的 **中位跨度 5.39 分**，平均 7.56，≥10 分的 7/22，最大 20.90（GPT-5.1-Codex：Crux 57.75% vs Terminus 2 36.85%）（M05 §1.1）。
  - 反向对照：同一个 harness（Codex CLI）换模型，GPT-5.5 82.2% → GPT-5-Nano 11.5%，极差 **70.7pp**（M06 §1.1）。
  - 最扎心的单例：TB 2.1 上 Gemini 3 Pro 套 Terminus 2 得 **73.93%**，套 Google 自家 Gemini CLI 只有 **65.84%**，差 8.09 分（M05 §1.3，当前榜全部经审核）。
- **反方 / 边界（这是全场最大的雷，详见第四节）**：
  - 两个数字**口径不同**：①是第三方控制变量实验，②是官方榜上不同提交方各自 harness 的横向对比 —— 框架、工具集、运行预算都不一样，**不是控制变量**。
  - **「约 1/4 量级」这个说法的分子分母要说清楚**：M06 的推导是「同模型换 harness 极差 18.4pp ÷ 同 harness 换模型极差 70.7pp」。而 **18.4pp 那一条（Opus 4.6：Meta-Harness 76.40% vs Claude Code 57.98%）被 M05 §1.2 自己标为「不宜作为主论据」**（相差 3 个月、一方未核验）。用双方都核验的版本是 62.92% vs 57.98% = +4.94。
    → **推论（本文推导，非研究笔记原话）**：若换成「中位换 harness 5.39 ÷ 极差换模型 70.7」，比值只有约 **1/13**。所以「1/4」是**极值比极值**，是对 harness 最友好的口径。上台时最好说成「一个数量级以内、但明显小一档」，别把 1/4 说成精确结论。
  - 还有一条反证不能漏：mini-SWE-agent **100 行 Python** 在 SWE-bench Verified 拿 65%，同期精心设计的 scaffold 也就 70–75%（M05 §1.4）。**harness 的边际收益是「选错会掉很多分」，不是「做复杂就涨分」。**

### 论点 3 · harness 的核心资产是一条分界线：无状态纯函数内核 + 有状态的一切都挂在外面

- **断言**：`runAgentLoop` 只管转圈，不管存盘、压缩、权限、回溯；这些全由外层编排 + 事件钩子提供。你造 agent 时第一个要想清楚的就是这条线画在哪。
- **凭什么（代码级取证，commit `4488ad5`，workspace 0.83.0）**：
  - `agent-harness.ts` 1185 行；`executeTurn` 调 `runAgentLoop` 的 **6 个参数里 5 个由 harness 提供**（messages / context 快照 / loopConfig / 事件处理器 / streamFn），agent-loop 自己一个状态都不存（R10 §9.3）。
  - Turn Snapshot：`createTurnState()` 每轮冻结 **10 个字段**（messages / resources / toolContext / streamOptions / sessionId / systemPrompt / model / thinkingLevel / tools / activeTools），运行中 `setModel()` 不撕裂进行中的请求，下一轮才生效（R10 §9.2(2)）。
  - 相位状态机 5 相：`idle | turn | compaction | branch_summary | retry`，非 idle 一律抛 `busy` —— **不是布尔忙标志位**，因为它能回答「为什么忙」且相位迁移可枚举（R10 §9.2(1)，讲稿 P14 Q&A）。
  - 持久化时序：`message_end` 立即落盘；扩展的写进 `pendingSessionWrites`，只在 `turn_end` 边界 flush 并发 `save_point` —— 保证 transcript 顺序纯净、记录可重放（R10 §9.2(7)）。
  - 失败兜底：`emitRunFailure` 把异常补成一整套 `message_start → message_end → turn_end → agent_end`，上层永远看到「完整的一轮」（R10 §9.2(8)）。
- **反方 / 边界**：
  - **P14 讲的 AgentHarness 不是 `pi` CLI 实际跑的那条路**。R10 §0 的头号发现：产品路径是 `AgentSession`（`coding-agent/src/core/agent-session.ts:303`）+ `Agent`，`grep -rn "AgentHarness" packages/coding-agent/src/` **无输出**；AgentHarness 只被 `packages/evals` 用。两条路共享同一个 `agent-loop.ts` 内核，所以「内核纯函数」这个论点仍然成立，但「pi 的活教材」这句话要限定为**同一内核的第二种封装 / SDK 路径**。
  - 扩展性有固有代价：每个 hook 事件都是一份要长期维护的公开契约；能接管压缩这种强切点，出问题最难查（讲稿 P14 Q&A 已认）。
  - **计数口径待核实**：P14 页脚写「21 事件 / 10 可改流程」，R10 §7.6 实测 harness 路径是 **22 项结果映射 / 8 项可改流程**，扩展路径（`ExtensionAPI`）是 **33 个 `on()` / 8 个有 Result 类型**。三组数字都对不上，上台前必须核一次或改口径。

### 论点 4 · 循环真正难的地方不在循环，在中断、插队、截断、判停

- **断言**：`while(true){llm();tools();}` 是教科书骨架；工程量全在边界条件。pi 的双层 while 把三种排队语义做进内核。
- **凭什么**：
  - 双层结构：外层 `while(true)` 处理 follow-up；内层 `while (hasMoreToolCalls || pendingMessages.length > 0)` 处理 tool-call 链 + steering（`agent-loop.ts:170/:174`，R10 §1.2）。
  - **4 个判停点**：错误/中断（`:196-200`，唯一 abort 出口，不抛异常）／宿主 `shouldStopAfterTurn`（`:247-257`）／内层无工具无消息（`:174`）／外层 follow-up 为空（`:263-271`）。
  - `terminate` 语义极严：`shouldTerminateToolBatch` 要求批次内 **every** 一个结果都 `terminate === true`（`:582-584`）。
  - **截断保护**：`stopReason === "length"` → `failToolCallsFromTruncatedMessage()`，**整批判失败让模型重发**，绝不拿半截 JSON 去执行（`:211-213`）。
  - 并发边界画得极清楚：`prepareToolCall`（参数校验 + `beforeToolCall` 权限钩子）在 for 循环里**串行**跑完，只有 `execute` 进 `Promise.all`（`:489-554`）；`tool_execution_end` 按**完成顺序**发（UI 实时），tool-result 消息按 assistant **声明顺序**写（历史可重放）—— 同一个 for 循环里刻意拆开的两条时间线。
  - abort 三层落点：signal 透传 → 循环层把 aborted 当正常消息处理 → 工具层 3 处显式 `signal?.aborted` 检查（R10 §1.4）。
  - 错误恢复的两条契约：`StreamFunction` 一旦被调用**不得抛异常**，失败编码成 `stopReason`（`packages/ai/src/types.ts:314-324`）；中断留下的孤儿 tool_call 由 `transform-messages.ts` 补 `"No result provided"` 的错误 result —— 这是 abort 后还能继续对话的关键（R05 §1.5）。
- **反方 / 边界**：
  - **超时是空的**：pi 把超时交给工具自己管，bash 工具 timeout 默认不设。这是 pi 的选择，**要按坑讲不要按亮点讲**（讲稿 P15 明确要求）。内核统一超时会误杀长任务，交给工具则容易漏 —— 两边都要说。
  - 「截断即整批失败」会浪费一次调用，会被听成过度保守，必须给出「拿半个参数去写文件」的画面感。
  - 判停枚举有更好的外部参照：Claude Agent SDK 的 `ResultMessage.subtype`（`success` / `error_max_turns` / `error_max_budget_usd` / `error_during_execution` / `error_max_structured_output_retries`，且**只有 success 带 result**）；OpenAI Agents SDK `DEFAULT_MAX_TURNS = 10`（R05 §1.2）。pi 没有预算上限这个判停维度。

### 论点 5 · 会话树不是历史记录，是可执行状态

- **断言**：append-only + `parentId` 让「回到三步之前换个思路」变成状态操作而不是重来一遍；线性历史等于每次犯错都从头开始。
- **凭什么**：
  - 每条 entry 都继承 `SessionEntryBase { type, id, parentId: string|null, timestamp }`（`session-manager.ts:46-51`）—— **这就是树的父指针**。append 时 `parentId: this.leafId`，然后 `leafId` 前移（`:1044-1049`）。
  - **11 种条目**（harness 路径）里包含 `model_change` / `thinking_level_change` / `active_tools_change` / `leaf` —— 换模型、改思考档位、换工具集**本身就是事件**，所以整条历史能精确重放，不只是消息序列（R05 §4.3）。
  - 读取是路径回溯 + 压缩感知：`buildContextEntries` 沿 parentId 回到根，取路径上**最后一个** compaction 条目，把它放最前，只保留 `firstKeptEntryId` 之后的尾巴（`session-manager.ts:418-454`）。**压缩因此成为 L4 与 L5 的焊点**。
  - 分支不删旧数据：`branch(id)` 只移动 leafId，注释原文 `"Existing entries are not modified or deleted."`（`:1360-1365`）；`branchWithSummary` 额外追加一条 `branch_summary`，让被放弃的分支不至于白干。
  - 三种分叉语义（SDK 路径的声明式选择器）：`{kind:"all"} | {kind:"through_entry"} | {kind:"before_user_message"}`，后两者 `readPathToRootOrCompaction` —— **遇 compaction 就停**（`harness/session/fork.ts:4-24`）。
  - 谱系对比很好用：**Cursor = 文件快照**（只回滚代码）→ **Claude Code = 快照 + 线性 JSONL + 拷贝式分支**（`/branch` 明确是 "creates a copy…leaving the original intact"）→ **pi = 天然树形事件日志 + 物化分支表 + 树导航 API**（R05 §4.2–4.4）。
- **反方 / 边界**：
  - **「O(1)」这个词是页面上的措辞，代码不完全支持**。R10 §12 明确修正了旧结论：`/fork` 会 `createBranchedSession()` **新建一个 session 文件**（逐条重链 parentId、摘掉 label 条目），是 O(路径长度) 的拷贝；只有 `/tree` 的 `branch()` 是纯指针移动。
  - SQLite 后端 `branch_entries` 是分支物化表，切一次分支插整条路径，**旧 branch 行不回收 —— 已知的单调增长问题**（R05 §4.3）。取证 commit 的标题本身就是 `fix/sqlite-session-linear-time`。
  - 「被放弃的分支压成摘要注入」有反作用：**你刚否掉的思路，又以摘要形式回到了上下文里**（讲稿 P16 Q&A 已认，建议做成可配）。
  - 「向前是一张图」这半边要小心措辞：**LangGraph 不是纯 DAG**，它支持环，本质是 Pregel/BSP 消息传递；准确说法是「显式状态图 + 超步执行 + 可 checkpoint」（R05 §3.6 原文警告）。它真正的贡献是**把「什么时候算一轮结束」从模型判断变成图算法的不动点判定**。

### 论点 6 · 上下文是注意力预算，不是仓库 —— 而且这是关于注意力分配的断言，不是关于窗口大小的断言

- **断言**：窗口「能装下」不等于模型「找得到」；每多塞一个 token，都在稀释同一份有限的注意力。
- **凭什么（三层证据，机制 / 实证 / 厂商自认）**：
  - 机制（Anthropic 官方表述，2025-09-29《Effective context engineering for AI agents》）：transformer 每个 token 要 attend 到所有 token，**n 个 token 就是 n² 对关系**；加上训练分布层面长序列样本稀缺，所以是 **"performance gradient rather than a hard cliff"**（性能斜坡不是悬崖）。
  - 实证 A（位置效应）：Liu et al.《Lost in the Middle》—— U 型曲线，GPT-3.5-Turbo 在相关信息位于中间时，**表现低于完全不给文档的 closed-book（56.1%）**；且「扩展上下文的模型并不更会用上下文」。
  - 实证 B（长度本身是自变量）：Chroma《Context Rot》(2025-07-14)，18 个模型 —— **只加 1 个干扰项就低于 baseline**；反直觉的是把 haystack 句子**随机打乱反而更好**。
  - 厂商自认（P18 红框）：同一个 Gemini 3.6 Flash，长上下文召回 **128k 91.8% → 1M 54.0%**（Google DeepMind 官方模型页 GDM-MRCR v2）。
  - 占用结构的硬数字（页面上没用、但可临场补）：Anthropic cookbook 的 research agent 末态上下文里，**文件读取结果占 96.3%**（~322,946 tokens），工具调用记录 1.9%，agent 自己的推理文本只有 1.7%（R04 §4.1）。**上下文的绝大部分从来不是「对话」。**
- **反方 / 边界**：
  - **n² 是官方博客的直觉解释，不是注意力衰减的严格证明**（讲稿 P18 Q&A 已明确要求这样说）。不要当定理用。
  - 「性能斜坡不是悬崖」意味着**没有一个「安全长度」阈值**可给。所有「控制在 X token 以内」的建议都是经验值。
  - P18 的预算条**比例为示意**，右上角自己写了。这个口径必须在讲条形图之前先说，否则整页都会被当成实测数据。
  - 大窗口不是没意义 —— 「能装」和「能用好」是两件事，且中间被无视的现象**窗口越大越明显**。

### 论点 7 · 压缩必须是「可解释的有损」——你要说得出丢掉的是哪一类信息

- **断言**：「让 LLM 写个摘要」只是起点；工程量在切点合法性、保留策略、摘要迭代、以及缓存污染。
- **凭什么（pi 的四条 + omp 的一条反直觉路线）**：
  - **绝对阈值不用百分比**：`DEFAULT_COMPACTION_SETTINGS = { reserveTokens: 16384, keepRecentTokens: 20000 }`；判定就一行 `contextTokens > contextWindow - reserveTokens`（`compaction.ts:132-136 / :235-238`）。SDK 路径常量完全相同。
  - **切点白名单是一段自带 PPT 属性的代码**：`isCutPointMessage` 对 `toolResult` **直接 return false**（`:308-321`），注释原文 `"Never cut at tool results (they must follow their tool call)."` 切到轮中间就 `findTurnStartIndex` 回退到轮首并标 `isSplitTurn`，被劈开的半个 turn 额外生成 turn prefix summary —— **一次压缩可能发两次 LLM 请求**。
  - **摘要迭代而非重做**：有前次摘要时换用 `UPDATE_SUMMARIZATION_PROMPT`（`:643`），规则是 PRESERVE / ADD / 把 Progress 里的 In Progress 移到 Done。摘要 prompt 是固定 6 段（Goal / Constraints & Preferences / Progress / Key Decisions / Next Steps / Critical Context），结尾硬约束 `"Preserve exact file paths, function names, and error messages."`
  - **独立缓存独立会话**：不污染主线 prompt 缓存 —— 讲稿点名「最容易漏、漏了最疼」的一条。maxTokens = `0.8 × reserveTokens`（turn-prefix 摘要用 0.5×）。
  - **三道防重复触发的护栏**（页面上没画，很值得口述）：换模型豁免（小窗切大窗时旧 overflow 不再触发）／压缩边界时间戳比较／**overflow 只救一次**（`_overflowRecoveryAttempted`，第二次直接告诉用户换大窗模型）（R10 §6.2）。
  - **omp 的第三条路 snapcompact**：把要丢弃的历史**本地确定性光栅化成点阵 PNG**，零 LLM 调用、零 API key、零网络。三条理由都有源码顶部注释支撑：①计费不对称 —— Gemini 3.x 按 `media_resolution` **每图固定 1,120 token、与像素无关**，所以放大到 2048px 是纯赚；而 OpenAI 是**面积计费**（32px patch × 1.2，10k-patch 预算），分辨率提不了 chars/$，所以停在 1568。②**存在 OCR 悬崖**：密排 `6x12-dim` 在 opus-4.8 上 f1 掉到 **.351**（低于 ~16px/char 下限，模型直接弃答），拉开字距的 `11on16-bw` 反而 **.806**；Gemini 侧加行距 .807 → .934。③零依赖 = **窗口已经爆了、摘要式压缩恰好失效时它仍然能跑**。它在 omp 里是**默认压缩策略**（`settings-schema.ts:1943`）。
  - 安全顺序：**先脱敏 → 再光栅化 → 最后按 provider 预算裁图**，保证 secret 不被烙进图像。中央凹布局 `[文本头][HQ×3][密集LQ×N][HQ×3][文本尾]`，超预算先丢最老的中段。
- **反方 / 边界**：
  - **.351 / .806 是项目自测、单一来源、未独立复现**（引自 snapcompact 源码顶部注释）。讲稿要求当场说明。只当方向性信号，不当基准。
  - 「某些模型按每图固定预算计价」—— 计价规则会变，讲稿 Q&A 里作者自己说「没有逐家核对，会后补」。**待核实**。

## 三、被低估的点

### (a) 「上下文是预算不是仓库」是关于**注意力力学**的断言，不是关于窗口大小的断言

最常见的误读是把它听成「窗口不够大，所以要省着用」——那样的话，1M 窗口一出现，这条建议就该作废了。它恰恰相反：

1. **失效的不是容量，是信噪比**。Chroma 的关键设计是把「长度」作为独立自变量：内容不变、只加**一个干扰项**，性能就低于 baseline。这不是装不下，是**注意力被分掉了**。
2. **更狠的是那个反直觉结果**：把 haystack 句子随机打乱，模型**反而更好**。如果瓶颈是容量，打乱应该无影响或更差；它更好，说明模型在跟**上下文内部的结构性干扰**较劲 —— 连贯的无关叙述比零散的无关句子更能骗走注意力。这直接对应 Drew Breunig 的 Distraction / Confusion / Clash 三种失效（R04 §2.4）。
3. **位置也不是中性的**：Lost in the Middle 的 U 型意味着上下文里存在「注意力盲区」——同样一段内容，放中间约等于没放（GPT-3.5-Turbo 甚至低于 closed-book 56.1%）。所以 **compaction 不只是删东西，它同时是在给幸存内容重新分配位置**。递诵（Manus 的 `todo.md`、Anthropic 的 `NOTES.md`）之所以有效，靠的就是把目标反复推回近端注意力窗口 —— 这是纯粹的位置操纵，跟省 token 无关。
4. **一条工程佐证**：pi 的压缩阈值用**绝对值 16K 而不是百分比**（`reserveTokens`）。理由是「窗口越大，百分比留出来的空间越离谱」—— 这个选择只有在「有效工作区并不随窗口线性放大」的前提下才成立。**一行常量就是对「预算说」的投票。**

> 上台一句话：这不是「窗口不够」，是「注意力不够」。窗口从 128k 加到 1M，召回从 91.8% 掉到 54.0% —— **容量涨了 8 倍，能力掉了近一半**，这就证明两者不是同一回事。

### (b) 双层 while 到底买到了什么（单层买不到）

单层循环也能跑完 tool-call 链。双层多买的是**「已收工」这个可观测、可重入的状态**：

1. **三种排队语义被分开建模**：steer（运行中插队，内层开头注入）／follow-up（agent 已发 `agent_end`、用户又追加活，外层再来一遍）／next-turn（配置切换，`prepareNextTurn` 时才生效）。单层循环只能把这三件事挤成一件，结果要么把 follow-up 当 steering（用户改主意会被当成对当前工具链的补充）、要么把 steering 当新会话（打断重来）。
2. **turn snapshot 链不断裂**。外层重入时走的还是同一条 `runAgentLoop`，`createTurnState()` 的冻结/重建链条连续，`save_point` 序列连续。如果靠「循环外面再包一层调用方重启」来实现 follow-up，你会丢掉这条链：重启意味着重新组装 context、重新算快照，而且中间那段「已 idle 但马上又要跑」的窗口里，扩展的 pending 写往哪 flush 就成了未定义行为。
3. **背压和失败回滚是队列级的**：`QueueMode = "all" | "one-at-a-time"`（默认后者）；`drainQueuedMessages` 在下游失败时 `queue.unshift(...messages)` **把消息塞回队列**（`:479-480`）。`abort()` 还返回 `AbortResult { clearedSteer, clearedFollowUp }` —— **被清掉的排队消息还给调用方**，TUI 可以塞回编辑器。这些语义只有在「队列属于循环内核」时才可能，外挂一层做不到。
4. **两级判停对应两级责任**：内层判停是「模型说完了」（`hasMoreToolCalls`、`terminate`），外层判停是「宿主说完了」（`getFollowUpMessages` 空 / `shouldStopAfterTurn`）。**模型的收工权和宿主的收工权被分在了不同层** —— 这是 R05 §1.4 说「三种排队语义做进内核，罕见」的实质。

### (c) 「会话树 = 可执行状态」对重试成本的真实含义

这条主张的价值和它的陷阱是同一件事：**它只让上下文维度的回退变便宜，对世界状态一个字都没说。**

1. **便宜的那一半是真的**：回退 = 移动 leafId + 后续 append 长出新分支，旧条目不改不删（`branch()` 注释原文）。读取成本 = O(路径长度)，而且遇 compaction 就停 —— **压缩点天然是重试的成本天花板**。重试不再需要「重新执行以获得状态」，因为状态就是日志本身。
2. **贵的那一半没人提**：LangGraph 官方的警告最直白 —— **"Replay re-executes nodes… LLM calls, API requests, and interrupts fire again"**、**"side effects must be idempotent"**。Claude Code 的 checkpoint 文档更具体：**bash 造成的 `rm/mv/cp` 改动 rewind 不回来；subagent 的编辑不在本 session 的 checkpoint 内；symlink/hardlink 路径跳过不还原**。官方自己的定位是 **"checkpoints as 'local undo', Git as 'permanent history'"**。
3. **所以真正的结论是**：会话树把重试成本从「上下文重建」搬到了「环境回滚」。你省下的是 token 和 turn，你欠下的是文件系统、git 状态、已发出的网络请求。**这正是为什么 pi 的 examples 里必须有 `git-checkpoint.ts` 和 `sandbox/`** —— 树只管自己那一半，另一半得你补。
4. **还有两笔隐性账**：`/fork` 是**新建文件的 O(路径) 拷贝**（不是 O(1)）；SQLite 的 `branch_entries` 每切一次分支插整条路径且**旧行不回收**。「便宜的重试」在存储侧是单调增长的。
5. **一个正面的推论**：既然 `model_change` / `thinking_level_change` / `active_tools_change` 都是树上的条目，那「用便宜模型跑到第 5 步、发现不行、回到第 3 步换贵模型重试」是**一次状态操作**，不是一次重跑。这才是「可执行状态」最值钱的用法，页面上没点破。

### (d) 一个被当成实现细节的元方法论：先问「有没有不调 LLM 的做法」

snapcompact 最容易被讲成猎奇（「把文字画成图，好酷」）。R08 §6.1 第 8 条给出的真正启发是另一句：**「压缩/摘要之外的第三条路是确定性本地变换」**。判据是成本结构而不是效果：

- 摘要式压缩在 **overflow 恢复路径上恰好失效** —— 窗口已经爆了，你连那次摘要调用都发不出去。任何依赖 LLM 的兜底方案在最需要它的时刻都不可用。
- 零 LLM 调用同时消掉了三样东西：一次计费、一次延迟、**一次幻觉机会**。
- 同源的还有一条：omp 把 **eval 数字写进代码注释**（`snapcompact.ts:1-46`）。半年后没人记得为什么是 1932px，除非注释里就写着 `f1 .806 vs .755`。**参数和它的证据住在一起** —— 这条比位图压缩本身更值得抄。

## 四、最容易被挑刺的地方 + 怎么答

### ① P13 的 6.7% → 68.3%（NOTES.md 标为全场最大的雷）

**风险**：只念极值 = 标题党，会被当场拆穿。

**必须成对出口的三句话**（顺序不能乱）：
1. 「6.7% → 68.3% 是 **16 个模型 × 180 任务、只换编辑工具格式** 这一个变量的结果 —— 但**原作者自己写了：越弱的模型收益越大**。这是最弱模型上的极值，不是普适倍数。」
2. 「同一张页面上我放了冷水：Terminal-Bench 官方榜 22 个模型，换 harness 的 **中位数只挪动 5.39 分**，7 个 ≥10 分，最大 20.90。」
3. 「而同一个 harness 换模型，极差是 70.7pp。**模型是主项，harness 是明显小一档的次项。但主项你买不到差异化 —— 大家用的是同几个模型；次项才是你能自己攥住的那部分。**」

**被追问「那 6.7→68.3 是不是标题党」** → 老实答：那是最弱模型上的极值，中位数是 5.39 分，两个数我都放上来了，就是不想只讲好听的。

**被追问「TB 榜是严格控制变量吗」** → 不是。榜上是不同提交方各自的 harness，框架、工具集、运行预算都不一样。所以我只敢说「小一档」，不敢说精确倍数。

**新增的高危追问（NOTES 未覆盖）：「那『1/4 量级』这个数怎么来的？」**
→ 必须能答：它是 **18.4pp ÷ 70.7pp**，而 18.4pp 那条对比（Opus 4.6：Meta-Harness 76.40% vs Claude Code 57.98%）**一方未经官方核验、两条相差 3 个月**，我们自己的研究笔记（M05 §1.2）就标了「不宜作为主论据」。双方都核验的版本是 62.92% vs 57.98% = 4.94 分。**建议改口径**：口头说成「一个数量级以内、但明显小一档」，或者干脆只报 5.39 / 20.90 / 70.7 三个数，不做除法。若坚持保留「1/4」，页面上要注明是**极值比极值**。

**「既然模型是主项，是不是该多花钱买模型」** → 该。两件事不冲突：买模型抬上限，做 harness 把上限兑现，且只有后者是你的差异化。

**补一个反证会显得更诚实**：mini-SWE-agent **100 行 Python** 拿 SWE-bench Verified 65%，同期精心 scaffold 也就 70–75%。所以正确的结论是「**选错 harness 会掉很多分，但做复杂不等于涨分**」。

### ② P13 的七层栈会被问「这是谁的分法」

→ 直接承认：不是行业公认，是按 `pi-mono` 四个包反推的。别的项目切得不一样（Böckeler 切 inner/outer、guides/sensors；HF 术语表把 harness 限成执行层、**不含 UI**）。这是本场的**范围声明**，不是定义。

### ③ P14 讲 AgentHarness，但 `pi` CLI 根本没用它

**这是本章第二大的雷，NOTES.md 没有列。** R10 §0 的 grep 结果是硬的：`grep -rn "AgentHarness" packages/coding-agent/src/` **无输出**。

### ⑤ P16 的「O(1) 操作」
